# Fix email move/labels -- Issue #159

## Problem

When a user asks the voice assistant to move an email to a folder/label (e.g. "invoices"), nothing happens and the user gets no feedback. Two root causes found:

1. **Silent success on non-existent folders**: Both Gmail (Unipile + IMAP) silently accept `moveToFolder` with a non-existent folder name. No error is thrown, the email stays in the inbox, but the system reports `{"moved": true}`.
2. **Hardcoded `"INBOX"` in Unipile `listInbox`**: The Unipile email listing hardcodes `folder=INBOX` in the API query. Gmail's inbox happens to have `provider_id: "INBOX"` so it works. Outlook's inbox has a different `provider_id`, causing a 422 error.

## What was done

### 1. E2E tests added (`packages/email/src/__tests__/e2e/email-client.e2e.ts`)

Two new test cases in the `describe.each(accounts)` block:

- **"moveToFolder throws when target folder does not exist"** -- sends email, attempts move to `NONEXISTENT_${Date.now()}`, asserts it throws and email stays in inbox.
- **"moveToFolder works with a user-created label from listFolders"** -- finds a non-special-use folder from `listFolders`, moves to it, verifies undo works. Skips if no user-created folders exist.

### 2. Folder existence validation before move

Added `validateFolderExists` in `packages/email/src/account-client.ts` -- calls `listFolders`, checks target folder is in the list (case-insensitive), throws with available folder names if not found. Wraps both `moveToFolder` implementations (Unipile + IMAP).

Same validation added in Python `apps/voice-pipeline/src/tools/handlers.py` in both `_dispatch_tool` (IMAP branch, ~line 690) and `_dispatch_tool_unipile` (~line 816). Both call `list_folders` before the move and raise `ValueError` with available folder names if not found.

### 3. Inbox folder resolution by role (`provider_id`)

**TypeScript** (`packages/email/src/unipile-client.ts`):
- Added `resolveInboxFolderProviderId(accountId)` helper -- fetches `/api/v1/folders`, finds the folder with `role: "inbox"`, returns its `provider_id`.
- `listInbox` now calls this instead of hardcoding `folder=INBOX`.
- `listFolders` now filters inbox by `role` instead of `name`.

**Python** (`apps/voice-pipeline/src/tools/unipile_client.py`):
- Added `_resolve_inbox_folder_provider_id(account_id)` -- same logic.
- `list_inbox` uses it instead of hardcoding `"INBOX"`.
- `list_folders` filters inbox by `role` instead of `name`.

### 4. Investigation scripts

Created `testscripts/2026.04.07-outlook-unipile-404/` with standalone scripts to investigate the Outlook Unipile 404 issue:
- `investigate.mjs` -- queries folders API, tests GET/PUT with different ID formats
- `test-fresh-email-put.mjs` -- sends email, finds it, tries PUT immediately
- `test-put-timing.mjs` -- measures how long until PUT works after email appears in list

## What is next: Outlook Unipile 404 on mutations

### Root cause identified

The investigation scripts revealed:

- Unipile returns two IDs per email: `id` (short, e.g. `hZWLnc8BXR6S9Um66u3jxg`) and `provider_id` (Outlook's long base64 ID)
- `mapToEmailSummary` in `unipile-client.ts:557` uses `provider_id` as the email ID: `id: String(item.provider_id ?? item.id ?? "")`
- For **freshly synced** Outlook emails, `PUT /api/v1/emails/{unipile_id}` returns 404 for ~7 seconds after the email appears in list
- `PUT /api/v1/emails/{provider_id}` works immediately
- However, the e2e tests are still getting 404 with `provider_id` on mutation operations

### Remaining investigation needed

The 404 errors in e2e happen on the **undo step** of archive/delete/move tests. The flow is:
1. `archiveEmail(emailId, "INBOX")` -- PUT with `provider_id`, sets `folders: []`
2. `waitUntilGoneFromInbox` -- polls until email leaves inbox
3. Undo via `moveEmail(identifier, to, from)` -- PUT with the ID from undo recipe

The undo recipe stores the `emailId` that was passed to `archiveEmail`. But `moveEmail` also calls `unipilePut` with this ID. The undo's `to` parameter is `"INBOX"` -- which is the hardcoded string, not the resolved inbox folder ID/provider_id.

**Likely cause**: The `folders` body param in the undo PUT uses `"INBOX"` as the target folder, which doesn't work for Outlook (same issue as `listInbox`). The fix should use the inbox `provider_id` (or the folder `id`) in the undo recipe's `to` param, not the hardcoded string `"INBOX"`.

### Specific things to check/fix

1. **Undo recipe `to` param**: `archiveEmail` stores `to: sourceFolder` where `sourceFolder` defaults to `"INBOX"`. For Outlook Unipile, this should be the resolved inbox folder ID. Check `deleteEmail` (uses `folders: ["TRASH"]` hardcoded) and `moveToFolder` similarly.

2. **All hardcoded folder names in unipile-client.ts**: grep for `"INBOX"`, `"TRASH"`, `"ARCHIVE"` -- these should all use resolved folder IDs for Outlook compatibility. Lines 128, 136, 155, 183.

3. **Archive test result confirmed**: The archive PUT itself succeeds (no 404), but `waitUntilGoneFromInbox` fails -- the email is still in inbox after `archiveEmail` with `folders: []`. So `folders: []` does NOT remove from inbox on Outlook Unipile. The archive function likely needs to use the resolved archive folder ID instead. Outlook has an archive folder with `role: "archive"` and `id: "uWfR3vNFXsiYAprMNEN5IQ"`.

4. **The core issue for all 4 Outlook mutation failures**: The `folders` body param in PUT calls uses hardcoded strings (`[]` for archive, `["TRASH"]` for delete, `["INBOX"]` for undo). For Outlook Unipile, these must use resolved folder IDs or `provider_id`s. This is the same class of bug as the `listInbox` fix.

5. **Fix approach**: Add a folder resolution layer in `unipile-client.ts` that resolves folder names/roles to their Unipile IDs. The functions that need updating:
   - `archiveEmail` (line 128): `folders: []` -> `folders: [resolvedArchiveId]` or remove from inbox by moving to archive
   - `deleteEmail` (line 155): `folders: ["TRASH"]` -> resolved trash folder ID
   - `moveToFolder` (line 183): `folders: [targetFolder]` -> already uses user-provided folder, but undo recipe stores `"INBOX"` as the source
   - `moveEmail` (line 210): `folders: [to]` -> `to` often comes from undo recipes with hardcoded `"INBOX"`

6. **After fixing**, run full e2e suite to verify all 4 test accounts pass.

7. **Python has no e2e test coverage for mutations.** The e2e tests in `packages/email/src/__tests__/e2e/` only cover the TypeScript `EmailAccountClient`. The Python voice pipeline (`handlers.py`, `unipile_client.py`) unit tests mock `_dispatch_tool`, so they never hit the real Unipile API. The Python fixes (resolved folder IDs in `archive_email`, `delete_email`, `move_to_folder`, undo handler `to_folders` fix) are the same logic as TypeScript but are currently untested against real accounts.

8. **Pre-existing Python undo bug found and fixed.** The `unipile_move_email` undo handler in `handlers.py:934` was reading `recipe.params["to_folder"]` (singular) and wrapping it in `{"folder": ...}`, but the recipes store `"to_folders"` (plural array) with `{"folders": [...]}`. Fixed to `{"folders": recipe.params["to_folders"]}`.
