# LLM Multi-Provider Plan

Short summary: add a simple shared LLM package so the WhatsApp executor, interaction, and narration agents can use either OpenRouter or another API provider such as Cerebras without rewriting the agent loops.

This plan is written so a new agent can continue the work without prior context.

## Goal

Add a small provider abstraction for the existing text-generation clients so the repo can support more than one inference API provider.

The first target is:

- keep the existing agent behavior the same
- keep the implementation simple
- support `openrouter` and `cerebras`
- avoid overengineering the package structure

Success means:

- the WhatsApp text and voice runtimes no longer instantiate OpenRouter clients directly
- provider choice is defined by code constants
- model choice is defined by code constants
- each runtime can choose its own provider and model independently
- adding a later provider is a small change

## Agreed Package Structure

Use a small package without `src/`:

- `packages/llm/client.ts`
- `packages/llm/types.ts`
- `packages/llm/providers/openrouter.ts`
- `packages/llm/providers/cerebras.ts`
- `packages/llm/package.json`
- `packages/llm/tsconfig.json`

Do not add `index.ts` unless import ergonomics later make it necessary.

## Current State

- The executor loops are already mostly provider-agnostic because they depend on an injected text client interface.
- The concrete implementation is still OpenRouter-specific and duplicated in two places.
- The shared DTO names are OpenRouter-specific even though the shapes are generic.
- The env layer is still hard-coded around `OPENROUTER_API_KEY`.
- The provider is effectively hard-coded to OpenRouter by the current client construction.
- The model constants are hard-coded to `google/gemini-3-flash-preview` in multiple runtimes.

## Findings To Preserve

- The text executor already depends on an injected client interface in `apps/whatsapp-server/src/text/executionAgent.ts`.
- The voice executor already depends on an injected client interface in `apps/whatsapp-agent/src/lib/openpoke/executionAgent.ts`.
- The current tool schema shape is generic JSON-schema function calling, not inherently tied to OpenRouter.
- The OpenRouter client implementation is duplicated across:
- `apps/whatsapp-server/src/text/openRouterClient.ts`
- `apps/whatsapp-agent/src/lib/openpoke/openRouterClient.ts`
- The current env loaders require `OPENROUTER_API_KEY` directly:
- `apps/whatsapp-server/src/text/env.ts`
- `apps/whatsapp-agent/src/lib/env.ts`
- We agreed not to introduce new provider/model env vars in the first implementation.
- The first implementation should keep provider and model selection as code constants close to the agent runtimes.
- The intended setup is per-runtime constants, not one global provider choice for the whole app.
- That means interaction, execution, summarization, and narration can each use different providers and different models.
- API keys should remain in env and should not be moved into constants.
- The current factory functions instantiate `FetchOpenRouterTextClient` directly in the text interaction, text execution, voice interaction, voice execution, and voice narration runtimes.
- The repo already uses simple provider switching elsewhere, for example in `apps/whatsapp-agent/src/lib/whatsappVoice.ts`.
- The agreed package structure is intentionally small and should not introduce `src/`, `index.ts`, or extra abstraction layers unless the code becomes messy.

## Tradeoffs And Technical Implications

- Keep the package small.
  - This is the preferred approach for this repo.
  - It reduces cognitive overhead and keeps the first change easy to review.

- Rename OpenRouter-specific DTOs to generic LLM DTOs.
  - This is a real cleanup, not cosmetic only.
  - It removes provider assumptions from runtime code.
  - It will touch imports in several agent files.

- Move provider-specific HTTP details into `providers/openrouter.ts` and `providers/cerebras.ts`.
  - This keeps the branching out of the agents.
  - It also makes later providers easier to add.

- Keep one shared `client.ts` factory.
  - This keeps runtime wiring simple.
  - It avoids spreading provider-selection logic across both apps.

- Do not add `index.ts` yet.
  - It is unnecessary for the first implementation.
  - We can add it later if package imports become annoying.

- Keep provider and model selection in constants for now.
  - This matches the current preference for a simple first implementation.
  - It avoids introducing a config layer that is not needed yet.
  - Constants should live close to the agent code that uses them.

- Keep API keys in env.
  - Secrets should not move into constants.
  - For the first pass, `OPENROUTER_API_KEY` can stay where OpenRouter is still used.
  - If Cerebras is added, a provider-specific API key env can be added only where needed.

- Keep role-specific models.
  - Interaction, execution, summarization, and narration may want different models.
  - Provider choice and model choice should be separate constants, not one combined string hidden in the factory.

- Allow role-specific providers.
  - Interaction and execution should be able to use different providers when that is useful.
  - The same should apply to summarization and narration in the voice app.
  - The shared package should not assume one provider per app.

- Cerebras support should be treated as OpenAI-compatible, but not assumed to be identical forever.
  - The request and tool-calling format is close enough for the first implementation.
  - We should keep provider-specific parsing/request code isolated in case behavior differs later.

## Target State

After this work:

- all text and voice agent runtimes use `packages/llm`
- agent code depends only on generic `Llm*` DTOs and `LlmTextClient`
- provider selection happens through constants in code
- each runtime owns its own provider/model constants
- the two app-local OpenRouter client files are deleted

## Clarification

The intended design is:

- text interaction and text execution can use different providers and different models
- voice interaction, voice execution, voice summarization, and voice narration can each use different providers and different models
- this should be expressed with separate constants in each runtime file unless repetition later justifies a tiny shared constants file
