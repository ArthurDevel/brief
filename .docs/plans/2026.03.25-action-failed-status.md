# Action "failed" Status

## High-Level Goal

When an action fails during approval (execution), mark it as `"failed"` in the database with the error reason stored for debugging. On bulk approve/reject, continue processing remaining actions instead of breaking on the first failure. Show the failure reason as a tooltip on the "failed" status badge in the UI.

## Important Technical Notes

### Move "mark as failed" logic into executeAction (action-queue.ts)

Instead of handling the failed state in the approve route's catch block, move it into `executeAction` itself. This keeps the action lifecycle state machine in one place (executeAction already manages pending -> approved -> executed). On dispatch failure:

1. Update the action row to `status: "failed"` with `result: { error: message }`
2. Re-throw the error so the caller (approve route) can return a 500 response

This makes the logic reusable if `executeAction` is ever called from another context.

Note: only the `dispatchTool` call is wrapped in try/catch for the "failed" transition. If the initial DB load or the final "executed" update fails, those are infrastructure errors and the action stays in its current state ("approved"). This is intentional -- infra errors are transient.

### Bulk loop -- continue instead of break

The `handleBulk` function currently does `break` on a non-OK response. Remove the `break` so it continues to the next action. Remove the `setError` call inside the loop. After the loop, call `loadSession()` to refresh the UI. Failed actions will show as `"failed"` in the table because the API route already marked them in the DB.

### Actions page filter

The actions page (`actions/page.tsx`) currently filters into `pending` and `executed | undone`. Failed actions fall through both filters and disappear. Add `"failed"` to the executed/completed filter so they show up in the history section.

### Migration SQL

The check constraint on `actions.status` has an auto-generated name. The migration must use the explicit constraint name from the initial schema. Pattern:

```sql
alter table actions drop constraint actions_status_check;
alter table actions add constraint actions_status_check
  check (status in ('pending', 'approved', 'executed', 'undone', 'rejected', 'failed'));
```

#### UI Changes

- The status badge for `"failed"` actions shows `title={action.result?.error}` so the error message appears on hover (native browser tooltip).
- Failed actions show a dash (`-`) in the actions column -- no buttons. Failed is a terminal state.
- On individual action failure (`handleAction`), immediately update the action in local `session.actions` state to `status: "failed"` with `result: { error: message }` so the badge renders right away without waiting for `loadSession()`. Remove the `setError` banner call for action failures -- the inline badge + tooltip replaces it.
