# Per-Session Log Capture

## High-Level Goal

Capture all raw log output (the same lines visible in the terminal) per voice session and upload them to Supabase Storage for debugging. A single new module (`session_logger.py`) intercepts logs from both loguru and stdlib logging using `contextvars` to attribute log lines to the active session. Logs are uploaded as `.log` text files alongside existing call recordings. Log capture must never block or crash the pipeline -- if it fails, the call continues normally.

## Important Technical Notes

### Why contextvars

The voice pipeline runs multiple concurrent sessions in the same asyncio event loop. Each `_webrtc_bot()` or `twilio_stream_ws()` call is a separate async task. Python's `contextvars.ContextVar` is propagated automatically to child async tasks, so setting the session_id once at the start of the bot handler is sufficient -- all downstream code (pipeline, tool handlers, IMAP calls via `asyncio.to_thread`) will inherit the context.

### Python 3.12 requirement

`asyncio.to_thread` only copies `contextvars.Context` into spawned threads from Python 3.12+. The project uses Python 3.12-slim (Docker). Add a comment in `session_logger.py` noting this dependency so nobody downgrades silently.

### Intercepting both logging systems

The codebase uses two logging systems:
- **loguru** in `server.py` (uses `logger.info(...)` from loguru)
- **stdlib logging** everywhere else (uses `logging.getLogger(__name__)`)

We add:
1. A **loguru sink** (function-based) that reads the `ContextVar` and appends to the session buffer
2. A **stdlib `logging.Handler`** subclass that does the same

Both are installed via an explicit `install()` function (NOT at module import time, to avoid side effects in tests). The `start(session_id)` function creates the buffer and sets the context var. The handlers check if a session is active before buffering -- if not, it's a no-op.

Use a consistent format string for both handlers so log lines look uniform in the output file. Example: `"{timestamp} {level} [{module}] {message}"`.

### Orphan cleanup context

The lifespan shutdown handler calls `_cleanup_session()` from a different async task than the original bot handler. The ContextVar will NOT be set in the lifespan task. Therefore `stop(session_id)` must work purely by dict lookup (keyed by session_id), not by reading the ContextVar. The ContextVar is only used by the handlers to determine which buffer to write to.

### Thread safety

`_handle_log_line` does a dict lookup + `list.append`. Both are GIL-atomic in CPython. A race between `stop()` (which pops the buffer) and a concurrent `_handle_log_line` from a thread could lose the very last log line -- this is an acceptable trade-off. `_handle_log_line` should check-and-return-early if the session_id is not in the dict.

### Buffer size cap

Add a `MAX_LINES = 50_000` constant. If a buffer exceeds this, stop appending. Prevents unbounded memory growth for pathological long-running sessions.

### Log recursion prevention

The ordering in `_cleanup_session` must be: `stop()` first (clears ContextVar + removes buffer), then `upload_session_logs()`. This way any logs emitted during upload are not captured to the now-removed buffer.

## Per-File Methods and Types/DTOs

### session_logger.py (NEW)

#### Module-level state

```
_buffers: dict[str, list[str]]    -- session_id -> list of formatted log lines
_current_session_id: ContextVar[str | None]
```

#### Constants

```
STORAGE_BUCKET = "session-logs"
MAX_LINES = 50_000
LOG_FORMAT = "{timestamp} {level} [{module}] {message}"
```

#### Methods

| Method | Arguments | Returns | Description |
|--------|-----------|---------|-------------|
| `install` | none | `None` | Adds the loguru sink and stdlib handler. Stores the loguru sink ID for removal. Safe to call multiple times (idempotent). |
| `uninstall` | none | `None` | Removes the loguru sink and stdlib handler. For use in test teardown. |
| `start` | `session_id: str` | `None` | Creates a log buffer for the session and sets the ContextVar to the session_id. |
| `stop` | `session_id: str` | `str` | Removes the buffer from the dict, clears the ContextVar (only if it currently holds the given session_id), returns the accumulated log text as a single string. Returns empty string if session_id is unknown. |
| `upload_session_logs` | `session_id: str, log_text: str, supabase: Client` | `None` (async) | Uploads the log text to Supabase Storage as `{session_id}.log`. Swallows all exceptions. |

Internal (prefixed with `_`):

| Method | Arguments | Returns | Description |
|--------|-----------|---------|-------------|
| `_handle_log_line` | `session_id: str, formatted_line: str` | `None` | Appends a formatted log line to the session's buffer. Returns early if session_id is not in the dict or buffer is at MAX_LINES. |
| `_SessionLogHandler` (class) | inherits `logging.Handler` | -- | Stdlib logging handler. In `emit()`, reads the ContextVar, formats the record, calls `_handle_log_line`. |
| `_loguru_sink` | `message` (loguru Message object) | `None` | Loguru sink function. Reads the ContextVar, calls `_handle_log_line` with the formatted message string. |

### server.py (MODIFIED)

#### Changes to lifespan startup

Call `session_logger.install()` once during lifespan startup.

#### Changes to `_setup_pipeline_session`

After creating the `ActiveSession`, call `session_logger.start(session.session_id)`. Also add `session_logger.stop(session.session_id)` to the existing `except` block (before `raise`) to prevent buffer leaks when setup fails.

#### Changes to `_cleanup_session`

After all existing cleanup steps (before `_live_pipeline_sessions.pop`), call `log_text = session_logger.stop(session.session_id)`, then `await session_logger.upload_session_logs(session.session_id, log_text, supabase)`.

### 009_session_logs_bucket.sql (NEW)

Same pattern as `008_call_recordings_bucket.sql`: creates a private Supabase Storage bucket `session-logs` with no public access.

## Success Criteria

- Every completed voice session has a `{session_id}.log` file in the `session-logs` Supabase Storage bucket
- Log files contain all terminal output from that session (both loguru and stdlib), with timestamps, levels, and module names
- Concurrent sessions do not leak logs into each other
- Log capture failure never crashes or blocks the voice pipeline
- All five tests pass
- No changes to any existing log statements in the codebase
