# Plan: Unipile Dual-Stack Email Accounts

## High-Level Goal

Introduce a new `user_email_accounts` table as the source of truth for mailbox connectivity, move custom IMAP/SMTP secret references out of `user_settings` into that table, and add a dual-stack email architecture:

- `gmail` and `outlook` accounts connect through Unipile and are addressed by stored Unipile account metadata.
- `custom` accounts continue to use direct IMAP/SMTP, but their host/user/secret references live in `user_email_accounts`.
- Supabase authentication remains unchanged.

The implementation covers the full mailbox surface of the product: settings/dashboard flows, live voice email flows, contact sync, newsletter generation, and end-of-session enrichment. The app should not have split behavior where only some features understand Unipile-backed Gmail/Outlook accounts.

## Important Technical Notes

### Data Migration and Rollout Safety

The migration should be split into two schema steps:

1. Create `user_email_accounts`, backfill existing custom IMAP/SMTP settings into that table, and update application code to read from the new table.
2. Remove legacy email columns from `user_settings` only after every web and voice code path has been switched.

This keeps rollout reversible and avoids a cross-runtime breaking change during the migration window. If a bug is found in Phase 2-5 code, all application code can be rolled back while the new table sits unused -- the old code will continue reading from `user_settings` until the legacy columns are dropped in 018.

The new table must be wired like the existing user-owned tables:

- Row-level security enabled.
- Select/insert/update/delete policies scoped to `auth.uid() = user_id` for user-facing clients.
- `updated_at` trigger attached via the shared `update_updated_at()` helper.

### One Active Account Per User in Phase 1

The new table should support multiple rows over time, but Phase 1 should enforce a single active mailbox per user. A partial unique index such as "one active account per user" keeps the schema future-friendly without forcing the UI or voice flows to solve multi-mailbox selection yet.

### Safe Storage Model

`user_email_accounts` stores connection metadata and secret references, not bearer credentials for Unipile-backed Gmail/Outlook accounts. The security boundary is:

- Unipile API key in server environment variables only.
- IMAP/SMTP passwords still stored in Supabase Vault, but referenced from `user_email_accounts`.
- Per-user Unipile rows store `unipile_account_id`, provider, email address, status, and timestamps; these are identifiers and state, not standalone mailbox credentials.

If any environment still has rows relying on legacy plaintext `user_settings.imap_password` or `smtp_password`, the rollout must include a one-time migration into Vault-backed secret IDs before dropping those columns. The schema cleanup step should not silently discard plaintext-only credentials.

### Provider-Aware Undo Semantics

The existing undo flow assumes IMAP folder moves keyed by Message-ID and source/destination folders. Unipile-backed undo recipes should preserve equivalent behavior, but the stored undo payload must use identifiers that remain stable for Unipile operations. The plan should keep undo behavior outcome-compatible while allowing different payload shape under the hood.

### Hosted Auth Correlation

The Unipile hosted-auth link generation should not trust client-submitted account identifiers. The connect route should generate the hosted-auth payload on the server and pass an HMAC-signed correlation token (containing the Supabase user ID and a timestamp) as Unipile's `name` field. Unipile returns this `name` value verbatim in the `notify_url` callback payload alongside `status` (`"CREATION_SUCCESS"` or `"RECONNECTED"`) and `account_id`. The `notify_url` handler must verify the HMAC signature before trusting the embedded user ID.

Unipile does not provide built-in signature verification for `notify_url` callbacks, so the HMAC-signed `name` field is the only authentication mechanism for the callback endpoint.

#### Environment Variables

Both `apps/web` and `apps/voice-pipeline` need:

- `UNIPILE_API_KEY` -- server-side API key for all Unipile REST calls
- `UNIPILE_DSN` -- Unipile API base URL (e.g. `https://{dsn}.unipile.com`)

Web-only:

- `UNIPILE_NOTIFY_SECRET` -- HMAC secret used to sign/verify the correlation token in the `name` field

These must be added to `apps/web/.env.example` and `apps/voice-pipeline/.env.example`.

### Settings API Loses Email, Stays Partial

Email account management moves entirely to `PUT /api/user/email-accounts/custom` and the Unipile connect/notify routes. `PUT /api/user/settings` no longer handles any email fields.

The settings API must preserve its existing partial update semantics for the remaining fields:

- General settings updates write only voice/tool/PIN fields.
- Schedule updates write only `callSchedule`.

The GET response still includes `emailAccount: EmailAccountSummary | null` (read from `user_email_accounts`) so the dashboard can render unified status.

### Voice Pipeline Abstraction

The current voice pipeline is built around a shared live IMAP connection plus a lock. Unipile-backed accounts do not need a persistent IMAP socket, but the tool handler should keep the existing serialization behavior so user-visible voice interactions remain deterministic across providers.

`pipeline.py` currently reads `user_context.imap_config.user` for prompt metadata and passes `user_context.smtp_config` to tool handlers. Both must switch to the new `user_context.email_account` field. The old `imap_config` and `smtp_config` fields on `UserContext` are replaced by `email_account: EmailAccount`.

### Background Jobs Must Share the Same Account Model

Contact sync, newsletter generation, and end-of-session enrichment all currently assume direct IMAP credentials. In the final migration they must resolve mailbox access from `user_email_accounts` using the same provider-aware abstraction as live tool execution; otherwise the product remains partially broken for Unipile-backed Gmail/Outlook users.

### Mailbox Identity Changes Must Invalidate Contacts

Today the app deletes `user_contacts` and forces a full sync when the configured inbox changes. The new model needs the same behavior keyed off mailbox identity rather than raw `imap_user`:

- Custom account updates should compare the previous active mailbox identity to the new one.
- Unipile connect/reconnect callbacks should do the same when they activate a different mailbox.
- When the mailbox identity changes, stale contacts should be cleared and the next sync should run in full mode.
