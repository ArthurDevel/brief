# Plan: Unipile Dual-Stack Email Accounts

## High-Level Goal

Introduce a new `user_email_accounts` table as the source of truth for mailbox connectivity, move custom IMAP/SMTP secret references out of `user_settings` into that table, and add a dual-stack email architecture:

- `gmail` and `outlook` accounts connect through Unipile and are addressed by stored Unipile account metadata.
- `custom` accounts continue to use direct IMAP/SMTP, but their host/user/secret references live in `user_email_accounts`.
- Supabase authentication remains unchanged.

The implementation covers the full mailbox surface of the product: settings/dashboard flows, live voice email flows, contact sync, newsletter generation, and end-of-session enrichment. The app should not have split behavior where only some features understand Unipile-backed Gmail/Outlook accounts.

## Important Technical Notes

### Data Migration and Rollout Safety

The migration should be split into two schema steps:

1. Create `user_email_accounts`, backfill existing custom IMAP/SMTP settings into that table, and update application code to read from the new table.
2. Remove legacy email columns from `user_settings` only after every web and voice code path has been switched.

This keeps rollout reversible and avoids a cross-runtime breaking change during the migration window.

### One Active Account Per User in Phase 1

The new table should support multiple rows over time, but Phase 1 should enforce a single active mailbox per user. A partial unique index such as "one active account per user" keeps the schema future-friendly without forcing the UI or voice flows to solve multi-mailbox selection yet.

### Safe Storage Model

`user_email_accounts` stores connection metadata and secret references, not bearer credentials for Unipile-backed Gmail/Outlook accounts. The security boundary is:

- Unipile API key in server environment variables only.
- IMAP/SMTP passwords still stored in Supabase Vault, but referenced from `user_email_accounts`.
- Per-user Unipile rows store `unipile_account_id`, provider, email address, status, and timestamps; these are identifiers and state, not standalone mailbox credentials.

### Provider-Aware Undo Semantics

The existing undo flow assumes IMAP folder moves keyed by Message-ID and source/destination folders. Unipile-backed undo recipes should preserve equivalent behavior, but the stored undo payload must use identifiers that remain stable for Unipile operations. The plan should keep undo behavior outcome-compatible while allowing different payload shape under the hood.

### Hosted Auth Correlation

The Unipile hosted-auth link generation should not trust client-submitted account identifiers. The connect route should generate the hosted-auth payload on the server and use a server-verifiable correlation value in Unipile's `name` field so the `notify_url` handler can safely map the callback back to the authenticated Supabase user.

### Voice Pipeline Abstraction

The current voice pipeline is built around a shared live IMAP connection plus a lock. Unipile-backed accounts do not need a persistent IMAP socket, but the tool handler should keep the existing serialization behavior so user-visible voice interactions remain deterministic across providers.

### Background Jobs Must Share the Same Account Model

Contact sync, newsletter generation, and end-of-session enrichment all currently assume direct IMAP credentials. In the final migration they must resolve mailbox access from `user_email_accounts` using the same provider-aware abstraction as live tool execution; otherwise the product remains partially broken for Unipile-backed Gmail/Outlook users.

- Legacy email columns on `user_settings` are removed only after all consumers have migrated and tests pass.
