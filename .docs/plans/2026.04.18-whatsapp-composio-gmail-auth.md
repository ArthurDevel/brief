# WhatsApp Composio Gmail Auth

## Goal

Replace the current hardcoded Composio wiring with a user-scoped Gmail authentication flow that starts from WhatsApp:

- if a WhatsApp user sends `authenticate gmail`
- we reply with a WhatsApp CTA button like `Connect with Gmail`
- the button opens `/whatsapp/connectors/gmail`
- that route uses the existing `/whatsapp/*` inline auth shell if the user is not yet signed in
- once signed in, the page starts a Composio Gmail connect flow
- Composio redirects back to our app
- we persist the resulting Composio `connected_account_id` in a new `user_composio_connections` table
- the WhatsApp agent/runtime switches away from the current global env-scoped Composio account and resolves the correct Composio connection for the current WhatsApp user

Plainly stated:

- this feature is meant to replace the current hardcoded Composio setup
- we are not designing a permanent dual system
- by the end of this work, the WhatsApp agent should use the user-specific connection from `user_composio_connections`, not `COMPOSIO_CONNECTED_ACCOUNT_ID`
- remove the old env-based connected-account runtime path as part of this implementation

Hard decisions from the discussion:

- keep Gmail hardcoded for the first version
- add a dedicated `user_composio_connections` table instead of overloading `user_email_accounts`
- do not send the raw Composio link directly in the WhatsApp message; send the user to our own `/whatsapp/connectors/gmail` page first
- `/whatsapp/connectors/gmail` must preserve the standalone WhatsApp auth model already established in `/whatsapp/*`
- replace the hardcoded Composio env usage as part of this feature, not as separate future cleanup
- remove the old env-based connected-account runtime path directly instead of keeping compatibility wiring around it

- After each phase, check the completed boxes in this document.
- When new findings pop up, add them to this plan before moving on.

## Target User Flow

```text
User sends "authenticate gmail" in WhatsApp
  -> inbound WhatsApp handler recognizes the hardcoded command
  -> system sends a WhatsApp CTA template with a button to /whatsapp/connectors/gmail?phone=<wa-phone>
  -> user opens /whatsapp/connectors/gmail
  -> if no Supabase session exists, the existing WhatsApp OTP auth shell appears inline on that same path
  -> after successful WhatsApp OTP auth, the user remains on /whatsapp/connectors/gmail
  -> page shows a Connect with Gmail action
  -> page POSTs to /api/whatsapp/connectors/gmail/start
  -> backend creates a Composio Gmail connection request for the signed-in user
  -> browser redirects to Composio
  -> user completes Google auth
  -> Composio redirects back to /api/whatsapp/connectors/gmail/callback?...&status=success&connected_account_id=...
  -> callback persists the Composio connection to user_composio_connections
  -> user is redirected back to /whatsapp/connectors/gmail?connected=1
  -> future WhatsApp agent/runtime loads the correct connected_account_id for this user instead of using one global hardcoded account
```

Important UX constraints:

- the WhatsApp message should deep-link to our app first, not directly to a Composio URL
- `/whatsapp/connectors/gmail` must remain inside the existing path-preserving WhatsApp auth flow
- the user should not be bounced through the main `/login` or `/dashboard` routes

## Key Tradeoffs And Technical Implications

### Use our own `/whatsapp/connectors/gmail` page as the entrypoint

Composio connect links are better created when the user is already in-browser and authenticated. Sending a raw Composio redirect URL in the WhatsApp message would make the flow more fragile, harder to debug, and less aligned with the current `/whatsapp/*` auth model.

Implication:

- the WhatsApp button should point at our app
- the connect page should create the Composio URL only after the user lands there

### Store Composio connections in a dedicated `user_composio_connections` table

`user_email_accounts` is specifically shaped around `unipile` and `imap_smtp` mailbox connectivity. Reusing it for Composio would blur semantics and force constraint changes that are unrelated to the existing email account model.

Implication:

- add a dedicated table for Composio toolkit connections
- keep the schema narrow and explicit for Gmail-first rollout
- avoid destabilizing the current email account system

### WhatsApp identity remains the bridge to the app user

The current WhatsApp auth model links a WhatsApp phone number to a Supabase user through `user_settings.whatsapp_phone`. That should remain the source of truth for identifying who is trying to connect Gmail from WhatsApp.

Implication:

- the connect page relies on the existing `/whatsapp/*` auth shell
- the runtime side should map inbound WhatsApp phone -> Supabase user -> `user_composio_connections`

### The agent must stop relying on global Composio env state

Today the agent uses one `COMPOSIO_USER_ID` and one optional `COMPOSIO_CONNECTED_ACCOUNT_ID` from env. That blocks per-user auth entirely.

Implication:

- `apps/whatsapp-agent/src/lib/env.ts` and `apps/whatsapp-agent/src/lib/composio.ts` need a redesign
- Composio session creation should become request/user scoped
- the runtime needs a reliable way to resolve the active Supabase user or at least the active `connected_account_id` from the inbound caller phone
- this replacement is part of the deliverable, not optional cleanup after the auth flow lands
- once the new lookup is in place, missing Gmail auth should fail fast instead of silently falling back to env configuration

### Gmail can be hardcoded now, but the table should not paint us into a corner

The user explicitly wants Gmail only for the first version. That does not mean the schema should assume there will never be other Composio toolkits later.

Implication:

- hardcode the UI flow and command handling for Gmail
- still store `toolkit` and provider metadata in the DB so the table can grow cleanly later

### Browser callback should be tied to a signed-in session

Composio redirects with `status` and `connected_account_id`. The simplest version is to require the user to still have the normal Supabase session from the `/whatsapp/*` auth island when they return.

Implication:

- the callback route can trust the signed-in user instead of inventing a separate HMAC correlation scheme immediately
- if session continuity proves unreliable, we may need to add a signed state token later

### WhatsApp delivery likely needs a second template type

The current WhatsApp helper only supports OTP text/template sending. The Gmail connect CTA is a different message type and needs its own approved WhatsApp template/button flow.

Implication:

- extend `apps/web/lib/whatsapp-messaging.ts` with a connector CTA send helper
- treat WhatsApp template approval as a requirement for this feature

## Suggested Data Model

`user_composio_connections`

- `id uuid primary key default gen_random_uuid()`
- `user_id uuid not null references auth.users(id) on delete cascade`
- `toolkit text not null` -- first value: `gmail`
- `provider text not null default 'composio'`
- `connected_account_id text not null`
- `status text not null default 'connected'`
- `external_user_id text` -- optional copy of the Composio user ID we use
- `connected_at timestamptz`
- `last_error text`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`

Constraints/indexes to add:

- check `provider in ('composio')`
- check `status in ('connected', 'reconnect_required', 'pending', 'error')`
- unique `(user_id, toolkit)` for the Gmail-first version
- unique `(connected_account_id)` if we want one local row per Composio account
- RLS policy so users can read their own rows; writes may stay server-side only

Open design choice to confirm during implementation:

- whether we store a separate Composio `external_user_id` or simply reuse the Supabase `user.id` string as the Composio user ID. Reusing the Supabase user ID is the simplest first version.

## Known Findings

- `apps/whatsapp-agent/src/lib/env.ts` currently assumes a single global `COMPOSIO_USER_ID` and optional `COMPOSIO_CONNECTED_ACCOUNT_ID`; this must change for per-user Gmail auth.
- The intended end state is full replacement of the global connected-account runtime path, not a permanent old-path/new-path split.
- `apps/web/app/whatsapp/*` already has the route-preserving auth behavior we want, so `/whatsapp/connectors/gmail` should live inside that tree instead of inventing a new auth flow.
- `user_email_accounts` is intentionally constrained to `unipile` and `imap_smtp`, so it is the wrong storage home for Composio connected accounts.
- Composio’s manual auth flow supports `session.authorize("gmail", { callbackUrl })` and redirects back with `status` and `connected_account_id`, which matches the intended browser flow.
- The implementation uses the Supabase `auth.users.id` value directly as the Composio external user ID.
- `connected_account_id` was made nullable in `user_composio_connections` so pending/error rows can exist before a successful Composio callback returns an account ID.
- The WhatsApp voice runtime resolves the caller from LiveKit participant metadata that already contains the normalized WhatsApp phone number from the bridge.
- Reconnect failures keep the same per-user path and surface an actionable spoken error instead of falling back to a global Composio account.
