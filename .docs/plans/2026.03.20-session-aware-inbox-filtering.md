# Session-Aware Inbox Filtering

## High-Level Goal

When the agent calls `list_inbox` or `search_emails` during a session, the results should reflect queued (pending/approved) actions from that session:

1. **Hide** emails that have a pending `delete_email` or `archive_email` action
2. **Show** queued `send_email` actions as synthetic entries appended to `list_inbox` results

This prevents the agent from seeing stale state and re-processing emails it already acted on.

## Important Technical Notes

### Filtering location

The filtering happens **inside** `_dispatch_tool` / `dispatchTool`, between the IMAP fetch and the markdown format call. This is the only place where we have access to the raw `EmailSummary[]` list before it becomes a markdown string.

Flow for `list_inbox` / `search_emails`:
1. Fetch emails from IMAP -> `EmailSummary[]`
2. Call `fetchPendingEmailIds(sessionId, supabase)` -> `Set<string>`
3. Filter: `emails.filter(e => !pendingIds.has(e.id))`
4. Format the filtered list with `formatEmailSummaries()`
5. (Only for `list_inbox`) Call `fetchQueuedSends(sessionId, supabase)`, append formatted section if non-empty

### JSONB field extraction

`email_id`, `to`, and `subject` live inside the JSONB `arguments` column, not as top-level columns. Both `fetchPendingEmailIds` and `fetchQueuedSends` should select the full `arguments` column and extract fields client-side:

```
// TS
const rows = await supabase.from("actions").select("arguments").eq(...).in(...)
const emailIds = new Set(rows.map(r => r.arguments.email_id))

// Python
rows = supabase.table("actions").select("arguments").eq(...).in_(...).execute()
email_ids = {r["arguments"]["email_id"] for r in rows.data}
```

Do NOT use PostgREST JSONB arrow syntax -- it is fragile and varies by client version. Extract client-side.

### executeAction call site

`executeAction` also calls `dispatchTool`. When executing a previously-approved action, we do NOT want session-aware filtering. Pass `null` for `sessionId` in that call path, and skip filtering when `sessionId` is null.

### Queued sends section

For pending `send_email` actions, query the DB for `status IN ('pending', 'approved')` with `tool_name = 'send_email'` and `session_id = current_session`. Format as:

```
## Queued Outgoing (2 emails)

- **To:** alice@example.com | **Subject:** Re: Meeting notes
  *Status: Awaiting approval*

- **To:** bob@example.com | **Subject:** Invoice follow-up
  *Status: Awaiting approval*
```

Queued sends are only appended to `list_inbox`, not `search_emails` (search results are query-specific, queued sends don't match arbitrary queries).

### Fake Supabase extension (TS tests)

The existing fake Supabase in the test file supports `.select().eq().single()`. The new `fetchPendingEmailIds` query needs `.select().eq().in().in()` chaining. The fake must be extended to support `.in()` filtering, or the query can be structured as multiple `.eq()` calls with client-side filtering. Simplest: extend the fake with `.in()` support.

|--------|-----------|---------|-------------|
| `fetchPendingEmailIds` | `sessionId: string, supabase: SupabaseClient` | `Promise<Set<string>>` | Queries actions table for pending/approved delete_email and archive_email actions in this session, returns set of email_ids |

## Success Criteria

- When 20 emails are queued for deletion, a subsequent `list_inbox` call within the same session returns 0 of those 20 emails
- When an email is queued for archive, `search_emails` does not return it
- When `send_email` is queued, the next `list_inbox` call shows a "Queued Outgoing" section with the email details
- Pending actions from a different session do NOT affect the current session's view
- No filtering occurs when `executeAction` dispatches a tool (sessionId = null)
- All existing tests continue to pass
- The IMAP layer is not changed -- filtering is purely in the handler layer
