# Pipecat Voice Pipeline (`apps/voice-pipeline/`)

## High-Level Goal

Replace the OpenAI Realtime API (all-in-one STT+LLM+TTS) with a modular **Pipecat** pipeline using **Deepgram STT** + **OpenRouter LLM** + **Deepgram TTS**, running as a new standalone Python app alongside the existing TypeScript voice gateway.

**Why:** The current OpenAI Realtime approach is expensive, not modular (can't swap providers), and uses basic silence-based VAD. Pipecat gives us prosody-based turn detection (SmartTurn v3), pitch-preserving speed control, and per-component provider flexibility at lower cost.

**Both backends coexist.** The existing `apps/voice-gateway/` stays untouched. The dashboard can connect to either.

## Important Technical Notes

### Custom Twilio Transport

Pipecat has **no native Twilio transport**. The closest reference is `pipecat.transports.websocket.fastapi.FastAPIWebsocketTransport`. The custom `TwilioTransport` must:

1. Extend `BaseTransport` with `input()` and `output()` methods returning `BaseInputTransport` / `BaseOutputTransport` subclasses
2. The input transport runs a background task reading the FastAPI WebSocket. Twilio sends JSON: `{"event": "media", "media": {"payload": "<base64-mulaw-8kHz>"}}`. Parse, decode base64, transcode mulaw 8kHz -> PCM16 at the pipeline's sample rate, push as `InputAudioRawFrame`
3. The output transport implements `write_audio_frame()` which transcodes PCM16 -> mulaw 8kHz, base64-encodes, sends as `{"event": "media", "media": {"payload": "..."}}`
4. Handle Twilio `"event": "start"` (extract and store `streamSid` -- required for sending `"event": "clear"` to interrupt audio playback on the phone side during interruptions) and `"event": "stop"` (trigger disconnect)
5. Implement `send_clear()` method that sends `{"event": "clear", "streamSid": "..."}` to flush queued audio -- called when the pipeline detects a user interruption via VAD

### Pipecat Function Calling Integration

Pipecat's `OpenAILLMService` supports function calling natively via the OpenAI-compatible API. Key integration:

1. Pass tool definitions via `tools` parameter on the LLM service
2. Register each tool handler using `llm.register_function(name, handler)` -- this is the standard Pipecat pattern (e.g., `llm.register_function("list_inbox", handle_list_inbox)`). Each registered handler receives the function arguments and returns a result string. Internally, route through `tools/handlers.py:handle_tool_call()`.
3. IMAP operations are synchronous (`imapclient`), so wrap in `asyncio.to_thread()` to avoid blocking the event loop

### Initial Greeting

When a WebRTC client connects, the pipeline should send an initial `LLMRunFrame` to trigger a greeting (matching the test script pattern at line 355-358). Without this, the assistant stays silent until the user speaks first. For the Twilio path, the TwiML already says "Connected. How can I help you?" but the pipeline should also send a greeting frame after the transport is ready.

### IMAP Connection Ownership

Each session (WebRTC or Twilio) creates its own IMAP connection on connect and closes it in a `finally` block on disconnect. The `server.py` functions `bot()` and `twilio_stream_ws()` own this lifecycle -- not the pipeline factory.

### SoundTouch Library Path

The `libSoundTouchDll` path is platform-specific. Configurable via `SOUNDTOUCH_LIB_PATH` env var. Defaults:
- macOS (Homebrew): `/opt/homebrew/lib/libSoundTouchDll.dylib`
- Linux: `/usr/lib/x86_64-linux-gnu/libSoundTouch.so`

If the library is not found, the speed processor should gracefully disable itself (passthrough mode) rather than crash.

### IMAP Connection Resilience

IMAP connections can drop during long calls. Implement the same `withReconnect` pattern from the TS codebase: wrap each IMAP operation with a try/reconnect/retry pattern. If reconnect fails, return a friendly error message to the LLM rather than crashing the pipeline.
