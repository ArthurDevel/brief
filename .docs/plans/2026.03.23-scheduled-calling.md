# Scheduled Calling Feature

## High-Level Goal

Allow users to schedule daily outbound calls from the voice assistant. In settings, the user picks one time per day of the week (e.g. Monday 09:00, Tuesday off, Wednesday 14:30) and the system calls them at that time. The call is a normal voice interaction -- same pipeline, same tools. If the user does not answer, the call is skipped (no retry). Scheduled calls count toward the monthly usage limit.

The scheduler runs as a background `asyncio` task inside the existing voice-pipeline process. It checks every 30 seconds which users are due for a call, uses a `last_call_at` field inside the schedule JSONB as a deduplication guard to prevent double-calls, and initiates outbound calls via the Twilio REST API.

## Important Technical Notes

### Single JSONB column: `call_schedule`

All schedule data lives in one JSONB column on `user_settings`:

```json
{
  "timezone": "America/New_York",
  "last_call_at": "2026-03-23T14:00:00Z",
  "monday":    "09:00",
  "tuesday":   null,
  "wednesday": "14:30",
  "thursday":  "09:00",
  "friday":    "09:00",
  "saturday":  null,
  "sunday":    null
}
```

- Day keys: `"HH:MM"` string (local time) or `null` (no call that day).
- `timezone`: IANA timezone string (e.g. `"America/New_York"`).
- `last_call_at`: ISO 8601 timestamptz string, used as the dedup guard. Set by the scheduler after a successful call. The frontend never writes this field.

### Deduplication: preventing double calls

The scheduler runs every 30 seconds, so it will re-query the same users multiple times within their scheduled minute. To prevent calling a user twice:

1. Before initiating a call, the scheduler atomically claims the slot by updating `last_call_at` inside the JSONB with a WHERE guard:
   ```sql
   UPDATE user_settings
   SET call_schedule = jsonb_set(call_schedule, '{last_call_at}', to_jsonb(now()::text))
   WHERE user_id = $1
     AND (
       call_schedule->>'last_call_at' IS NULL
       OR (call_schedule->>'last_call_at')::timestamptz
          < (date_trunc('day', now() AT TIME ZONE (call_schedule->>'timezone'))
             AT TIME ZONE (call_schedule->>'timezone'))
     )
   ```
   The double `AT TIME ZONE` is critical: `now() AT TIME ZONE tz` converts to a naive timestamp in the user's zone, `date_trunc('day', ...)` truncates to midnight, and the outer `AT TIME ZONE tz` converts back to a proper `timestamptz`. Without the outer cast, PostgreSQL interprets the naive timestamp as UTC, which is wrong for non-UTC users.

2. This returns 0 rows if the user was already called today (in their local timezone), preventing duplicates even across concurrent scheduler ticks.

3. If the subsequent Twilio call fails, the scheduler rolls back `last_call_at` to its previous value so the user can be retried on the next tick.

### Timezone dependency

The scheduler uses `zoneinfo` from Python stdlib (3.9+). The Docker image (`python:3.12-slim`) includes timezone data. If it ever doesn't, add `tzdata` to `requirements.txt`.

### Time matching: using a window, not exact minute

The scheduler checks every 30s, but slow iterations or timing drift could cause it to skip an exact minute. `get_due_users` matches the scheduled time against a 5-minute window: the user is "due" if `scheduled_time <= current_local_time < scheduled_time + 5min`. Combined with the dedup guard, this ensures:
- A user is not missed due to scheduler jitter.
- A user is never called twice (the dedup guard fires after the first call).

### Scheduler approach: fetch-all + filter in Python

Since each user has a different timezone, efficiently querying "users due now" in a single SQL query requires per-row timezone conversion. For simplicity (and because user counts are low), the scheduler fetches all users with a non-null `call_schedule` and filters in Python. This can be optimized to an RPC/raw SQL query later if needed.

### Outbound call flow (Twilio)

Twilio's `calls.create()` accepts a `url` parameter -- Twilio fetches TwiML from this URL when the callee answers. We add a new endpoint `/twilio/scheduled-call` that:
1. Validates the internal API key from query params (`?token=<key>`). Note: the token is in the URL because Twilio only supports URL-based callbacks (no custom headers). This is a standard Twilio pattern.
2. Returns `<Connect><Stream>` TwiML pointing at `/twilio-stream`, with `userId` as a custom parameter -- identical to what `build_twiml_connect` produces today after PIN verification.
3. The `stream_url` must be built using `settings.public_url` (same logic as `twilio_verify_pin` in `server.py` lines 649-653), NOT `request.url.hostname`, because the request comes from Twilio's servers and `request.url.hostname` may be an internal hostname.

Important: Twilio sends the callback as a POST with `application/x-www-form-urlencoded` form data, not JSON. The endpoint must parse `request.form()` and read `userId` and `token` from `request.query_params`.

This means the existing `twilio_stream_ws` handler works unchanged -- it receives the `userId` from the stream's custom parameters and runs the normal pipeline.

### Timezone in the frontend

The browser's `Intl.DateTimeFormat().resolvedOptions().timeZone` is used to preload the timezone picker on first visit (only if `timezone` is null in the schedule). The user can change it. The timezone is always visibly displayed next to the schedule so the user knows exactly what timezone applies.

## Success Criteria

1. A user can configure a weekly call schedule (time per day + timezone) in the dashboard Settings > Schedule tab.
2. The scheduler initiates an outbound Twilio call at the configured time in the user's timezone.
3. A user is never called twice for the same scheduled slot (dedup guard works).
4. Users who have exceeded their monthly usage limit are not called.
5. If the user does not answer, the call is simply skipped (no retry).
6. The outbound call enters the same voice pipeline as a normal inbound call (full email assistant interaction).
7. All 9 unit tests pass.
