# Multi Phone Number Support

## High Level Goal

Support multiple company phone numbers (US, Belgium, and extensible for future countries) so users are matched to the correct local number. The user's phone number and country are stored together as JSONB. The frontend auto-detects country from the phone prefix (using `libphonenumber-js`) and shows the matching company QR code. If no company number exists for the user's country, a message is shown listing available countries. The backend prevents outbound scheduled calls to unsupported countries.

Company phone numbers are environment-aware (`dev` or `prod`) so dev and prod servers use different Twilio numbers. Setup scripts are provided to add new phone numbers and update Twilio webhooks.

## Important Technical Notes

### Migration: phone_number text -> phone JSONB

The migration must handle existing data. Steps:
1. Create `company_phone_numbers` table with `environment` column and seed data (US + BE prod numbers)
2. Add `phone` JSONB column to `user_settings`
3. Migrate existing `phone_number` values: `UPDATE user_settings SET phone = jsonb_build_object('number', phone_number, 'countryCode', 'US') WHERE phone_number IS NOT NULL` (assume existing users are US since that was the only number)
4. Drop the old `phone_number` column (this also drops the implicit unique constraint)
5. Drop the old `idx_user_settings_phone` index
6. Create a **unique** functional index: `CREATE UNIQUE INDEX idx_user_settings_phone_number ON user_settings ((phone->>'number'))` -- unique to prevent two users registering the same phone (existing code uses `.single()` which would throw on duplicates)
7. Enable RLS on `company_phone_numbers` with SELECT policy for authenticated users (no INSERT/UPDATE/DELETE -- admin only via service role)

### company_phone_numbers table schema

```sql
create table company_phone_numbers (
  id uuid primary key default uuid_generate_v4(),
  phone_number text not null unique,       -- E.164 format
  label text not null,                      -- e.g. "United States", "Belgium"
  country_code text not null,              -- ISO 3166-1 alpha-2 (e.g. "US", "BE")
  environment text not null default 'prod' -- 'dev' or 'prod'
    check (environment in ('dev', 'prod')),
  is_active boolean not null default true,
  created_at timestamptz default now(),

  -- one number per country per environment
  constraint company_phone_numbers_country_env_unique unique (country_code, environment)
);
```

The `country_code` column is NOT globally unique because the same country can have different numbers for dev and prod. Instead, the unique constraint is `(country_code, environment)`.

Seed data:
- `('+16509774723', 'United States', 'US', 'prod', true)` -- current US prod number
- `('<belgian_prod_number>', 'Belgium', 'BE', 'prod', true)` -- new BE prod number
- Dev numbers should be added via the `add-company-phone.sh` script after setup

### APP_ENVIRONMENT setting

A new `APP_ENVIRONMENT` env var (`dev` or `prod`, default `prod`) is added to the voice pipeline and web app. This determines which company phone numbers are used.

- Voice pipeline: `Settings.app_environment` field, loaded from `APP_ENVIRONMENT` env var
- Web app: `NEXT_PUBLIC_APP_ENVIRONMENT` env var (needs to be public so the frontend can filter)
- All queries to `company_phone_numbers` filter by `environment = <app_environment>`
- The `dev-server-start.sh` script sets `APP_ENVIRONMENT=dev` automatically

### lookup_user_by_phone: use maybe_single() instead of single()

The current `lookup_user_by_phone` uses `.single()` which raises an `APIError` (PGRST116) when no row is found, rather than returning `None`. The implementation should switch to `.maybe_single()` which returns `None` for zero rows and raises only on multiple rows. This is a pre-existing bug that this change fixes.

### Supabase JSONB querying from Python

The current query `.eq("phone_number", phone)` becomes `.eq("phone->>number", phone)`. PostgREST uses `column->>key` syntax (no quotes around the key) for JSONB text extraction:

```python
supabase.table("user_settings").select("user_id, pin_locked").eq("phone->>number", phone)
```

### Scheduler: resolving the from_ number (avoiding N+1 queries)

Instead of querying `company_phone_numbers` per-user inside `initiate_scheduled_call`, we fetch all company phone numbers **once per scheduler tick** in `_scheduler_loop` and pass them as a lookup dict (`dict[str, str]` mapping `country_code -> phone_number`) to `initiate_scheduled_call`.

Flow:
1. `_scheduler_loop` calls `fetch_company_phones(supabase)` once per tick
2. Passes the dict to each `initiate_scheduled_call(user, settings, supabase, company_phones)` call
3. `initiate_scheduled_call` looks up `user.country_code` in the dict
4. If no match, logs warning and returns False (do NOT call Twilio)
5. Uses the matched number as `from_`

Updated call site in `_scheduler_loop`:
```python
company_phones = fetch_company_phones(supabase, settings.app_environment)
for user in due_users:
    initiate_scheduled_call(user, settings, supabase, company_phones)
```

### Removing twilio_phone_number from Settings

`Settings.twilio_phone_number` is currently used in two places:
1. `scheduler.py` line 219: `from_=settings.twilio_phone_number` -- replaced by lookup dict
2. `scheduler.py` line 262: `start_scheduler` check -- replace with check for `twilio_account_sid` and `twilio_auth_token` only (the from number comes from DB now)

The `TWILIO_PHONE_NUMBER` env var and `Settings.twilio_phone_number` field are removed entirely.

### Phone number validation: no country restriction on save

The `PUT /api/user/phone` route does NOT validate that the user's country is a supported company phone country. Any valid E.164 number can be saved (the phone is needed for caller ID authentication regardless). The unsupported-country check happens only at display time (call page) and at outbound-call time (scheduler).

### dev-server-start.sh changes

The script currently reads a single `TWILIO_PHONE_NUMBER` from env and configures its webhook. With multiple numbers in the database, the script needs to:
1. Remove the `TWILIO_PHONE_NUMBER` env var requirement
2. Set `APP_ENVIRONMENT=dev`
3. Query `company_phone_numbers` from Supabase where `environment = 'dev'` and `is_active = true`
4. Loop over each number: look up Twilio SID, configure the webhook
5. If no dev numbers exist, print a message pointing to `add-company-phone.sh` and continue without Twilio

### Setup scripts

Two bash scripts in `scripts/` at the project root. Both load `.env` from the voice-pipeline directory for Supabase and Twilio credentials.

Each script must have a clear usage block at the very top (in the header comment) with:
- One-line description of what the script does
- Full usage examples with all argument combinations
- List of required env vars (loaded from `.env`)
- Prerequisites (e.g. curl, jq)

**`add-company-phone.sh`** -- Add a new company phone number to the database and configure its Twilio webhook.

Usage: `./scripts/add-company-phone.sh --phone "+32123456789" --country BE --label "Belgium" --env dev --webhook-url "https://my-server.com"`

Steps:
1. Validate required args: `--phone`, `--country`, `--label`, `--env` (dev/prod)
2. Insert into `company_phone_numbers` via Supabase REST API (using service role key)
3. If `--webhook-url` is provided: look up the Twilio phone SID, configure the voice webhook
4. Print confirmation with the inserted row

**`update-twilio-webhooks.sh`** -- Update Twilio voice webhooks for all company phone numbers to point to a new server URL.

Usage: `./scripts/update-twilio-webhooks.sh --url "https://new-server.com" --env prod`

Steps:
1. Validate required args: `--url`, `--env` (dev/prod)
2. Query `company_phone_numbers` from Supabase where `environment = <env>` and `is_active = true`
3. For each number: look up the Twilio phone SID, update the voice webhook to `<url>/twilio/voice`
4. Print summary of updated numbers

### Frontend: libphonenumber-js auto-detection

Use `parsePhoneNumber` from `libphonenumber-js` to extract country from the phone input:
```typescript
import { parsePhoneNumber } from "libphonenumber-js";
const parsed = parsePhoneNumber("+32485123456");
// parsed.country === "BE"
```

The country dropdown shows all countries detected by `libphonenumber-js` (not just supported ones). This allows users from any country to save their phone number. The dropdown auto-updates on phone input change but remains manually editable.

### Call page loading state

The call page currently renders synchronously. After this change it must fetch user settings + company phones on mount. A loading state is shown while these fetches are in-flight, consistent with how `GeneralTab.tsx` handles loading.

### Country dropdown UX

The dropdown should show a curated list of common countries (not all 240+ from libphonenumber-js). The auto-detected country from the phone input is always shown/pre-selected. The list should include at minimum: US, BE, and any other countries in `company_phone_numbers`, plus common ones (UK, DE, FR, NL, etc.). The exact list can be refined later.

### Deployment: phases 1-3 must ship together

The migration (Phase 1) drops the `phone_number` column. The settings API (Phase 3) reads `row.phone_number` via `mapRowToSettings`. If the migration is deployed before the settings route is updated, the GET endpoint will break. Phases 1, 2, and 3 must be deployed atomically (same commit/deploy). The defaults block in the GET handler (lines 90-106) also needs `phoneNumber: null` changed to `phone: null`.

### Belgian phone number placeholder

The seed data for the Belgian number uses `'<belgian_number>'`. The actual number must be filled in before the migration is applied. The implementer should ask the user for this number.

1. A user can set their phone number with a country on the settings page
2. Country is auto-detected from the phone prefix via `libphonenumber-js`
3. Users from any country can save their phone number (no country restriction)
4. The call page shows the QR code for the matching company number (US or BE)
5. If the user's country has no matching company number, a clear message is shown listing the supported countries
6. Incoming calls still authenticate correctly via the JSONB phone column
