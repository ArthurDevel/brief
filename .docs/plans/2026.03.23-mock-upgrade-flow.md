# Mock Upgrade Flow (Plan Selection -> Payment Method -> Free Month)

## High-Level Goal

Create a multi-step upgrade flow that feels like a real subscription checkout. The user selects a plan, picks a payment method, and then -- instead of being charged -- sees a friendly message granting them a free month of Pro. The backend actually upgrades the user's plan to `pro` in the database.

Flow:
1. **Plan Selection** -- side-by-side comparison, user clicks "Continue with Pro"
2. **Payment Method** -- user picks a payment method (Credit Card, iDEAL, Bancontact), clicks "Continue to Payment"
3. **Confirmation** -- message: "We're still setting up our payment system. Enjoy a free month of Pro on us!" + plan is upgraded in DB

## Important Technical Notes

### RLS requires service role for update

The `subscriptions` table has a **select-only** RLS policy -- there is no update policy for users. The upgrade API route must use `createServiceRoleClient()` (from `apps/web/lib/supabase/client.ts`) to perform the plan update, not the cookie-based user client. The user client is only used to authenticate the request and get the user ID.

### Upsert instead of update

Use upsert (on conflict `user_id`) rather than a plain update. If a subscription row somehow does not exist (e.g. trigger failure for older users), the upsert creates it. This matches how the auth callback already handles missing rows.

### Check Supabase response for errors

After the upsert call, check `.error` on the Supabase response. If the upsert failed (network issue, etc.), return a 500 with the error message. Do not assume success.

### No migration needed

The `plan` column already accepts `'pro'` via its check constraint. No schema change required.

## Per-File Methods and Types/DTOs

### types.ts (MODIFIED)

#### Types

```
UpgradeResponse {
  plan: "free" | "pro"
  error?: string
}
```

Note: no `success` field -- follow the existing pattern where 200 means success and non-200 includes `{ error: string }`. On 200 the response contains `{ plan }`. On 401/500 the response contains `{ error }`.

---

### upgrade/route.ts (NEW)

#### Methods

| Method | Arguments | Returns | Description |
|--------|-----------|---------|-------------|
| `POST` | `NextRequest` (body ignored) | `NextResponse<UpgradeResponse>` | Authenticates user via cookie-based client, upserts their subscription to `plan = 'pro'` using service role client, checks for Supabase errors, returns the new plan. Idempotent: calling as a pro user simply returns `{ plan: "pro" }` (the upsert is a no-op). Returns 401 with `{ error }` for unauthenticated requests, 500 with `{ error }` for DB failures. |

4. Update `BillingTab.tsx`: replace disabled button with a `<Link>` to `/dashboard/settings/upgrade`, update JSDoc

## Success Criteria

- Free-plan user can click "Upgrade to Pro" on the billing tab
- User sees a 3-step flow: plan selection -> payment method -> confirmation
- On the confirmation step, the user's plan is upgraded to `pro` in the database
- User sees: "We're still setting up our payment system. Enjoy a free month of Pro on us!"
- After upgrading, the billing tab shows `pro` as the current plan with the 5h limit
- Already-pro users do not see the upgrade button on the billing tab
- Pro users who navigate directly to `/dashboard/settings/upgrade` are redirected to the billing tab
- Unauthenticated requests to the upgrade endpoint return 401
- Failed upgrade attempts show an error with a retry option
