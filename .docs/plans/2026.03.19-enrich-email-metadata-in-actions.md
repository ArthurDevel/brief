# Enrich Email Metadata in Action Arguments

## Goal

Store email metadata (subject, from) in the `arguments` column for actions that reference an `email_id`. This makes the session summary email and dashboard display meaningful info ("Delete: Weekly standup notes from Alice") instead of just a raw ID.

**Two-step approach:**
1. **During voice session**: Save the RFC `message_id` (stable email identifier) into action arguments. This is already available from the IMAP envelope -- zero extra IMAP calls.
2. **At end-of-session**: Use `message_id` to look up subject/from for all email-referencing actions. Update the DB, then send the summary email.

The `message_id` is stable across folder moves (archive, delete, etc.), so no folder-routing logic is needed at enrichment time.

|--------|-----------|---------|-------------|
| `enrichActionsWithEmailMeta` | `actions: ActionRow[], imapClient: ImapFlow` | `Promise<ActionRow[]>` | For each action with `email_id` in arguments: if `message_id` is present, use `fetchEmailMetaByMessageId`; otherwise use `fetchEmailMetaByUid`. The `POST` handler gets new steps between loading actions and sending the email:
1. Load user IMAP credentials from `user_settings` + Vault (same pattern as approve route, filter by `session.user_id` explicitly since service role bypasses RLS)
2. Open IMAP connection
3. Call `enrichActionsWithEmailMeta`, then update each enriched action's `arguments` column in the DB
4. Close IMAP connection

Entire enrichment block wrapped in try/catch so email sending still happens on IMAP failure.

## Important Technical Notes

### Why message_id is saved during the session (not at end-of-session)
The RFC Message-ID is a stable identifier that does not change when emails move between folders. By saving it during tool execution (when the IMAP connection is already open and the folder already selected), we avoid the problem of stale UIDs at enrichment time. The envelope fetch adds ~10ms per archive/delete call.

### Envelope fetch ordering
In `archive_email`/`delete_email`, the envelope fetch MUST happen after `client.select_folder(source_folder)` (so the UID is valid in the selected context) and before `client.move(...)` (so the email is still there).

### Undo recipe format is NOT changing
The undo recipe dict continues to use `email_id` in params, same as before. The `message_id` is only merged into the action `arguments` column for enrichment purposes. This avoids breaking `_dispatch_undo` in Python or `dispatchUndo` in TypeScript.

### Pending actions without message_id
Pending actions (e.g. `delete_email`, `archive_email` if configured as queued) are not executed during the session, so no envelope is fetched. The email is still in INBOX at end-of-session, so `fetchEmailMetaByUid` works for these. If a race condition occurs (user approves from email before enrichment runs), the per-action try/catch handles the failure gracefully.

### fetchEmailMetaByMessageId searches multiple folders
Gmail's All Mail does not include Trash. So `fetchEmailMetaByMessageId` searches All Mail first, then Trash if not found. This covers both archived and deleted emails.

### IMAP credentials in end-of-session route
The end-of-session route currently only uses Supabase. It needs IMAP access for enrichment. The approve route demonstrates the pattern: load `user_settings` for host/port/user, retrieve password from Vault via `retrieveSecret`. The end-of-session route does the same, filtering by `user_id` explicitly (service role client bypasses RLS).

### Per-action failure tolerance
An email may have been permanently deleted. `enrichActionsWithEmailMeta` wraps each fetch in try/catch and skips that action on failure. The action keeps its original arguments.

### Complete IMAP failure tolerance
The entire enrichment block in the POST handler is wrapped in try/catch. If IMAP is completely unreachable, the email is still sent with un-enriched data.
