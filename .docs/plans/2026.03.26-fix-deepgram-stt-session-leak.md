# Fix Deepgram STT Session Leak

## High-Level Goal

After a voice session ends (WebRTC disconnect or Twilio hangup), the Deepgram STT service's websocket connection handler and keepalive tasks survive the pipeline shutdown and run indefinitely. They enter an infinite reconnect loop (keepalive fails -> 1011 timeout error -> reconnect -> repeat), accumulating zombie connections across sessions. Fix this by explicitly cancelling the STT service's dangling asyncio tasks after the pipeline runner returns.

## Root Cause

When `task.cancel()` propagates a `CancelFrame` through the pipeline, pipecat's `DeepgramSTTService.cancel()` calls `_disconnect()`, which calls `cancel_task(self._connection_task, timeout=1.0)`. If the Deepgram websocket close handshake takes longer than 1 second, the cancellation times out (logged as a warning) and the `_connection_handler` task survives. Since `_connection_handler` runs a `while True` reconnect loop, it re-enters the loop and reconnects forever.

Pipecat's `_print_dangling_tasks()` detects and logs these zombie tasks ("Dangling tasks detected") but does not force-kill them.

## Important Technical Notes

### Why we cannot fix this inside pipecat

The 1-second timeout in `cancel_task` is hardcoded in pipecat's `FrameProcessor`. The Deepgram SDK's websocket close handshake can exceed this, especially under network latency. We do not control pipecat internals, so we clean up from our side.

### Force-cancelling via the STT task manager

Each pipecat `FrameProcessor` (including `DeepgramSTTService`) has a `_task_manager` attribute (a `TaskManager` instance) that tracks all asyncio tasks created by `self.create_task()`. After `runner.run(task)` returns, we can call `task_manager.current_tasks()` to get any surviving tasks and cancel them directly.

The STT's `_connection_handler` and `keepalive` tasks are created via `self.create_task()`, so they appear in `current_tasks()`. Cancel them by calling `.cancel()` directly on the raw `asyncio.Task` objects, then `await asyncio.gather(*tasks, return_exceptions=True)` with a 5-second `asyncio.wait_for` wrapper. Do NOT use pipecat's `cancel_task` method -- that is what caused the problem in the first place (1-second timeout too short).

Capture `current_tasks()` into a local list before cancelling -- tasks are removed from the manager's internal dict as they finish (`_task_done_handler`), so a second call would return fewer/no tasks.

If the 5-second gather times out (`asyncio.TimeoutError`), log a warning and continue -- do not retry. The zombie tasks will be garbage collected when the event loop ends.

### Accessing `_task_manager` (private attribute)

The `_task_manager` attribute is private to pipecat's `FrameProcessor`. Access it as `stt._task_manager` (not `stt.task_manager` which is a property that raises if `None`). Check `stt._task_manager is not None` before calling `current_tasks()`. If it is `None` after a normal pipeline run, log a warning -- this would indicate pipecat changed the attribute name.

### TTS does not have this issue

The `TrackedDeepgramTTSService` (Deepgram TTS) does NOT have a `while True` reconnect loop -- it uses a single receive task. Only the STT service is affected.

### Accessing the STT instance

Currently `create_pipeline()` returns only a `PipelineTask`. We add a `PipelineResult` dataclass that bundles the task with the STT service reference, so the server can access it for cleanup.

### Both transport paths need the fix

Both `_webrtc_bot()` and `twilio_stream_ws()` have the same `try: runner.run(task) finally: cleanup` pattern. Both need the STT cleanup in the `finally` block.

### Phase 2: STT cleanup function
3. Add `cancel_stt_tasks()` to `server.py` that iterates `stt._task_manager.current_tasks()` and cancels each surviving task

4. Update `_setup_pipeline_session` to unpack `PipelineResult` and pass `stt` through the return tuple
5. Update `_webrtc_bot` `finally` block to call `cancel_stt_tasks(stt)` before `_cleanup_session`
6. Update `twilio_stream_ws` `finally` block to call `cancel_stt_tasks(stt)` before `_cleanup_session`

## Success Criteria

- After a WebRTC session ends, no Deepgram STT tasks continue running (no keepalive/reconnect loop in logs)
- After a Twilio session ends, same behavior
- Multiple sequential sessions do not accumulate zombie STT connections
- If the STT service was never started (pipeline setup failure), `cancel_stt_tasks` does not raise
- Normal session cleanup (IMAP close, cost tracking, Langfuse, recording upload) is unaffected
- All existing tests pass
- New tests pass
