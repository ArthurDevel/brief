# Short-Lived Session Review Links

## Goal

Allow a user who receives a session recap email to review and approve/reject pending actions for that session for the first hour without signing in.

If the user is already authenticated, they should be sent to the normal session dashboard. If they are not authenticated, they should see a minimal token-backed review page scoped to only that one session.

Email links must not execute actions directly. They should open the minimal review page, and mutations should happen only after the user clicks buttons on that page.

## Context

Current behavior:

- Session recap emails are generated after the end-of-session API runs.
- Email buttons link to the authenticated dashboard session page with query params like `?action=approve&actionId=...`.
- Middleware redirects unauthenticated users away from `/dashboard/*` to `/login`.
- The dashboard page reads the email query params and calls the authenticated action APIs.

Desired behavior:

- Recap emails contain one short-lived session review token.
- The token opens a minimal review page for that session for one hour.
- The token authorizes only `approve` and `reject` actions for pending actions in that session.
- Expired, missing, revoked, or invalid tokens should redirect to authentication.
- Authenticated owners should use the normal dashboard instead of the minimal page.

## Tradeoffs And Technical Implications

### Recommended Design

Use one short-lived session review token per recap email. The token opens a minimal review page instead of executing actions directly.

This gives better UX than per-action tokens because the user can review all pending actions in one place. It is safer than making the normal dashboard public because the temporary surface can be narrowly scoped.

### Why Email Links Should Not Execute Actions Directly

Email clients, link scanners, corporate gateways, and preview tools can open links automatically. If an approve/reject link performs a mutation on `GET`, those systems could accidentally approve or reject actions before the user sees the email.

Therefore:

- Email links should only open a review page.
- The review page should use `POST` requests for approve/reject.
- Server routes must still validate the token on every request.

### Bearer Token Risk

The token is a temporary bearer credential. Anyone with the recap email link can open the minimal review page and approve/reject pending actions for that one session until the token expires.

Mitigations:

- One-hour expiry.
- Long random token.
- Store only a SHA-256 hash of the token in the database.
- Scope token to exactly one `user_id` and one `session_id`.
- Do not accept action IDs outside the token session.
- Allow only `approve` and `reject`.
- Do not expose full dashboard navigation.
- Do not expose settings, account details, transcript, full email bodies, undo, or draft conversion.
- Log token usage with `last_used_at`.
- Optionally add audit events later if needed.

### Single-Use Versus Session-Use

Do not make the token single-use on page open. The user may need to approve/reject several actions from the minimal review page.

Instead:

- Keep token valid until `expires_at` or `revoked_at`.
- Revalidate it on each page/API request.
- Only pending actions can be mutated.

### Authenticated User Behavior

If the user is authenticated and owns the token's session, redirect to the normal dashboard:

```text
/dashboard/sessions/:sessionId
```

This keeps the minimal page only for unauthenticated review.

If an authenticated user does not own the session, treat the token as invalid for that user and redirect to login or return unauthorized, depending on the route.

## Data Model

Add a table similar to:

```sql
create table session_review_tokens (
  id uuid primary key default uuid_generate_v4(),
  user_id uuid not null references auth.users(id) on delete cascade,
  session_id uuid not null references sessions(id) on delete cascade,
  token_hash text not null unique,
  expires_at timestamptz not null,
  revoked_at timestamptz,
  last_used_at timestamptz,
  created_at timestamptz not null default now()
);
```

Suggested indexes:

```sql
create index idx_session_review_tokens_session_id on session_review_tokens(session_id);
create index idx_session_review_tokens_user_session on session_review_tokens(user_id, session_id);
create index idx_session_review_tokens_expires_at on session_review_tokens(expires_at);
```

RLS:

- Enable RLS if consistent with project policy.
- Do not add user-accessible policies.
- Access should happen through service-role server code only.

## Token Contract

Raw token:

- Generated with Node crypto.
- At least 32 random bytes.
- Encoded as URL-safe base64 or hex.

Stored token:

- Store `sha256(rawToken)`.
- Never store the raw token.

Validation should return:

```ts
interface SessionReviewTokenContext {
  tokenId: string;
  userId: string;
  sessionId: string;
  expiresAt: string;
}
```

Invalid when:

- Token missing.
- Token hash not found.
- `expires_at <= now`.
- `revoked_at is not null`.

## Minimal Review Page Scope

The minimal page should show:

- Session date/time or simple session heading.
- Counts for total and pending visible actions.
- Pending and completed action table.
- Tool label.
- From/to.
- Subject.
- Status.
- Approve/reject controls for pending actions.
- Bulk approve/reject controls for pending actions.

The minimal page should not show:

- Full transcript.
- Full email bodies.
- Settings.
- Account details.
- Navigation to the rest of the app.
- Undo.
- Convert-to-draft.
- Arbitrary action endpoints.

## API Design

### Load Review Data

```text
GET /api/session-review?token=...
```

Returns a DTO with minimal data:

```ts
interface SessionReviewResponse {
  sessionId: string;
  startedAt: string;
  endedAt: string | null;
  durationSeconds: number | null;
  actions: SessionReviewAction[];
}

interface SessionReviewAction {
  id: string;
  toolName: string;
  label: string;
  contact: string;
  subject: string;
  status: string;
  createdAt: string;
}
```

Rules:

- Validate token with service role.
- Load only the token session.
- Load only actions for `token.user_id` and `token.session_id`.
- Filter out read-only actions, matching the dashboard behavior.
- Do not return `arguments` wholesale.
- Update `last_used_at`.

### Mutate Actions

```text
POST /api/session-review/actions
```

Body:

```ts
interface SessionReviewActionRequest {
  token: string;
  operation: "approve" | "reject";
  actionIds: string[];
}
```

Rules:

- Validate token with service role.
- Validate non-empty string `actionIds`.
- Load all requested actions.
- Reject the request if any requested action does not belong to `token.user_id` and `token.session_id`.
- Only mutate `pending` actions.
- For `reject`, update status to `rejected`.
- For `approve`, load the active email account and use existing action execution logic.
- Return a bulk-style result with succeeded, failed, skipped, and per-action statuses.

- `rg` is not installed in this workspace shell; use `grep`/`find` or install/use an available alternative when searching.
- Current recap email links are dashboard links, not direct mutation links.
- Current dashboard page processes email query params client-side after authentication.
- Existing authenticated approve/reject/bulk endpoints require Supabase auth cookies.
- Existing middleware allows `/api/sessions/:id/end-of-session` publicly through a regex because it is protected by `INTERNAL_API_KEY` inside the route.
- `executeAction` and `bulkExecuteActions` in `packages/tools/src/action-queue.ts` are the right execution primitives to reuse for token-scoped approval.
- Token route APIs now reject requests from an authenticated user whose user ID differs from the token user ID. Unauthenticated requests can use the bearer token as intended.
- Route-level session-review API tests were not added in this pass; helper tests, TypeScript compile, and the full unit suite were run instead.
