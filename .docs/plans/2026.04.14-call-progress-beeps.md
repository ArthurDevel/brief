# Call Progress Beeps

## Goal

Add short "phone beep" progress audio during call startup silence.

Behavior:
- Twilio calls: start the beep as early as possible after the Twilio stream is ready.
- Web calls: start the beep as early as possible while `/call` is connecting.
- Stop the beep on the first actual assistant audio.
- "Assistant audio" includes both normal reply TTS and tool narrations.
- Do not stop the beep just because inbound user speech begins.

## Current Findings

- Recent Twilio log timing shows the earliest practical pre-pipeline beep point is after Twilio stream metadata is parsed, because that is when `streamSid` is available.
- In Twilio, a beep that starts only after Pipecat `StartFrame` is too late for the silence we care about.
- In web calling, a server-side beep also starts too late for the earliest silence window. The clean approach is browser-local audio.
- The correct stop condition is not "LLM started" and not "TTS requested". It is the first real assistant audio packet.
- Tool narrations already flow as assistant audio via `TTSAudioRawFrame` in the voice pipeline, so stopping on first outbound assistant audio naturally covers narrations too.
- The current prototype startup-tone processor is not the right solution for the earliest silence window; keep findings from it but do not treat it as the final design.

## Tradeoffs And Technical Implications

### Twilio

- Best implementation is outside the Pipecat pipeline, directly on the Twilio websocket.
- This lets the beep start before pipeline boot and before LLM/TTS work begins.
- It requires direct Twilio media-event emission and one clear handoff to real assistant audio.
- The beep cannot start before `streamSid` exists.
- If desired behavior is "stop only when assistant speaks", the beep may continue while voicemail or the callee is speaking. That is a product choice and may sound odd, but it matches the requested behavior.

### Web

- Best implementation is in the browser on `/call`, not in the voice pipeline.
- This covers pre-WebRTC / pre-pipeline silence that the server cannot fill.
- The stop condition should be first remote assistant audio energy, not just peer connection state.
- Browser-local beep behavior will not automatically apply to non-browser call paths, which is fine because Twilio has its own implementation.

### Shared Product Semantics

- Start the beep as early as the channel allows.
- Stop on first actual assistant audio.
- Assistant audio includes:
  - greeting TTS
  - normal response TTS
  - tool narration audio
- Final Twilio stop condition: the first outbound `TTSAudioRawFrame` on the pipeline output path, intercepted immediately before `transport.output()`. On handoff, stop the direct beep task and send one Twilio `clear` before forwarding the assistant frame.
- Final web stop condition: the first sustained remote audio energy detected from the remote WebRTC media stream in the browser. Connection state alone does not stop the beep.
