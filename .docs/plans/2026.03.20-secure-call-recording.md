# Secure Call Recording for Admin Debugging

## High-Level Goal

Record call audio (both user and assistant in a single mixed file) server-side in the voice pipeline for admin debugging purposes. Recordings are stored in a private Supabase Storage bucket accessible only via the service role key (Supabase dashboard). Recording must never block or interfere with the active call -- if recording fails, the call continues normally.

## Important Technical Notes

### Two recorders -- why and where

In Pipecat, frames flow left-to-right through the pipeline chain. `InputAudioRawFrame` (user mic) enters at `transport.input()` and flows downstream. Although STT has `audio_passthrough=True` which forwards it, the user aggregator consumes it -- it does not reach the TTS/output stages. `TTSAudioRawFrame` (assistant) is created by the TTS service and flows from there onward.

Therefore a single recorder cannot capture both streams. We use two `AudioRecorder` instances:

```
transport.input() -> watchdog -> [user_recorder] -> stt -> user_agg -> llm -> tts -> speed -> [assistant_recorder] -> transport.output()
```

- **user_recorder**: captures `InputAudioRawFrame` (placed after watchdog, before STT)
- **assistant_recorder**: captures `TTSAudioRawFrame` (placed after speed processor, before transport output)

Each recorder filters for its target frame type only, pushing all frames downstream unchanged.

Note: narration audio (short phrases like "Checking your inbox") is pushed as `TTSAudioRawFrame` from the LLM handler and flows through the speed processor. The assistant_recorder will capture these too, which is correct for a debug recording.

### Audio mixing at session end

Both recorders accumulate raw PCM16 16kHz mono bytes in an `AudioBuffer`. At session end (`_cleanup_session`), `combine_wav_buffers()` merges them:
- Both buffers are the same format (PCM16 16kHz mono)
- The shorter buffer is zero-padded to match the longer one
- Samples are summed using int32 intermediate values, clipped to int16 range
- Result is written as a PCM16 mono WAV file using Python's `wave` module

This is an interleaved sum, not a time-aligned mix. For debugging purposes this is good enough -- you hear both sides of the conversation in one file.

### Memory management

For a typical call (5 minutes), raw PCM16 16kHz mono = ~9.4 MB. Even a 30-minute call is ~56 MB. This is acceptable for debug recording.

### Non-blocking guarantee

- `process_frame()`: try/except around buffer append, always pushes frame downstream
- `upload_recording()`: called after pipeline has ended (in `_cleanup_session`), uses `asyncio.to_thread()` since Supabase storage upload is blocking I/O. All exceptions logged and swallowed.
- `combine_wav_buffers()`: pure in-memory operation, called after pipeline ends. Wrapped in try/except in server.py.

### Storage path convention

Files stored as: `{session_id}.wav` in the `call-recordings` bucket.

### Server plumbing

`_setup_pipeline_session` currently returns a 5-tuple. With recorders, it must also return `user_recorder` and `assistant_recorder` (or `None` if recording is disabled). Both `_webrtc_bot` and `twilio_stream_ws` must unpack and forward these to `_cleanup_session`.

`_cleanup_session` signature must default recorders to `None`: `_cleanup_session(..., user_recorder=None, assistant_recorder=None)` so that:
- Sessions with `recording_enabled=False` pass `None`
- The lifespan shutdown path (which unpacks from `_live_pipeline_sessions` dict) can pass `info.get("user_recorder")` and `info.get("assistant_recorder")` without crashing

`_live_pipeline_sessions[session_id]` must include `"user_recorder"` and `"assistant_recorder"` keys so the lifespan shutdown can upload recordings for orphaned sessions too.

## Per-File Methods and Types/DTOs

### recorder.py (NEW)

#### Types

```python
@dataclass
AudioBuffer:
    chunks: list[bytes]     # accumulated raw PCM16 audio chunks
    sample_rate: int        # audio sample rate (Hz)
    num_channels: int       # number of audio channels (1)
```

#### Methods

| Method | Arguments | Returns | Description |
|--------|-----------|---------|-------------|
| `AudioRecorder.__init__` | `target_frame_type: type, sample_rate: int = 16000, num_channels: int = 1` | `None` | Initialize with the frame type to capture (InputAudioRawFrame or TTSAudioRawFrame) |
| `AudioRecorder.process_frame` | `frame: Frame, direction: FrameDirection` | `None` | If frame matches target type, append its audio bytes to the buffer. Always pushes frame downstream. Try/except around capture logic. |
| `AudioRecorder.get_buffer` | none | `AudioBuffer` | Return the accumulated audio buffer |
| `combine_wav_buffers` | `user_buffer: AudioBuffer, assistant_buffer: AudioBuffer` | `bytes` | Sum both PCM16 buffers into a single mono WAV file (PCM16 encoding). Zero-pads shorter buffer. Returns complete WAV bytes. |
| `upload_recording` | `session_id: str, wav_bytes: bytes, supabase: Client` | `None` | Async function. Upload WAV to Supabase Storage using `asyncio.to_thread()`. Logs and swallows all exceptions. |

## Success Criteria

- With `RECORDING_ENABLED=true`, a WAV file appears in `call-recordings` bucket after each call ends
- The WAV file contains audible audio from both user and assistant in a single mono file
- With `RECORDING_ENABLED=false` (default), no recording happens and no performance impact
- Recording failures never crash the pipeline or affect call quality
- No recording-related API endpoints exist -- admin access is Supabase dashboard only
- Only the service role key can access the recordings bucket
