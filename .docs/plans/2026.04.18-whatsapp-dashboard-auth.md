# WhatsApp Dashboard Auth

## Goal

Build a standalone auth and navigation system for `apps/web/app/whatsapp/*` that:
- lets a user open any `/whatsapp/*` page directly
- authenticates the user through a WhatsApp-delivered OTP
- signs the user into the existing Supabase account
- does not depend on the main `/login` flow or the main dashboard UX

Hard decisions for this plan:
- `/whatsapp/*` becomes its own auth island
- it may reuse the normal Supabase user/session system
- it must not rely on the current admin-only `/whatsapp` protection
- OTP delivery must happen through WhatsApp, using the normal Supabase email OTP generated server-side
- no custom fallback auth model; use Supabase-managed OTP only
- use one dedicated WhatsApp phone field and ignore `user_settings.phone.number` for this feature

Instructions for whoever executes this plan:
- After each phase, check the completed boxes in this document.
- When new findings pop up, add them to this plan before moving on.

## Target User Flow

```text
User receives WhatsApp message with CTA URL
  -> user opens /whatsapp/<page>
  -> page renders requested destination immediately
     or renders inline WhatsApp login UI on that same URL
  -> user requests login code
  -> system sends OTP through WhatsApp
  -> user enters OTP on the same /whatsapp/<page>
  -> Supabase verifies OTP and returns session
  -> page reloads/auth shell resolves
  -> user stays on the originally requested /whatsapp/<page>
```

Important UX constraint:
- There is no redirect to `/login`.
- The requested `/whatsapp/*` path is the source of truth.
- Login UI is an inline gate for the requested page, not a separate app entrypoint.

## Key Tradeoffs And Technical Implications

### `/whatsapp` must stop being admin-only

Today, `apps/web/middleware.ts` redirects unauthenticated users away from protected routes and also treats `/whatsapp` as privileged/admin-only. That has to change before any customer-facing WhatsApp dashboard can exist.

Implication:
- `/whatsapp/*` needs its own route policy instead of piggybacking on the current admin guard.

### WhatsApp UX is separate, but Supabase accounts are shared

The user wants `/whatsapp` to be operationally separate from the main dashboard UX, but it should still authenticate into the same Supabase account.

Implication:
- We can reuse Supabase users and sessions.
- We should not reuse the main dashboard’s login page, copy, or routing assumptions.

### Preferred auth model: Supabase-generated email OTP, WhatsApp-delivered

Supabase docs and the installed SDK support `auth.admin.generateLink(...)` for generating email links and raw OTPs without sending email. The implemented path is:
- resolve `whatsapp_phone -> user_id -> auth user email`
- `auth.admin.generateLink({ type: "magiclink", email })`
- use `properties.email_otp` as the login code sent through WhatsApp
- `verifyOtp({ email, token, type: "magiclink" })` to establish the session

Implication:
- Supabase still owns OTP generation and verification.
- We do not depend on Supabase phone providers or WhatsApp-capable phone auth providers.
- Delivery is handled by our own WhatsApp sender.

### Account creation can happen on first WhatsApp login

Using the normal email OTP generation path normally requires an email identity, so the implementation creates an internal synthetic email when a WhatsApp number does not already map to a user.

Implication:
- Existing users can log in through WhatsApp once `user_settings.whatsapp_phone` is linked.
- New users can be created from WhatsApp by provisioning a Supabase user with an internal synthetic email derived from the phone number.
- The dashboard still includes a dedicated save path for the WhatsApp number for existing accounts.

### Use one dedicated WhatsApp phone field

By "dedicated WhatsApp phone binding", the intent is only:
- add one new WhatsApp-specific field
- keep it separate from the existing `user_settings.phone.number`
- use only the WhatsApp field for `/whatsapp` auth decisions

Implication:
- `user_settings.phone.number` remains whatever it already means elsewhere in the product.
- `/whatsapp` auth logic reads and writes only the new WhatsApp field.

### Keep WhatsApp normalization local to the new field

Do not try to reconcile the legacy `phone.number` semantics with WhatsApp auth.

Implication:
- Pick one canonical format for the new WhatsApp field.
- Normalize only the WhatsApp auth input/output and webhook-side WhatsApp comparisons that need it.

### Shared Supabase session is acceptable

`/whatsapp` uses the normal Supabase browser cookie on purpose.

Implication:
- The route tree is separate, but the authenticated user identity is shared with the rest of the app.

## Fixed Decisions

- `/whatsapp/*` is a standalone UX and auth boundary.
- `/whatsapp/*` should be directly openable and preserve destination through auth.
- Do not route users through the main `/login` page.
- Use existing Supabase accounts.
- Allow creation of new Supabase accounts from WhatsApp by assigning an internal synthetic email identity.
- OTP must be delivered through WhatsApp.
- Add one dedicated WhatsApp phone field and ignore `user_settings.phone.number` for this flow.
- Normalize only the new WhatsApp field and WhatsApp-specific comparisons.
- Prefer Supabase-managed OTP generation/verification via `auth.admin.generateLink` + `verifyOtp`.
- Do not build a custom fallback auth model.

## Initial Findings

- `apps/web/middleware.ts` currently redirects unauthenticated users away from protected routes and explicitly treats `/whatsapp` as a privileged route. That is incompatible with a customer-facing WhatsApp dashboard.
- The old `/whatsapp` test console and its message-thread routes were removed entirely instead of being preserved under `/admin`.
- `apps/web/app/api/user/phone/route.ts` is not relevant to `/whatsapp` auth except as a warning not to overload `user_settings.phone.number` semantics.
- Supabase auth-js in the installed workspace exposes `auth.admin.generateLink(...)` with `properties.email_otp`, `properties.hashed_token`, and `properties.action_link`. That is the repo-side implementation used here.
- Supabase docs do not show a dedicated server-side API for "generate phone OTP without initiating delivery" for normal sign-in. The documented extension point is delivery replacement, not separate OTP issuance.
- Because the implemented flow uses the normal email OTP artifact, unknown WhatsApp numbers are provisioned with a deterministic internal email identity like `wa_<digits>@<domain>`.
- `apps/web/middleware.ts` now forwards the requested `/whatsapp/*` path in request headers so the server layout can render the inline auth gate without losing the destination.
- `user_settings.whatsapp_phone` is now editable from dashboard settings and is used as the public lookup key for WhatsApp login.
- Focused Vitest coverage now exists for the WhatsApp auth helpers, and `pnpm --filter @dublin/web build` completes successfully after the refactor.
