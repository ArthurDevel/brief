# WhatsApp Voice History Persistence

## Goal

Persist WhatsApp voice history in a simple and explicit way:

- interaction-agent history for voice calls should be stored in a new voice-specific table
- execution-agent history should keep using the shared execution-agent tables
- voice and text should share executor history
- voice interaction history should stay separate from text chat history

This should follow the current text WhatsApp server as closely as possible, without adding a new generic event system or mixing concerns.

## Current Agreed Design

- Add a new table: `whatsapp_voiceagent_messages`
- Use a new voice-specific store for interaction-agent history:
  - `appendVoiceInteractionAgentMessage(...)`
  - `appendVoiceInteractionAgentToolCall(...)`
  - `appendVoiceInteractionAgentToolResult(...)`
  - `listVoiceInteractionAgentMessages(...)`
- Keep execution-agent persistence shared across text and voice
- Use explicit existing/shared executor methods for execution history:
  - `findOrCreateExecutionAgentThread(...)`
  - `appendExecutionAgentMessage(...)`
  - `appendExecutionAgentToolCall(...)`
  - `appendExecutionAgentToolResult(...)`
  - `listExecutionAgentMessages(...)`

## Tradeoffs And Technical Implications

- Voice interaction history should not reuse `whatsapp_messages`
  - text is one long continuous conversation
  - voice is one call/session-scoped conversation
- Execution-agent history should stay shared
  - the same executor history should be reusable by both text and voice
- Keep the design explicit
  - no generic event bus
  - no generic callback abstraction unless needed
  - no new generic session-log system
- Keep writes simple
  - write to DB
  - then update in-memory history
  - this is acceptable even though a crash between those two steps could create a short-lived mismatch
- `sessions.transcript` should not be treated as the source of truth for OpenPoke tool persistence
  - voice interaction history and execution history should be stored explicitly through the app stores

## Expected Data Model

Suggested `whatsapp_voiceagent_messages` fields:

- `id`
- `session_id`
- `user_id`
- `agent` with values like `interaction` or `executor` only if needed
- `type` with values `message`, `tool_call`, `tool_result`
- `role` with values `user`, `assistant`, `tool`
- `text`
- `tool_name`
- `tool_call_id`
- `tool_arguments`
- `tool_result`
- `created_at`

Note:

- Keep this simple. If `agent` is unnecessary because this table is only for voice interaction-agent history, remove it.
- Execution history should continue using the shared executor tables instead of this new voice interaction table.

## Read/Write Lifecycle

Voice interaction agent:

- At call start, load recent interaction history for the current `session_id` from `whatsapp_voiceagent_messages`
- Keep that history in memory during the active call
- On each new user utterance:
  - write to DB
  - then append to in-memory interaction history
- On each actually spoken assistant interaction reply:
  - write to DB
  - then append to in-memory interaction history
- On each interaction tool call/result:
  - write to DB
  - then append to in-memory interaction history

Execution agent:

- At the start of every execution run:
  - find or create the shared execution-agent thread
  - load recent execution-agent messages from DB
- During the run:
  - append tool calls/results and any needed assistant/user messages to the shared executor tables
  - also append the same data to the local in-memory execution message array

## Findings So Far

- The active voice OpenPoke flow currently keeps interaction history in memory in `liveKitAgent.ts`
- The active voice OpenPoke executor currently keeps execution history in memory only
- The text WhatsApp server stores interaction history in `whatsapp_messages`
- The text WhatsApp server stores execution history in `execution_agent_threads` and `execution_agent_messages`
- The voice runtime should follow that same separation:
  - voice interaction history gets its own voice-specific table
  - shared executor history remains shared across text and voice
- The implemented voice interaction store loads persisted interaction messages at call start, but a new call/session will normally start with an empty interaction history
- The implemented voice interaction store is optional when `sessions.id` creation fails, so existing call startup behavior is preserved
