# WhatsApp Text Execution Agent Plan

## Goal

Add the execution-agent layer to the WhatsApp text flow in `apps/whatsapp-server` so the text agent can move from direct replies to OpenPoke-style orchestration:

- the interaction agent decides when to reply, wait, draft, or delegate
- the execution agent performs tasks and reports back
- WhatsApp text keeps auth commands as a fast path
- unsupported actions fail clearly instead of pretending to work

This plan is written so a new agent can continue the work without prior context.

## Current State

- WhatsApp text exists and is working as an interaction-agent-only flow.
- The current text agent uses a single direct OpenRouter reply with no tool loop.
- The WhatsApp text interaction model is hardcoded to `google/gemini-3-flash-preview` to match OpenPoke's interaction agent.
- `packages/whatsapp-core` now exists for shared WhatsApp storage and normalization logic.
- The emulator now signs forwarded webhook payloads with `META_APP_SECRET`.
- The remote DB needed `029_recreate_whatsapp_messages.sql` because `024_whatsapp_auth.sql` had dropped the table created in `023_whatsapp_messages.sql`.

## Findings To Preserve

- `024_whatsapp_auth.sql` drops `whatsapp_messages`. Any new agent must know that `029_recreate_whatsapp_messages.sql` is required for the current text flow.
- The current WhatsApp text prompt is intentionally narrower than OpenPoke because there is no execution-agent or tool loop yet.
- `packages/whatsapp-core` is the intended place for more shared voice/text logic, but only the minimal storage and phone helpers have been moved so far.
- `/api/chat/history` is not called by the current repo code. Previous 404s seen in the browser were not caused by the current workspace files.
- The WhatsApp text execution runtime now depends on `COMPOSIO_API_KEY` inside `apps/whatsapp-server`.
- The text execution runtime creates a synchronous Composio session per turn and includes WhatsApp auth-template custom tools in that session.

## Tradeoffs And Technical Implications

- We should keep auth commands as a fast path for now.
  - This avoids blocking the existing WhatsApp connector flow while the execution-agent work is still incomplete.

- Text and voice should not share the same system prompt.
  - Shared runtime helpers can live in `packages/whatsapp-core`.
  - Prompt content must stay channel-specific.

- We should not copy OpenPoke's interaction prompt verbatim until the supported tool surface exists.
  - If we tell the model it can call tools that do not exist, it will hallucinate capability.

- We should keep the first execution-agent version simple.
  - Prefer a small supported tool surface and clear errors over broad partial support.

- We should not add new tables unless they are necessary.
  - `whatsapp_messages` is the current conversation log.
  - If future execution state needs durable tracking beyond message history, we should justify that separately.

- Execution can be synchronous first.
  - This is simpler for the first pass.
  - Async/background follow-ups can be added later if a task truly needs it.
