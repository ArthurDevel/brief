# Shared User Settings Defaults

## Goal

Move user-settings defaults to one language-neutral source of truth so the web app and voice pipeline stop drifting when a user has no `user_settings` row or when a specific settings field is missing.

This plan only covers shared defaults for the existing user settings surface. It does not include contact sync changes, newsletter config changes, or Exist Helper work.

## Context

Current behavior is inconsistent across surfaces:

- The web settings API returns `voicePreference = "aura-2-helena-en"` and `voiceSpeed = 1.0` when a row or field is missing.
- The voice pipeline falls back to `voice_preference = "aura-2-andromeda-en"` and `voice_speed = 1.2` when a row or field is missing.
- The web `GeneralTab` initializes local state with `DEFAULT_VOICE = "aura-2-andromeda-en"` and `DEFAULT_SPEED = 1.2` before the settings API response arrives.

We want one source of truth for the default settings data, with small per-language adapters on top of it.

## Constants To Centralize

These are the settings defaults that should come from the shared file instead of being redefined per runtime:

- `voice_config.voice`
  - Current web API default: `"aura-2-helena-en"`
  - Current voice pipeline default: `"aura-2-andromeda-en"`
  - Current `GeneralTab` local default: `"aura-2-andromeda-en"`
- `voice_config.speed`
  - Current web API default: `1.0`
  - Current voice pipeline default: `1.2`
  - Current `GeneralTab` local default: `1.2`
- `tool_approval_config`
  - Current default everywhere: `{}`
- `phone`
  - Current default everywhere: `null`
- `call_schedule`
  - Current default everywhere: `null`

These fields should stay derived at the adapter layer rather than being primary values in the shared file:

- `emailAccount`
  - Runtime response decoration in the web API, not a stored default.
- `hasPin`
  - Derived from `pin_hash`, but the no-row web response should still map it to `false`.
- `memory_entries`
  - Voice pipeline runtime data, not part of persisted `user_settings` defaults.
- `timezone`
  - Derived from `call_schedule.timezone` or `phone.countryCode`, not a fixed settings default.

## Recommended Shared File Shape

Use DB/domain naming in the shared file so both runtimes map from the same schema:

```json
{
  "voice_config": {
    "voice": "aura-2-andromeda-en",
    "speed": 0
  },
  "tool_approval_config": {},
  "phone": null,
  "call_schedule": null
}
```

Notes:

- Do not include `emailAccount`, `hasPin`, `memory_entries`, or `timezone` in the JSON.
- Keep the JSON limited to persisted or directly persisted-shaped settings data.
- Each runtime should map from this domain shape into its own DTO shape.

## Tradeoffs And Technical Implications

### Why JSON Instead Of Shared TS Or Shared Python Code

The web app and voice pipeline run in different languages, so a normal code module cannot be imported by both.

JSON gives us:

- One source of truth in the repo.
- Easy loading from both TypeScript and Python.
- Small adapters per runtime for typing and runtime shape conversion.

### Why Use Domain Naming In The Shared File

The persisted settings data already uses names like `voice_config`, `tool_approval_config`, and `call_schedule`.

Using that shape in JSON avoids:

- Maintaining one schema for TypeScript DTO names and another for Python/DB names.
- Re-encoding the same defaults multiple times.

Adapters can then map:

- JSON domain shape -> web `UserSettings`
- JSON domain shape -> voice `UserContext`

### Client-Side Consumption Constraint

`GeneralTab.tsx` is a client component, so it should not read files with `fs`.

Implementation implication:

- The TypeScript adapter should import the JSON at build time and export plain constants/helpers usable by both server and client code.
- The Python adapter should read the JSON from disk once and expose helper functions or module-level constants.

### Avoid Over-Centralizing Derived Values

Not every returned field should live in the shared JSON.

Specifically:

- `hasPin` should remain derived from `pin_hash`.
- `emailAccount` should remain injected by the web settings API.
- `timezone` should remain derived from schedule or phone.

If we put derived values into the JSON, we risk hiding where they really come from.
