# Plan: list_folders and move_to_folder tools + email_provider tracking

## High-level Goal

Add two new agent tools (`list_folders`, `move_to_folder`) that allow the voice agent to list available IMAP folders and move emails between them. Additionally, derive the user's email provider type (`gmail`, `outlook`, `custom`) from the IMAP host so the system prompt can include provider-aware hints (e.g., "on Gmail, moving to a folder acts as labeling").

## Important Technical Notes

### Email provider derivation

The provider type is derived from the IMAP host at session load time (not stored in DB). This mirrors the frontend's `detectProvider()` logic in `EmailTab.tsx`:
- `imap.gmail.com` -> `"gmail"`
- `outlook.office365.com` -> `"outlook"`
- anything else -> `"custom"`

This avoids a DB migration and stays consistent with the frontend. The `EmailProvider` type only exists in Python (`session.py`) since the TS side does not consume it.

### Gmail labeling hint in system prompt

When the provider is `"gmail"`, the system prompt should include a short note:
> "This user has a Gmail account. Moving an email to a folder is equivalent to applying a Gmail label -- the email will also remain in All Mail."

This helps the model understand the semantics and communicate accurately to the user. For Outlook/custom, no extra hint is needed since folder-move behavior is intuitive.

### Gmail hint in tool description

The `move_to_folder` tool description should include: "Moves an email to a specified folder. On Gmail, this is equivalent to applying a label." This is brief and model-facing.

### Folder listing: filtering non-selectable folders

`list_folders` should return all user-visible folders but exclude:
- `INBOX` (the user is already there)
- Folders with the `\Noselect` flag (e.g., the `[Gmail]` or `[Google Mail]` parent container)

Implementation details per library:
- **ImapFlow (TS)**: `client.list()` returns mailbox objects. Check `mailbox.flags` set for `\\Noselect`.
- **imapclient (Python)**: `client.list_folders()` returns tuples of `(flags, delimiter, name)`. Check if `b'\\Noselect'` is in the flags tuple.

Special-use folders (Trash, Sent, Drafts, All Mail) should be included since a user might want to move emails there.

### Undo recipe key consistency (TS vs Python)

There is an existing inconsistency in the undo recipe `params` between TS and Python:
- **TS** (`action-queue.ts` line 632-638): uses `messageId` key, and `moveEmail()` in `imap-client.ts` looks up by Message-ID header
- **Python** (`handlers.py` line 674-684): uses `email_id` key, and `move_email()` in `email_client.py` uses the UID directly

For `move_to_folder`, follow the same pattern in each language:
- **TS**: store `messageId` in undo recipe params (consistent with existing archive/delete undo)
- **Python**: store `email_id` in undo recipe params (consistent with existing archive/delete undo)

This inconsistency is pre-existing and out of scope to fix here. No new undo handler code is required -- both languages already handle `"move_email"` recipes.

### TS dispatchTool return type

The TS `dispatchTool()` returns `{ result, undoRecipe }` (2 fields). It does NOT return `message_id` -- that is a Python-only pattern used for DB enrichment. The `move_to_folder` case in TS should follow the same 2-field return as `archive_email`.

### TS lazy imports in dispatchTool

The `dispatchTool()` function in `action-queue.ts` (lines 462-465) uses lazy imports to avoid circular dependencies. The new functions `listFolders`, `moveEmailToFolder`, and `formatFolders` must be added to these existing destructured import lines.

### Python _fetch_message_id purpose in move_email_to_folder

In Python, `move_email_to_folder` calls `_fetch_message_id()` solely for the third return value (`message_id`) that `_execute_and_store` merges into `input.arguments` for DB enrichment. The undo recipe itself uses `email_id` (UID), not `messageId`.

### BASE_INSTRUCTIONS update

The `BASE_INSTRUCTIONS` string in `prompt.py` (line 29) currently says "list, read, search, draft, delete, archive, and send emails." Update this to also mention "move emails between folders and list available folders." Also update the stale "10 tools" comment in `_build_tool_behavior_section` to reflect the new total (15).

### No folder validation

If the user passes a non-existent folder name, the IMAP server will reject the `MOVE` command with a standard error. We let the IMAP error propagate -- no pre-validation of folder existence.

### Folder formatting

Following the existing pattern where every read-only tool uses a dedicated formatter (e.g., `formatEmailSummaries`, `formatEmail`), add a `formatFolders()` function to the markdown formatter in both TS and Python:
- **TS**: `packages/email/src/markdown-formatter.ts`
- **Python**: `apps/voice-pipeline/src/tools/markdown_formatter.py`

### Update fetchPendingEmailIds

`fetchPendingEmailIds` (both TS and Python) currently filters `["delete_email", "archive_email"]`. Since `move_to_folder` also removes an email from its source folder, add `"move_to_folder"` to this filter so moved emails don't show up in inbox listings when a user overrides `move_to_folder` to `mutating_queued`.

### Source folder parameter

Like `archive_email` and `delete_email`, `move_to_folder` accepts an optional `source_folder` (defaulting to `"INBOX"`). This supports future scenarios where the agent operates on emails outside INBOX.

### Tool labels

The `label` field for the new tools in `definitions.ts`:
- `list_folders` -> `"List Folders"`
- `move_to_folder` -> `"Move to Folder"`
