# Dashboard Safe Error Messages

## High-Level Goal

Stop exposing technical backend/provider/infrastructure errors in the dashboard UI. The user should only see curated human-readable messages. Raw errors should still be logged to the browser console on the client and to server logs in API routes.

Default rule:

- If an error has a defined mapping, show the mapped human-readable message.
- If an error is unknown, show `Something went wrong. Please try again.`
- Always log the original technical error with enough context for debugging.

## Important Technical Notes

### 1. Do not trust `error.message` for UI

Current dashboard code frequently does one of these:

- `setError(err instanceof Error ? err.message : "...")`
- `setError(body.error ?? "...")`
- `alert(body.error ?? "...")`
- `title={action.result?.error}`
- render `emailAccount.lastError` directly

All of those leak technical text. They must be replaced with a mapper that receives the raw error and returns a safe message.

### 2. Keep raw errors in logs

The safe-message system should not suppress debugging data.

Client-side:

- Use `console.error("[dashboard-error]", { context, error })`
- Return only the mapped message to UI state

Server-side:

- Log the original exception and relevant metadata with `console.error`
- Return a stable `code` plus safe `error`

### 3. Prefer route-level normalization for API responses

The frontend can defensively map legacy strings, but the cleaner long-term contract is:

```ts
type ErrorResponse = {
  error: string; // safe message
  code: string;  // stable machine-readable code
};
```

This lets the UI stop parsing backend/provider messages and also stabilizes test coverage.

### 4. Failed action tooltip currently leaks the worst errors

The `failed` badge tooltip currently uses `action.result.error`, which may contain:

- raw IMAP errors
- raw Unipile API responses
- folder lists
- database failures
- internal action IDs

This tooltip must render mapped safe text instead. Raw action failure text should remain available only in logs or database inspection.

### 5. Action failure data model tradeoff

There are two implementation options for failed actions:

Option A:

- Leave `result.error` as raw technical text in the database
- Map it client-side before showing badges/tooltips
- Lowest migration cost

Option B:

- Store structured error data in the database, e.g. `result: { errorCode, errorMessage, debugMessage }`
- UI uses `errorCode`
- Cleaner long-term model, but touches `packages/tools` and existing action lifecycle logic

Recommended first pass:

- Start with Option A
- Normalize UI output everywhere
- Normalize API route responses to `{ code, error }`
- Revisit structured action error storage only if support/debugging needs more consistency

### 6. Email settings have the broadest leak surface

`EmailTab` currently exposes:

- route responses from `test-connection`
- raw `Unipile getAccount failed (...)`
- raw IMAP/SMTP connection errors
- `emailAccount.lastError`

This is the highest-priority screen because it already surfaces provider-specific failures directly to users.

### 7. Call errors need browser-specific mapping

Call startup errors can originate from:

- browser microphone permission errors
- missing audio devices
- voice pipeline startup failures
- SDP negotiation failures
- usage limit conditions

The mapper should classify at least:

- permission/media-device errors
- network/transport failures
- usage limit failures
- generic call startup failures

### 8. Existing static banner copy can remain

Some messages are already user-friendly and should remain as-is:

- `No email account connected.`
- `Your email account needs to be reconnected.`
- `Your country is not yet supported.`

The work is mainly replacing dynamic/raw technical text.

## Proposed Mapping Rules

### Email patterns

- `Unauthorized`, `Not authenticated` -> `Your session expired. Please sign in again.`
- `Unipile getAccount failed`, `Unipile createHostedAuthLink failed`, `Failed to load active email account` -> `We couldn't connect to your inbox. Please check your settings.`
- `Unipile account status: reconnect_required` -> `This email account needs to be reconnected.`
- IMAP auth/socket/login errors -> `We couldn't connect to your inbox. Double-check your email address, password, and mail server settings.`
- SMTP/auth/send failures -> `We couldn't send email from this account. Double-check your outgoing mail settings.`
- `No active email account configured` -> `Connect your email account in Settings to continue.`
- missing-password validation -> `Please enter both your IMAP and SMTP passwords.`

### Call patterns

- `LIMIT_REACHED`, `usage_limit_exceeded` -> `You've reached your monthly call limit. Upgrade to keep calling.`
- browser `NotAllowedError`, permission denied, microphone access denied -> `We couldn't access your microphone. Please check your browser permissions.`
- `Failed to send SDP offer`, 5xx fetch failures, transport failures -> `We couldn't connect your call. Please check your internet connection and try again.`
- `no_phone_configured` -> `Add your phone number in Settings to receive calls.`
- `country_not_supported` -> `Calls aren't available in your country yet.`
- generic call-start failures -> `We couldn't start your call. Please try again.`

### Action patterns

- `Action not found` -> `That action is no longer available.`
- `Action is not pending`, `Action is not executed`, `cannot be executed -- status is` -> `That action has already been handled.`
- `No active email account configured` -> `Connect your email account in Settings to continue.`
- `Folder "..." does not exist` -> `That folder is no longer available.`
- `Email with UID ... not found`, `No email found with Message-ID ...`, `Message-ID header not found` -> `We couldn't find that email anymore.`
- IMAP/SMTP/Unipile move/send/reply/delete failures -> `We couldn't complete that email action. Please check your email settings and try again.`
- partial bulk failures -> `Some actions couldn't be completed. Please review them and try again.`

### Settings patterns

- phone-country mismatch -> `That phone number doesn't match the selected country.`
- invalid phone format -> `Enter a valid phone number in international format.`
- memory create/delete failures -> corresponding safe note messages
- generic settings save/load failures -> corresponding safe settings messages

### `EmailTab.tsx`

Replace all direct `err.message`, `body.error`, and `emailAccount.lastError` rendering with mapped messages. Keep raw values only in console logs.

Potential special cases:

- post-save verification result where IMAP fails but SMTP succeeds
- post-save verification result where SMTP fails but IMAP succeeds
- account badge status display using `lastError`

Recommended:

- Do not render raw `lastError`
- Either omit it entirely or map it through the email context mapper

### `CallContext.tsx`

Wrap `startCall` failure handling with `logAndMapDashboardError(err, "call")`.

Permission-specific browser errors should be recognized here if possible because this context has direct access to the thrown browser exception.

### `call/page.tsx`

Map:

- load failures from settings/company phones
- trigger-call response codes and fallback errors

Ensure `messages[data.error]` evolves into code-based mapping if the route starts returning stable codes.

### `dashboard/page.tsx`, `actions/page.tsx`, `sessions/[sessionId]/page.tsx`

Replace:

- raw `body.error`
- generic fallback strings embedded inline
- `alert(body.error ?? "...")`
- failed-action tooltip raw text

with shared mapped messages.

### API routes

Wrap route internals where raw tool/provider errors can bubble up. Return safe error payloads like:

```ts
return NextResponse.json(
  { code: "EMAIL_INBOX_CONNECT_FAILED", error: "We couldn't connect to your inbox. Please check your settings." },
  { status: 500 }
);
```

and log the raw error:

```ts
console.error("[user/settings/test-connection]", err);
```
