# Plan: Next.js Settings App + Supabase Auth

## High Level Goal

Build a Next.js web app where users authenticate via Supabase magic link, then configure their phone number and IMAP email credentials. These settings are stored in Supabase (with IMAP passwords encrypted via AES-256-GCM). The app and the Express voice server do NOT communicate directly -- they both read/write the same Supabase database independently.

Key architectural point: encryption logic lives in a `shared/` module at the monorepo root, used by both the Next.js app (encrypt before save) and the Express server (decrypt on call).

## Supabase Schema

This supersedes the schema from the server plan. The `id` references `auth.users(id)` directly.

```sql
create table users (
  id uuid primary key references auth.users(id),
  email text,
  phone_number text unique,
  display_name text,
  imap_host text,
  imap_port integer default 993,
  imap_user text,
  imap_pass text,                -- encrypted AES-256-GCM
  created_at timestamptz default now(),
  updated_at timestamptz default now()
);

alter table users enable row level security;

create policy "Users can read own row" on users for select using (auth.uid() = id);
create policy "Users can insert own row" on users for insert with check (auth.uid() = id);
create policy "Users can update own row" on users for update using (auth.uid() = id);

-- Auto-update updated_at
create or replace function update_updated_at()
returns trigger as $$ begin new.updated_at = now(); return new; end; $$ language plpgsql;

create trigger users_updated_at before update on users
for each row execute function update_updated_at();
```

Note: IMAP fields are nullable. The user row is created at first login with just `id` and `email`. IMAP fields are filled in on the settings page.

## Per-File Methods and Types

### shared/encryption.ts (NEW)

File description: AES-256-GCM encryption for IMAP passwords. Used by both the Next.js app and Express server. Reads `ENCRYPTION_KEY` env var (32-byte key, 64 hex chars). Stored format: `iv:ciphertext:authTag` (all hex-encoded).

#### Methods

| Method | Arguments | Returns | Description |
|--------|-----------|---------|-------------|
| `encrypt` | `plaintext: string` | `string` | Encrypts using AES-256-GCM with random 12-byte IV. Returns `iv:ciphertext:authTag` hex string. Throws if `ENCRYPTION_KEY` is missing. |
| `decrypt` | `encrypted: string` | `string` | Splits `iv:ciphertext:authTag`, decrypts. Returns plaintext. Throws if key missing or decryption fails. |

## Important Technical Notes

### IMAP Password Display on Settings Load

The IMAP password is stored encrypted. We cannot decrypt it client-side (the encryption key is server-only). On load:
- If `imap_pass` is non-null, the password field shows "********" and a "Change password" checkbox
- Only when checked does the field become editable
- On save, if `passwordChanged` is false, the Server Action skips updating `imap_pass`
- This is tracked via a hidden `passwordChanged` form field

### Supabase Auth Cookie Flow

Three client types from `@supabase/ssr`:
1. **Browser client** -- for Client Components (e.g., `signInWithOtp` on login page)
2. **Server client** -- for Server Components and Server Actions; reads cookies from `next/headers`
3. **Middleware client** -- refreshes session token on every request (Supabase tokens expire)

The middleware is critical. Without it, server-side auth breaks when tokens expire.

### User Row Creation Timing

The user row is created in `/auth/callback/route.ts` on first login (upsert with just `id` and `email`). This ensures:
- Row exists by the time user reaches `/settings`
- `id` matches `auth.users.id`
- IMAP fields are null until configured

### Encryption Key Shared Between App and Server

The `ENCRYPTION_KEY` env var must be identical in both processes. The `shared/encryption.ts` module ensures format compatibility. The key is 32 bytes represented as 64 hex characters.

### Express Server Changes (updates to server plan required)

The server plan needs the following updates to align with this plan:
1. **Add `ENCRYPTION_KEY` to `AppConfig`** -- the server needs it to call `decrypt()`
2. **Add `@shared/*` path alias** to `server/tsconfig.json` pointing to `../shared/`
3. **`lookupUserByPhone` must call `decrypt(row.imap_pass)`** before returning the `UserRecord`
4. **Handle snake_case -> camelCase mapping** -- Supabase returns `phone_number`, `display_name`, etc. The lookup function must map these to `phoneNumber`, `displayName`, etc.
5. **Handle nullable IMAP fields** -- if a user registered but hasn't configured IMAP, `lookupUserByPhone` should throw a descriptive error ("User has not configured email settings"). The `TwilioStreamHandler` should catch this and play a TTS message before hanging up.

The server uses the **service role key** (bypasses RLS) for phone number lookup. This is intentional -- the server reads any user's credentials by phone number, outside a user session.

## Success Criteria

1. User enters email, receives magic link, clicks it, lands on settings page authenticated
2. Unauthenticated users are redirected from `/settings` to `/login`
3. Authenticated users are redirected from `/login` to `/settings`
4. Settings form loads existing data from the `users` table
5. Phone number validation rejects non-E.164 formats
6. "Test Connection" verifies IMAP credentials before saving
7. "Save" encrypts IMAP password and upserts the row
8. IMAP password is never sent to the client in plain text
9. RLS prevents users from reading/writing other users' rows
10. Express server can decrypt IMAP passwords stored by the app using `shared/encryption.ts`
11. Session persists across page refreshes (middleware refreshes tokens)
