# WhatsApp Voice Narration Buffer Plan

Short summary: add a separate narrator flow for `apps/whatsapp-agent` that continuously generates short narration text while the execution agent is active, stores the latest sentence in a buffer, and lets the voice runtime decide when to speak that text.

- Keep the narrator separate from the interaction agent and execution agent
- Keep the narrator text-only; the voice runtime remains responsible for TTS playback
- Keep the implementation simple: one active execution, one latest narration buffer, no extra persistence

## Goal

Add lightweight voice-call narration during executor wait time without changing ownership boundaries:

- the interaction agent still owns the conversation outcome
- the execution agent still owns tool work
- the narrator continuously watches execution context and prepares one short filler sentence
- the voice runtime decides whether to speak the latest buffered narration
- if narration is already playing when execution finishes, let the short narration finish before the final interaction reply

## Decisions And Constraints

- The narrator is a separate concern from the interaction agent
- The narrator should run independently while the execution agent is active
- The narrator should continuously refresh a latest-sentence buffer instead of generating on demand
- The voice runtime should read the latest buffered sentence only when silence needs filling
- The narrator only generates text
- The voice runtime decides whether to speak the text and remains responsible for TTS playback
- The interaction agent should not gain extra narration orchestration logic beyond signaling execution start/end state
- The execution agent should not become responsible for hand-written narration events
- Keep the first version in-memory only; no database or cross-session narrator state
- Keep the first version single-execution aware; do not overengineer for parallel executor runs yet

## Current State

Today there is no narrator in `apps/whatsapp-agent`:

- the interaction agent delegates to the execution agent synchronously inside one turn
- the execution agent returns one final result to the interaction agent
- the voice runtime only speaks user-visible interaction actions
- there is no background narration loop
- there is no narration buffer
- there is no silence-driven filler speech

## Target State

The desired narration architecture:

- the voice runtime knows when delegated execution is active
- while execution is active, a narrator runtime periodically reads recent execution context
- the narrator runtime generates one short sentence and stores the latest one in a buffer
- when silence handling decides filler speech is needed, the voice runtime asks for the latest buffered sentence
- the voice runtime speaks that sentence through the existing TTS path
- when execution finishes, the narrator loop stops
- if a narration is currently playing, let it finish before the final interaction reply starts

## Tradeoffs And Technical Implications

### Separate narrator agent vs pushing narration into existing agents

Decision:

- use a separate narrator flow

Why:

- keeps the interaction agent focused on conversation outcomes
- keeps the execution agent focused on tool work
- avoids adding narration-specific output logic into either core agent

Cost:

- one extra runtime component to manage
- more moving parts inside the voice runtime

### Buffered narration vs on-demand narration

Decision:

- narrator should generate continuously while execution is active and keep the latest sentence in a buffer

Why:

- when silence needs filling, narration is already ready
- avoids waiting for a model call at the moment speech is needed
- matches the user’s desired behavior

Cost:

- narrator may generate sentences that are never spoken
- periodic model calls add some cost during longer execution windows

### Narrator sees recent executor context, not hidden internal reasoning

Decision:

- narrator should monitor recent executor context and keep continuity with its last sentence

Why:

- the user is comfortable with lightweight filler narration even if it is occasionally imperfect
- the narrator should sound continuous and context-aware

Risk:

- narration may sometimes be slightly off or generic
- prompt constraints must keep it short and avoid misleading completion claims

### Voice runtime owns speech and timing

Decision:

- narrator returns text only
- voice runtime decides whether to speak it and handles TTS playback

Why:

- current speaking path already lives in the LiveKit voice runtime
- this preserves one clear owner for queueing, timing, and playout behavior

Implication:

- narration playback rules belong in `liveKitAgent.ts`, not in the narrator implementation

### Let short narration finish before the final interaction reply

Decision:

- do not interrupt narration mid-sentence in the first version
- if execution finishes during narration playout, wait for narration to complete and then speak the final interaction reply

Why:

- simpler runtime behavior
- avoids audio interruption complexity

Implication:

- narration sentences must stay short
- the voice runtime needs a simple playout-aware gate before starting the final reply

## Findings

- The user wants the narrator to be separate from the interaction agent and execution agent
- The user wants the narrator to run independently while the execution agent is active
- The user wants the narrator to keep the latest sentence in a buffer so narration is ready before it is requested
- The narrator should only generate text
- The voice runtime should remain responsible for deciding whether to speak narration and for TTS playback
- If narration is still playing when execution finishes, the first version should let the short narration finish before the final interaction reply starts
- The user is comfortable with filler narration being occasionally imperfect as long as it is useful and simple
- The sequence diagrams for this architecture are documented in `.docs/whatsapp-voice-agent-sequence.md`
- The first implementation uses a read-only execution snapshot built from recent execution-agent text plus tool status lines
- The first implementation refreshes narration every 2 seconds and uses the same 2-second threshold before speaking buffered narration
- Narration text is intentionally not written into `conversationHistory`, so filler speech does not pollute later interaction prompts
- Focused verification completed with `pnpm --filter @dublin/whatsapp-agent build` and targeted Vitest coverage for the interaction observer path plus narration generation
