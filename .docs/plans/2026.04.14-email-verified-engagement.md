## Current Behavior

- The OTP verification itself is handled by Supabase in the lander via `supabase.auth.verifyOtp({ email, token, type: "signup" })`.
- On success, Supabase marks `auth.users.email_confirmed_at` and creates a real session cookie for the browser.
- `brief/milan-v1` already owns the transactional email system through Resend and tracks sends in `email_events`.
- Existing engagement emails are cron-driven and deduplicated by `(user_id, email_type)` in `email_events`.

## Desired Behavior

1. The user enters the OTP code in the lander.
2. Supabase verifies the OTP and creates an authenticated session.
3. The lander makes a same-origin or internal server call to `brief/milan-v1`.
4. `brief/milan-v1` verifies on the server that the request is valid and that the user is actually confirmed.
5. `brief/milan-v1` sends the new `email_verified` engagement email exactly once.
6. The send is recorded in `email_events` so retries and races do not double-send.

## Key Decisions

- The email should be triggered by a server endpoint, not by the cron-based engagement filter pipeline.
- The source of truth for eligibility is `auth.users.email_confirmed_at`, not `user_settings.updated_at`.
- The endpoint must not trust client-supplied `userId` or `email`.
- Dedup should be enforced at the database level using `email_events`.
- The lander repo should only trigger the flow after OTP success; it should not own the Resend send logic.
- Final endpoint contract: browser `POST` from the lander to `POST /api/engagement/email-verified` in `brief/milan-v1`, with no JSON body.
- Trusted auth artifact: the Supabase session cookie created immediately after `supabase.auth.verifyOtp(...)` succeeds.
- Origin policy: only `LANDER_URL` and `NEXT_PUBLIC_APP_URL` are accepted origins; onboarding-cookie fallback auth is explicitly not used.
- Success response contract:
  - `200 { success: true, status: "sent" }` when the email is newly sent
  - `200 { success: true, status: "already_sent" }` when the request is a safe duplicate
  - `401 { success: false, error: "Unauthorized" }` when no Supabase session is present
  - `409 { success: false, error: "Email is not verified yet" }` when `email_confirmed_at` is still null
  - `403 { success: false, error: "Forbidden origin" }` when the browser origin is not allowed
- Schema decision: no follow-up migration is needed right now; the existing `email_events` unique constraint plus delete-on-send-failure is sufficient for this trigger.

## Security Model

- The send endpoint must authenticate the request server-to-server or via a verified session, not via arbitrary JSON input.
- If the final design uses a browser-initiated call from the lander, the receiver must derive identity from a trusted auth artifact and re-check confirmation state on the server.
- If the final design uses an internal endpoint in `brief/milan-v1`, protect it with a shared secret such as `INTERNAL_API_KEY` and require the caller to supply only the minimum data needed.
- Always re-read the user through Supabase admin APIs before sending, and verify `email_confirmed_at` is set.
- Treat duplicate or repeated requests as success-without-send rather than as an error path.

## Dedup / Idempotency Strategy

Use a dedicated `email_type` such as `email_verified` in `email_events`.

Preferred flow:

1. Attempt to claim the send in `email_events` using the unique `(user_id, email_type)` constraint.
2. If the claim fails because the row already exists, return success without sending.
3. If the claim succeeds, send the email through Resend.
4. Persist the Resend ID on the claimed row.
5. If send fails after the claim, clean up the claim row so the trigger can be retried safely.

If implementation reveals that cleanup is too fragile, add a follow-up schema change with an explicit send status column and update this plan.

## Tradeoffs And Technical Implications

- Immediate endpoint trigger:
  Pros: sends right after verification, avoids cron delay.
  Cons: requires coordination with the lander to fire the trigger at the right time.

- Reusing `email_events`:
  Pros: existing admin UI, dedup behavior, and reporting already work.
  Cons: `email_events` currently assumes the row means "sent", so failed-after-claim sends may require deleting the row or extending the schema.

- Server-owned send logic in `brief/milan-v1`:
  Pros: one Resend implementation, one admin surface, one source of truth.
  Cons: requires a small cross-repo integration step from the lander.

- Session-based browser call from the lander:
  Pros: simple UX path after OTP success.
  Cons: the receiving endpoint must be careful not to accept weaker onboarding-cookie auth meant for pre-verification flows.

  - look up the user by trusted identity
