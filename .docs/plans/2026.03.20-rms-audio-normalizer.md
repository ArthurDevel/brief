# RMS Audio Normalizer for Voice Pipeline

## High Level Goal

The voice assistant is too quiet on both phone and web calls. Deepgram TTS outputs audio at RMS levels around -18 to -19.5 dBFS with variable peaks (-2.6 to -6.0 dBFS). The WSOLA speed processor has negligible impact on amplitude (<0.1 dB).

This plan adds an RMS-based normalizer with peak limiting as a Pipecat `FrameProcessor` in the audio pipeline. It targets a consistent RMS output of -12 dBFS while using tanh soft clipping to prevent peaks from exceeding -1 dBFS. The normalizer operates in streaming mode (chunk by chunk) with attack/release gain smoothing to avoid pumping artifacts.

The implementation is based on a validated prototype in `testscripts/2026.03.20-rms-normalizer/rms_normalizer.py`.

## Important Technical Notes

### Gain smoothing

The normalizer uses exponential moving average smoothing on the gain value across chunks. Attack (gain decrease, when signal gets louder) is fast (50ms) to prevent clipping. Release (gain increase, when signal gets quieter) is slow (200ms) to avoid pumping. The smoothing coefficient is computed per chunk based on chunk duration and the attack/release time constant:

```
coeff = exp(-chunk_duration_seconds / time_constant_seconds)
smoothed_gain = coeff * previous_gain + (1 - coeff) * desired_gain
```

### Tanh soft clipping

When the peak of the gained signal exceeds the peak limit, tanh soft clipping is applied. The signal is scaled into tanh range such that the peak limit maps to tanh(1) (~0.76), ensuring output stays below the limit while maintaining signal shape. This avoids the harsh distortion of hard clipping.

### Runtime bypass

The `AudioNormalizerProcessor` accepts a shared mutable `config` dict (same pattern as `AudioSpeedProcessor` which checks `config["speed"] != 1.0`). The normalizer checks `config.get("enabled", True)`. When disabled, frames pass through unchanged. This allows disabling the normalizer at runtime without a code deploy if it causes issues in production.

### Pipeline insertion point

The normalizer goes **after** the WSOLA speed processor and **before** the optional assistant recorder and transport output. This ensures:
1. Speed-adjusted audio gets normalized (WSOLA may slightly affect levels)
2. Recorded audio reflects what the user actually hears
3. Both WebRTC and Twilio paths benefit from the same normalization

Pipeline chain becomes:
```
transport.input -> watchdog -> [user_recorder] -> stt -> user_aggregator -> llm -> tts -> speed_processor -> normalizer -> [assistant_recorder] -> transport.output -> assistant_aggregator
```

## Phases

### Phase 1: Create normalizer module ✅
1. Create `apps/voice-pipeline/src/audio/normalizer.py`
2. Port `RMSNormalizer` from the prototype (`testscripts/2026.03.20-rms-normalizer/rms_normalizer.py`), keeping same logic
3. Add `AudioNormalizerProcessor` as a Pipecat `FrameProcessor` that wraps `RMSNormalizer` (follow the same pattern as `AudioSpeedProcessor` in `speed.py`)

## Success Criteria

- A quiet constant tone (~-18 dBFS RMS) processed through the normalizer comes out near -12 dBFS RMS
- A signal with peaks near 0 dBFS does not exceed -1 dBFS after normalization
- Silent audio is not boosted
- Streaming (small chunks) and batch (one block) produce output with RMS within 2 dB of each other
- The AudioNormalizerProcessor correctly normalizes TTSAudioRawFrame and passes other frames through unchanged
- The normalizer is positioned in the pipeline after speed_processor and before transport output
