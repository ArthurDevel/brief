# Standalone Call Page

## Goal

Move browser calling off the dashboard shell and into a dedicated standalone page at `/call`, while keeping `/dashboard/call` as the existing launcher page for phone-based calling and browser-call entry.

The intended product behavior is:

- `/dashboard/call` stays in place.
- The browser-call button on `/dashboard/call` opens a new tab to `/call`.
- `/call` becomes the real calling screen and owns all browser-call state and UI.
- The dashboard no longer needs an in-call top bar or layout-wide call persistence.

This plan does not include implementing reconnect/resume across refreshes, cross-tab sync, or server-tracked browser-call launches. The first version should be page-scoped and simple.

This is a move of the existing browser-call implementation into a dedicated route, not a greenfield rebuild. Any browser-call feature that exists today should be preserved unless we explicitly decide to remove or change it.

## Context

Current browser calling was built to survive navigation inside the dashboard:

- `apps/web/app/dashboard/call/page.tsx` renders the browser call controls and consumes a shared `CallContext`.
- `apps/web/contexts/CallContext.tsx` owns the WebRTC lifecycle and hidden `Audio` playback object.
- `apps/web/app/dashboard/layout.tsx` mounts `CallProvider` around the whole dashboard and renders `ActiveCallBar`.
- `apps/web/components/ActiveCallBar.tsx` exists only because the call can stay alive while the user navigates elsewhere in the dashboard.

That architecture is now the wrong fit. Once browser calling moves into its own tab, the call should live inside that tab only. Closing the tab should end the call. The dashboard should not know or care whether a browser call is currently active.

Also, the voice pipeline `sessionId` created by `/start` is an internal, ephemeral signaling id stored in memory on the voice server. It should not become the user-facing route shape for the new page.

## Current Browser-Call Features To Preserve

The standalone `/call` page should carry forward the existing browser-call behavior that currently exists across `dashboard/call`, `CallContext`, and the dashboard layout:

- authenticated browser-call start using the current Supabase session access token
- microphone permission request via `navigator.mediaDevices.getUserMedia({ audio: true })`
- WebRTC session setup against the existing voice-pipeline endpoints:
  - `POST /start`
  - `POST /sessions/{sessionId}/api/offer`
- TURN/STUN usage exactly as provided by the voice pipeline response from `/start`
- hidden/in-memory remote audio playback using `new Audio()` with `autoplay = true`
- call status transitions equivalent to the current implementation:
  - `Ready`
  - `Connecting...`
  - `Setting up audio...`
  - `Call active`
- safe error handling using the existing mapped dashboard error messages
- cleanup on manual end call
- cleanup on connection state failure/disconnect/close
- cleanup on component unmount / tab close
- existing auth failure handling for missing or invalid browser session

The intended removals are architectural, not behavioral:

- remove the dashboard-scoped `CallProvider`
- remove the dashboard top bar
- remove inline browser-call controls from `/dashboard/call`

Those removals should not drop the actual browser-call capabilities listed above.

## Product Shape

### `/dashboard/call`

This page remains the dashboard entry point for calling-related actions:

- phone number / QR flow
- "Call me" outbound phone flow
- browser call launcher

For browser calling, the page should no longer show an in-place start/end session UI. Instead it should present a button such as "Open call screen" or "Call from browser" that opens `/call` in a new tab.

### `/call`

This page becomes the dedicated browser call surface:

- standalone route, outside sidebar and dashboard chrome
- owns its own call lifecycle
- handles mic permission, WebRTC setup, call state, teardown, and post-call state
- designed as a focused calling screen that can grow later

Recommended first-pass screen states:

- ready / pre-call
- requesting microphone
- connecting
- in call
- ended
- error

Recommended first-pass controls:

- primary start button if not autostarting
- end call
- optional mute if trivial, otherwise defer
- lightweight "Back to dashboard" link

## Tradeoffs And Technical Implications

### Why A Standalone Page Instead Of A Dashboard-Scoped Provider

The dedicated page matches the product model more cleanly:

- the call has its own space
- the dashboard stays uncluttered
- no top bar is needed
- no hidden cross-page state is needed

It also sets up a better foundation for future call-specific UI without fighting the dashboard layout.

### Why `/call` Should Be A Real Page Route

We want a surface we can build on in the future, not a transient redirect or API endpoint.

A real page route gives us:

- stable product URL
- dedicated layout freedom
- better room for call-specific UX
- simpler ownership of WebRTC lifecycle

### Why Not Put The Voice-Pipeline `sessionId` In The URL

The current voice-pipeline session id is created by the backend signaling endpoint and stored in memory. It is not a durable product entity.

Using it in the browser URL would tightly couple frontend routing to internal signaling mechanics and make future reconnect behavior harder to reason about.

Recommendation:

- Route: `/call`
- Internal signaling: still create the voice-pipeline `sessionId` after the page loads and the user starts the call

### Popup Blocking Constraint

If `/dashboard/call` should open the standalone call page in a new tab, the tab creation must happen directly in the user click handler.

Implementation implication:

- use synchronous `window.open("/call?autostart=1", "_blank", "noopener,noreferrer")`
- do not await auth or setup work before opening the new tab

### Call Lifetime Changes

Today the call can survive navigation inside the dashboard because state lives in a provider at the dashboard layout level.

After this change:

- the call is page-scoped to `/call`
- closing the `/call` tab ends the call
- navigating around the dashboard no longer affects call state because the dashboard no longer owns it

This is consistent with the intended UX.

### Auth Model

`/call` should be an authenticated route, just like `/dashboard/*`.

The existing middleware already enforces auth for non-public routes. As long as `/call` is not added to `PUBLIC_ROUTES`, it will inherit the normal authenticated app behavior.

### Future Resume/Reconnect

This plan intentionally avoids a server-tracked browser-call launch model.

If later we want:

- refresh-safe resume
- cross-tab coordination
- rejoin by URL
- analytics around a product-level browser call launch object

then we can add an app-level `launchId` or similar. That should be a later extension, not part of the initial cleanup.

## Recommended Implementation Shape

### `apps/web/app/call/page.tsx`

Prefer a thin route file that renders a dedicated client component. That keeps the route stable while letting the UI grow later.

Recommended shape:

- `page.tsx` for route ownership
- `StandaloneCallClient.tsx` for all browser-only logic

### Standalone Call State

Do not reuse the old dashboard-wide `CallContext`.

Instead, make the `/call` page own:

- `callActive`
- `status`
- `error`
- `pipelineSessionRef`
- local cleanup on end/unmount

This is effectively the old logic from `CallContext`, moved back down to the page level where it now belongs. The goal is to preserve the current browser-call lifecycle and error behavior while changing where that logic lives.

### Autostart Behavior

Support `?autostart=1` so the dashboard launcher can open a ready-to-connect call tab.

Recommended behavior:

- open the tab immediately from the click handler
- the `/call` page loads
- if `autostart=1`, it begins the normal start flow on mount or after a brief user-visible ready state

One implementation detail to decide during build:

- whether autostart should immediately request microphone permission on load
- or whether the page should show a brief pre-call screen and require one more explicit "Start" click

Given browser permission friction, a first implementation may be more robust if the page lands on the call screen and starts automatically only when permitted, while still leaving a visible retry/start button.
