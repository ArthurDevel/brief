# Bulk Action API

## High-Level Goal

Move the bulk approve/reject loop from the frontend to a single backend API endpoint. Currently, the dashboard page (`page.tsx`) loops over pending actions and fires individual `POST /api/actions/:id/approve` requests sequentially. This means:

- Each request opens and closes its own IMAP connection
- Navigating away mid-loop causes partial execution with no feedback
- The frontend holds all orchestration state

The fix: a single `POST /api/actions/bulk` endpoint that accepts an array of action IDs and an operation (`approve` or `reject`), opens one IMAP connection, processes all actions, and returns a summary. The frontend calls this once instead of looping.

## Important Technical Notes

### Single IMAP connection for the entire bulk operation
The approve route currently opens a fresh IMAP connection per request. The bulk endpoint opens one connection and passes it to `executeAction` for each action in the loop. This is safe because ImapFlow is already sequential (one mailbox lock at a time). The connection is closed in a `finally` block after all actions complete.

### Partial failure handling
The bulk endpoint does NOT stop on first failure. It continues processing remaining actions and collects errors per action. Each failed action is independently marked as "failed" in the DB (the existing `executeAction` already handles this -- it marks the action as "failed" and then re-throws). `bulkExecuteActions` wraps each `executeAction` call in a try/catch, builds a `BulkActionResult` from either the success or the caught error, and continues to the next action.

### Status transition: pending -> executed (no intermediate "approved")
The existing single-approve route marks an action as "approved" before calling `executeAction`. However, `executeAction` already accepts both "pending" and "approved" statuses (line 126). For simplicity, `bulkExecuteActions` calls `executeAction` directly on "pending" actions without an intermediate "approved" step. This is simpler and avoids an extra DB round-trip per action. The end state is the same: "executed" or "failed".

### Ownership verification and filtering: single bulk query
The bulk route loads all action IDs in a single query: `SELECT id, user_id, status FROM actions WHERE id IN (...)`. It rejects the entire request with 403 if any action belongs to a different user (security). For non-pending actions (e.g. concurrently approved from another page), it filters them out and proceeds with the valid subset. The response includes skipped actions so the frontend knows what happened.

### Bulk reject: single DB update
The reject path does not need IMAP. It performs a single `UPDATE actions SET status = 'rejected' WHERE id IN (...) AND status = 'pending' AND user_id = ?`. The response reports how many were actually rejected. Non-pending actions are silently skipped (they are already in a terminal state).

## Per-File Methods and Types/DTOs

### types.ts (MODIFIED)

#### Types

```
BulkActionResult {
  actionId: string
  status: "executed" | "failed" | "rejected"
  error: string | null
}

BulkActionResponse {
  total: number
  succeeded: number
  failed: number
  results: BulkActionResult[]
}
```

Note: `BulkActionResult.status` will be "executed" or "failed" for the approve path, and "rejected" for the reject path. The request body shape (`{ actionIds: string[], operation: "approve" | "reject" }`) is validated inline in the route handler -- no separate DTO needed for a two-field body.

### action-queue.ts (MODIFIED)

#### Methods

| Method | Arguments | Returns | Description |
|--------|-----------|---------|-------------|
| `bulkExecuteActions` | `actionIds: string[], supabase: SupabaseClient, imapClient: ImapFlow, smtpConfig: SmtpConfig` | `BulkActionResponse` | Loops over actionIds, calls `executeAction` for each inside a try/catch. Builds `BulkActionResult` per action (success or caught error). Does not stop on failure. |

Add export for `bulkExecuteActions` from `./action-queue` and export types `BulkActionResult`, `BulkActionResponse` from `./types`.

## Success Criteria

- `POST /api/actions/bulk` with `{ actionIds: [...], operation: "approve" }` executes all actions using a single IMAP connection and returns a summary
- `POST /api/actions/bulk` with `{ actionIds: [...], operation: "reject" }` rejects all actions in a single DB call
- Partial failures do not block remaining actions
- The frontend "Approve All" / "Reject All" buttons call the bulk endpoint once instead of looping
- Navigating away mid-operation is safe: the server completes the full batch regardless
- All existing tests pass unchanged
- New integration tests pass for bulk execute (success, partial failure, already-executed, empty array)
