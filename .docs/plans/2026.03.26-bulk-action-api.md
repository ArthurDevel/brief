# Bulk Action API

## High-Level Goal

Move the bulk approve/reject loop from the frontend to a single backend API endpoint. Currently, the dashboard pages loop over pending actions and fire individual `POST /api/actions/:id/approve` requests sequentially. This means:

- Each request opens and closes its own IMAP connection
- Each email operation acquires and releases its own mailbox lock
- Navigating away mid-loop causes partial execution with no feedback
- The frontend holds all orchestration state

The fix: a single `POST /api/actions/bulk` endpoint that accepts an array of action IDs and an operation (`approve` or `reject`). For approve: opens one IMAP connection, groups actions by (tool_name, source_folder), acquires the mailbox lock once per group, and executes all IMAP operations under that lock (following the same batched pattern as `fetchEmailMetaBatch`). The frontend calls this once instead of looping.

No changes to the email package. The batched lock logic lives entirely in `bulkExecuteActions` in `action-queue.ts`, which directly uses `imapClient.getMailboxLock`, `imapClient.fetchOne`, `imapClient.messageMove`, and the already-exported `resolveSpecialUseFolder`.

## Important Technical Notes

### Batched IMAP operations under a single lock (following fetchEmailMetaBatch pattern)

`bulkExecuteActions` directly uses the ImapFlow client to batch operations. It does NOT call `executeAction` in a loop (that would go through `dispatchTool` -> `deleteEmail`/`archiveEmail`, each of which acquires its own lock). Instead:

1. Load all actions in a single DB query
2. Validate statuses -- skip non-pending actions (include them in results as "skipped")
3. Resolve each unique target folder once before the group loop (cache: `delete_email` -> Trash path, `archive_email` -> All Mail path). If folder resolution fails, mark the entire group as failed.
4. Group email-move actions by `(tool_name, source_folder)` -- each action's `arguments` already contains `email_id` and `source_folder`
5. Per group:
   - Acquire the mailbox lock once via `imapClient.getMailboxLock(sourceFolder)`
   - For each action in the group: `imapClient.fetchOne(uid, { envelope: true }, { uid: true })` to get Message-ID, then `imapClient.messageMove(uid, targetFolder, { uid: true })`
   - Individual failures are captured per action (not thrown), so one bad email does not abort the batch
   - Release the lock in a `finally` block
6. Build undo recipes from results (same `move_email` format as `archiveEmail`/`deleteEmail`)
7. Update all action rows in DB: successful ones get `status: "executed"` + undo recipe, failed ones get `status: "failed"` + error

### Non-move actions fall back to individual execution

Any tool_name that is not `delete_email` or `archive_email` falls back to calling `executeAction` individually. This covers `send_email` (SMTP), `draft_email` (IMAP append, not a move), `save_memory`, and `submit_feature_request`. In practice, bulk approve is mostly delete/archive actions.

### Tool name to target folder mapping

Resolved once before the group loop and cached:
- `delete_email` -> `resolveSpecialUseFolder(client, "\\Trash")`
- `archive_email` -> `resolveSpecialUseFolder(client, "\\All")`

### Status transition: pending -> executed (no intermediate "approved")

The existing individual approve flow sets `status: "approved"` before calling `executeAction`. In the bulk path, we skip this intermediate step -- actions go directly from "pending" to "executed" or "failed". The "approved" state was only useful as a signal that execution was attempted; in the bulk path, the entire batch is atomic from the frontend's perspective.

### Bulk reject: single DB update

The reject path does not need IMAP. The API route performs a single `UPDATE actions SET status = 'rejected' WHERE id IN (...) AND status = 'pending' AND user_id = ?`. No need for `bulkExecuteActions`. The response reports how many were rejected; non-pending actions are silently skipped.

### Ownership verification

The bulk route loads all action IDs in a single query. If any action belongs to a different user, return 403 for the entire request. This is a security boundary -- a legitimate client will never send action IDs belonging to another user. Stale/invalid IDs that don't exist are simply filtered out.

### Input validation

The API route validates:
- `actionIds` is an array of strings
- `operation` is `"approve"` or `"reject"`

## Success Criteria

- `POST /api/actions/bulk` with `{ actionIds: [...], operation: "approve" }` executes all actions using a single IMAP connection with batched lock acquisition per (tool_name, source_folder) group
- `POST /api/actions/bulk` with `{ actionIds: [...], operation: "reject" }` rejects all actions in a single DB call
- Partial failures do not block remaining actions
- The frontend "Approve All" / "Reject All" buttons call the bulk endpoint once instead of looping (both dashboard pages)
- Navigating away mid-operation is safe: the server completes the full batch regardless
- All existing tests pass unchanged
- New integration tests pass for bulk execute (success, partial failure, already-executed, empty array, mixed tools, mixed folders)
