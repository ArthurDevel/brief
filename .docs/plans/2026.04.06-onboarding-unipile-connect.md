# Plan: Onboarding Unipile Connect

## High-Level Goal

Replace the app-password IMAP/SMTP email setup in the brief-lander onboarding flow with Unipile hosted-auth (OAuth) for Gmail and Outlook. After this change, onboarding users connect their inbox by clicking "Connect with Gmail" or "Connect with Outlook", completing an OAuth flow via Unipile, and returning to the onboarding page to continue.

The custom IMAP/SMTP form is removed from onboarding entirely. Custom accounts are only available from the main app's settings page.

The existing Unipile `notify_url` handler in amsterdam handles the DB write to `user_email_accounts`. The brief-lander only needs to generate the hosted-auth link and detect when the connection is complete.

## Tests

No test infrastructure exists in brief-lander today (no vitest/jest config, no test files). The routes are thin wrappers around Unipile API calls and Supabase queries. Given the cost of setting up a test harness for this small change, we skip automated tests and rely on manual E2E verification:

- Register a new user, verify the INBOX step shows "Connect with Gmail" and "Connect with Outlook" buttons (no app-password form).
- Click "Connect with Gmail", complete the Unipile OAuth flow, verify redirect returns to `/onboarding` and the flow advances to the SCHEDULE step.
- Click "Connect with Outlook", complete the Unipile OAuth flow, verify redirect returns to `/onboarding` and the flow advances to the SCHEDULE step.
- Close the browser mid-OAuth, reopen `/onboarding`, verify the progress check correctly resumes at INBOX (no false positive from partial state).
- After redirect, verify that if the notify callback is delayed beyond 30 seconds, the UI shows a timeout message with a "Try again" button that returns to the connect buttons.

## Important Technical Notes

### Auth During Onboarding

The brief-lander supports two auth modes: Supabase session (confirmed email) and HMAC onboarding cookie (unconfirmed email). Both the new `connect` and `status` routes must use `resolveUserId()` to support either mode. The Unipile `notify_url` callback goes to amsterdam, which uses its own service-role client and HMAC verification -- no lander auth needed there.

### Notify URL Points to Amsterdam

The notify callback URL in the hosted-auth link is always `${NEXT_PUBLIC_APP_URL}/api/user/email-accounts/notify` (amsterdam). This is the same handler used when connecting from the settings page. The lander does not have its own notify handler.

### Success Redirect URL Back to Lander

The `success_redirect_url` in the hosted-auth link points back to the lander: `${NEXT_PUBLIC_LANDER_URL}/onboarding?inbox=connected`. This tells Unipile where to redirect the user's browser after OAuth completes. The lander's `NEXT_PUBLIC_LANDER_URL` is a build-time variable -- make sure the production build has the correct value.

### HMAC Correlation Token Must Match Amsterdam's Format

The lander's `connect/route.ts` must generate the HMAC correlation token in the exact same format as amsterdam's `signCorrelationToken` in `apps/web/app/api/user/email-accounts/connect/route.ts`. The format is `userId:timestamp:hmacSha256(userId:timestamp)` using `UNIPILE_NOTIFY_SECRET` as the HMAC key. The timestamp must be `Date.now().toString()` (milliseconds), matching amsterdam's connect route. This is the same env var used by amsterdam's notify handler to verify the token.

Do NOT reuse `computeHmac` from `onboarding-auth.ts` -- it prepends an `onboarding:` scope prefix to the HMAC payload. Amsterdam's notify handler verifier expects bare `userId:timestamp` with no prefix. Copy the HMAC pattern from amsterdam's `signCorrelationToken` directly.

### Race Between Redirect and Notify Callback

When Unipile redirects the user back to the lander, the `notify_url` server-to-server callback may not have arrived yet. The InboxPane handles this by polling `/api/user/inbox/status` every 2 seconds for up to 30 seconds. The `?inbox=connected` query parameter triggers this polling mode on page load.

If polling times out after 30 seconds (notify callback did not arrive), the UI shows an error message with a "Try again" button that resets to the connect buttons.

### Query Param and Session-Check Interaction

On page load, the `useEffect` in `OnboardingPage` runs the session/cookie check. When `?inbox=connected` is present in the URL, the InboxPane must enter polling mode immediately instead of showing the connect buttons. The flow is:

1. `useEffect` runs, detects session or cookie, determines step is INBOX (no active account yet if notify hasn't arrived).
2. `InboxPane` mounts, reads `?inbox=connected` from the URL, enters polling mode.
3. Polling detects the connected account, calls `onNext()`.
4. If polling times out, shows error with "Try again" button.

### No Reconnect Logic in Onboarding

During onboarding, the user is connecting their first account. The connect route does not need reconnect logic (no existing Unipile account to check). This keeps the lander's connect route simpler than amsterdam's.

### determineOnboardingStep Needs a Second Query

The browser-side `determineOnboardingStep` function currently queries `user_settings` for `phone, imap_host, pin_hash`. Since `imap_host` is no longer the source of truth, add a second query: `.from("user_email_accounts").select("id").eq("is_active", true).eq("status", "connected").maybeSingle()`. The presence of a row means inbox is configured. This works because `user_email_accounts` has RLS with `auth.uid() = user_id`.

## Per-File Methods and Types/DTOs

### src/app/api/user/inbox/connect/route.ts (NEW)

#### Methods

| Method | Arguments | Returns | Description |
|--------|-----------|---------|-------------|
| `POST` | `request: Request` (body: `{ provider: "gmail" \| "outlook" }`) | `Response<{ url: string } \| { error: string }>` | Authenticates via resolveUserId, generates HMAC correlation token (same format as amsterdam), calls Unipile `POST /api/v1/hosted/accounts/link` to create hosted-auth link with `success_redirect_url` pointing to lander and `notify_url` pointing to amsterdam, returns the auth URL |

### src/app/api/user/inbox/status/route.ts (NEW)

#### Types

```text
InboxStatusResponse {
  connected: boolean
  provider: "gmail" | "outlook" | null
  emailAddress: string | null
}
```

#### Methods

| Method | Arguments | Returns | Description |
|--------|-----------|---------|-------------|
| `GET` | (none, auth via cookie/session) | `Response<InboxStatusResponse \| { error: string }>` | Queries user_email_accounts for an active connected row and returns connection status |

### src/app/api/user/onboarding-progress/route.ts (MODIFIED)

Change: `hasInbox` is now determined by querying `user_email_accounts` for an active row with `status = 'connected'` instead of checking `user_settings.imap_host`. The `user_settings` query changes from `select("phone, imap_host, pin_hash")` to `select("phone, pin_hash")`, and a separate query to `user_email_accounts` provides the inbox status.

### src/app/onboarding/page.tsx (MODIFIED)

#### Changes to InboxPane

The `InboxPane` component is rewritten:
- Removes: email input, app-password input, provider-specific setup instructions, save + test-connection flow
- Adds: two buttons ("Connect with Gmail", "Connect with Outlook"), a "Verifying connection..." polling state with timeout handling, and a `?inbox=connected` query param reader via `useSearchParams()`

#### Changes to determineOnboardingStep

The function adds a second query to `user_email_accounts` to check for an active connected row, replacing the `user_settings.imap_host` check. The `user_settings` query changes to `select("phone, pin_hash")`. This browser-side query works because `determineOnboardingStep` is only called when a Supabase session exists -- the cookie-auth path uses the server-side `onboarding-progress` endpoint instead.

## Success Criteria

- The onboarding INBOX step shows "Connect with Gmail" and "Connect with Outlook" buttons with no app-password form.
- Clicking a connect button redirects to Unipile OAuth, and after completion the user is redirected back to `/onboarding` where the flow advances automatically.
- If the notify callback is delayed, the UI polls for up to 30 seconds and shows a clear timeout error with retry option.
- The onboarding progress check correctly detects connected Unipile accounts in `user_email_accounts`.
