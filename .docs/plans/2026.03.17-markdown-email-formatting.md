# Markdown Email Formatting

## High-Level Goal

Replace JSON-serialized email tool results with markdown-formatted strings. This reduces token bloat (no JSON keys, no HTML tags), strips unnecessary HTML from email bodies via HTML-to-markdown conversion, and provides a cleaner representation for the LLM to consume.

Key decisions:
- Format at the tool/handler level, not in the IMAP client. Structured data stays available internally.
- Fix TS-side MIME parsing (currently naive header/body split that leaks raw MIME and base64). Python side already handles MIME correctly.
- `list_inbox` and `search_emails` keep the snippet approach (first 100 chars of clean text).
- `read_thread` uses horizontal rules (`---`) as message boundaries.
- Use `turndown` (TS) and `markdownify` (Python) for HTML-to-markdown conversion.
- Inline metadata format (bold field names, not tables).

## Types and Methods

### markdown-formatter.ts (NEW)

Markdown formatting functions for email tool results.

Converts structured email data into compact markdown strings for LLM consumption.

- Formats inbox listings, full emails, and thread conversations
- Uses inline bold metadata (not tables) to minimize tokens

#### Methods

| Method | Arguments | Returns | Description |
|--------|-----------|---------|-------------|
| `formatEmailSummaries` | `emails: EmailSummary[], title: string` | `string` | Formats a list of email summaries as a markdown list with snippets. Used by `list_inbox` and `search_emails`. |
| `formatEmail` | `email: Email` | `string` | Formats a single full email as markdown with inline metadata header and full body. |
| `formatThread` | `messages: ThreadMessage[]` | `string` | Formats a thread as markdown with `---` separators between messages. |

#### Output Formats

**formatEmailSummaries** (for list_inbox / search_emails):
```markdown
## Inbox (3 emails)

- **[id:142]** From: Alice <alice@ex.com> | 2026-03-10
  **Weekly standup notes**
  > Here are the notes from today's standup meeting. We discussed...

- **[id:139]** From: Bob <bob@ex.com> | 2026-03-09
  **Invoice #1234**
  > Please find attached the invoice for March...
```

**formatEmail** (for read_email):
```markdown
# Weekly standup notes

**ID:** 142
**From:** Alice <alice@ex.com>
**To:** you@example.com
**Date:** 2026-03-10T09:00:00Z
**Status:** Unread

---

Here are the notes from today's standup meeting.

We discussed the following items:
- Backend migration timeline
- Frontend redesign progress
```

**formatThread** (for read_thread):
```markdown
# Thread: Project kickoff (2 messages)

---

**From:** Alice <alice@ex.com>
**To:** you@example.com
**Date:** 2026-03-13T10:00:00Z | **ID:** 789

Let's get started on the project. When can you begin?

---

**From:** you@example.com
**To:** Alice <alice@ex.com>
**Date:** 2026-03-13T11:30:00Z | **ID:** 790

I can start next Monday. Does that work?

---
```

Only use `simpleParser` for full-body reads (`readEmail`, `readThread`) where `source: true` fetches the complete message.


### email_client.py (MODIFIED)

#### Changes

- In `_extract_body`: change the fallback logic. Currently it tries `get_body(preferencelist=("plain",))` and then falls back to raw `get_payload(decode=True)` which returns raw HTML bytes for HTML-only emails. New logic:
  1. Try `get_body(preferencelist=("plain",))` -- if found, use it
  2. Try `get_body(preferencelist=("html",))` -- if found, convert to markdown via `markdownify(html, strip=["style", "script"])`
  3. If neither exists, return empty string

| Method | Arguments | Returns | Description |
|--------|-----------|---------|-------------|
| `_extract_body` | `raw_source: bytes \| str` | `str` | Extracts plain text body. Falls back to HTML-to-markdown conversion via markdownify when no plain text part exists. |

## Important Technical Notes

### TS MIME parsing (imap-client.ts)

The current `extractBody` does a naive string split on `\r\n\r\n` and returns everything after the headers. For multipart MIME emails, this returns raw MIME boundaries, base64-encoded attachments, and HTML tags mixed together.

The fix uses `mailparser`'s `simpleParser`, which returns a parsed object with `.text` (plain text) and `.html` (HTML) properties. The logic is:
1. If `.text` exists, use it directly
2. If only `.html` exists, run it through `turndown` to get markdown
3. If neither exists, return empty string

`mailparser` is the standard companion library for `imapflow` (same author). It handles charset decoding, quoted-printable, base64, and multipart boundaries.

### HTML-to-Markdown edge cases

Both `turndown` and `markdownify` handle standard HTML well. Potential issues:
- Tracking pixels (`<img>` with 1x1 dimensions) -- these convert to `![]()` markdown images. Consider stripping `<img>` tags with width/height <= 1 before conversion.
- Email signature blocks with heavy HTML -- these will produce verbose markdown. Acceptable for now; can be stripped later if needed.
- Inline CSS / `<style>` blocks -- `turndown` ignores these by default. For `markdownify`, pass `strip=["style", "script"]` to remove these tags before conversion.

### Snippet extraction

**TS side**: `listInbox` and `searchEmails` fetch partial source (`maxLength: 2000`). Passing truncated MIME to `simpleParser` will break. Keep the current naive snippet extraction for these -- it works acceptably for the 100-char preview. Only use `simpleParser` for full reads.

**Python side**: `_extract_snippet` works on `BODY.PEEK[TEXT]<0.2000>` (partial text body), not on full RFC822 source. It never calls `_extract_body`. This partial text could be HTML. For now, this is acceptable since the snippet is only 100 chars and HTML tags at the start are unlikely to be worse than the current behavior. If it becomes an issue, we can run a lightweight tag strip (not full markdownify) on the snippet later.

### JSON serialization of markdown results

In `pipeline.py`, the result is serialized via `json.dumps(result_dict)`. When the result contains `{"markdown": "<long string>"}`, every newline in the markdown becomes `\\n` in the JSON. This partially negates the token savings. Acceptable for now -- the primary goal is clean text extraction (no HTML/MIME garbage). The JSON wrapper can be optimized later if needed.
