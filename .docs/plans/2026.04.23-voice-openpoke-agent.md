# Voice OpenPoke Agent Plan

Short summary: migrate `apps/whatsapp-agent` from a single tool-calling voice agent to a voice-specific OpenPoke architecture with an interaction agent and an execution agent.

- Keep the voice agent implementation inside `apps/whatsapp-agent`
- Mirror the OpenPoke architecture used by WhatsApp text, but do not share the runtime with `apps/whatsapp-server/src/text`
- Keep the existing LiveKit call bootstrap, STT, TTS, and session lifecycle unless a later phase explicitly changes them

## Goal

Bring the WhatsApp voice agent onto the same OpenPoke model as the text agent:

- the interaction agent is the only layer that talks to the user
- the interaction agent decides whether to reply, wait, show a draft, or delegate
- the execution agent owns tool work and returns structured results
- the voice runtime remains voice-specific and can diverge from text later

## Decisions And Constraints

- Do not make the voice agent share the text runtime files
- It is fine to copy patterns from the text implementation if the voice implementation stays independent
- Use the same prompt behavior and OpenPoke prompt structure as the text agent in the first implementation
- Do not adapt prompts to voice-specific behavior yet unless required to make the runtime work
- Keep LiveKit as the runtime for the voice agent
- Replace direct tool execution in the speaking agent with interaction-tool delegation
- Preserve existing voice-specific context injection, greeting behavior, memory loading, Gmail context, and session persistence where still useful
- Voice needs interruption safety: old delegated work must not speak after a newer user turn has started

## Current State

Today the voice agent is not OpenPoke yet:

- `apps/whatsapp-agent/src/agent.ts` builds one `voice.Agent` with tools attached directly
- `apps/whatsapp-agent/src/lib/composio.ts` exposes Composio session tools directly to the LiveKit LLM
- there is no separate interaction agent runtime
- there is no separate execution agent runtime
- there is no explicit voice-side `send_message_to_agent`, `send_message_to_user`, `send_draft`, or `wait` loop

## Target State

The desired voice architecture:

- `agent.ts` remains the LiveKit bootstrap and session lifecycle entrypoint
- a voice interaction agent owns user-facing behavior
- a voice execution agent owns Composio tool work
- the interaction agent exposes only OpenPoke-style interaction tools
- the execution agent never talks directly to the user
- the interaction agent decides what to say after execution returns
- the voice runtime can later diverge from text without shared-runtime coupling

## Main Tradeoffs

### Keep LiveKit as the voice runtime

Decision:

- keep LiveKit for STT, TTS, and room session management
- replace the architecture inside the voice agent without replacing LiveKit

Why:

- lower migration risk
- smaller first change
- preserves current call transport behavior

Out of scope for this plan:

- rewriting the full voice stack into a custom STT -> LLM -> TTS pipeline

Why not:

- much larger scope
- mixes architecture migration with transport/runtime migration
- makes debugging harder

### Separate codebases vs shared runtime

Recommended:

- keep a separate OpenPoke implementation in `apps/whatsapp-agent`

Why:

- voice turn handling and interruption semantics differ from text
- the user explicitly wants future changes without tight coupling
- architecture can match without sharing code

Cost:

- some duplicated logic
- separate tests and maintenance

## Important Implementation Notes

- After each phase, check the completed checkboxes in this plan
- When new findings pop up during implementation, add them to this plan before moving on
- Fail fast on invalid tool arguments and invalid runtime state
- Keep code readable and explicit for junior developers
- Prefer simple DTOs and small single-purpose functions
- When porting prompts from text, keep the same prompt logic first and defer channel-specific wording changes

## Open Questions

- How much control does the current LiveKit API give us over per-utterance turn boundaries and interruption hooks?
- Should `send_draft` in voice only speak a short summary, or should it also persist a structured draft artifact for the web app?
- Do we want the interaction agent to keep a full per-call in-memory history separate from the LiveKit session history, or is one source of truth enough for phase 1?
- Should `apps/whatsapp-agent/src/lib/composio.ts` be reduced to execution-agent helpers, or replaced completely by new `openpoke` files?

## Findings

- The current OpenPoke implementation in this repo is the WhatsApp text flow inside `apps/whatsapp-server/src/text`
- The current voice agent in `apps/whatsapp-agent` is still a single tool-calling agent, not an interaction/execution split
- The user wants the first voice OpenPoke version to use the same prompts as text rather than adapting prompts to voice behavior yet
- The user wants LiveKit to remain the voice runtime; this plan should not imply a later migration away from LiveKit
- LiveKit tools can call `options.ctx.session.say(...)` and return `undefined`; this suppresses the extra tool-reply generation and gives us a clean `send_message_to_user` tool
- The current implementation now uses a voice-local OpenPoke execution agent plus a LiveKit interaction agent with OpenPoke interaction tools
- Turn supersession and stale-result handling are still pending; that work belongs in the remaining voice-specific turn-control phase
- The voice runtime now uses an explicit voice-local interaction loop driven by OpenRouter per turn instead of relying on LiveKit's built-in interaction planning
- LiveKit remains responsible for STT, TTS, and the call session, while the per-turn interaction prompt now follows the same tagged structure as the text agent
- `send_draft` was intentionally removed from the voice tool surface and the voice interaction prompt was updated so it no longer references drafts
