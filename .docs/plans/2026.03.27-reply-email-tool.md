# Plan: reply_email Tool

## High-Level Goal

Add a `reply_email` tool that allows the voice assistant to reply to an existing email. The tool is classified as `mutating_queued` (always requires dashboard approval before sending). It fetches the original email's headers from IMAP, builds a properly threaded reply message with `In-Reply-To` / `References` headers, and sends via SMTP upon approval. A `reply_all` boolean parameter controls whether all original recipients are included.

## Important Technical Notes

### Threading Headers (RFC 2822 / RFC 5322)

When replying, the outgoing message must include:
- `In-Reply-To`: the `Message-ID` of the email being replied to
- `References`: the original email's `References` header value + the original's `Message-ID` appended

This ensures email clients (Gmail, Outlook, etc.) group the reply into the same thread.

### Address Extraction

The existing `formatAddress()` / `_format_address()` helpers only return the first address from the envelope array. `fetchReplyContext` must iterate over **all** addresses in the envelope's `to` and `cc` arrays and extract the raw email address (not the display name), since these are used for SMTP recipients.

### Reply-All Recipient Logic

For `reply_all: true`:
- `To` = original `From` (the sender we are replying to)
- `CC` = original `To` + original `CC`, minus the current user's address (to avoid sending to yourself)

For `reply_all: false` (default):
- `To` = original `From`
- `CC` = empty

### Subject Prefix

Prefix with `Re: ` only if the subject does not already start with `Re:` (case-insensitive). This avoids chains like `Re: Re: Re: Hello`.

### Approval Flow

`reply_email` follows the exact same `mutating_queued` path as `send_email`:
1. LLM calls `reply_email` with `email_id`, `body`, and optionally `reply_all`
2. `handle_tool_call` classifies it as `mutating_queued`
3. Action is inserted as `pending` in the `actions` table
4. User approves from dashboard
5. `executeAction()` calls `dispatchTool("reply_email", ...)` which fetches the original email headers via IMAP and sends via SMTP

This means the IMAP fetch of the original email happens at **execution time** (when approved), not at queue time. The `email_id` UID stored in arguments must still be valid at approval time.

### Non-Override Rule

Like `send_email`, `reply_email` should be hardcoded to always be `mutating_queued` -- user config overrides should not be able to make it auto-execute. This must be enforced in three places:
1. `classifyAction()` in `action-queue.ts` (TS)
2. `classify_action()` in `classification.py` (Python)
3. `_build_tool_behavior_section()` in `prompt.py` (so the LLM prompt always shows it as requires-approval)
