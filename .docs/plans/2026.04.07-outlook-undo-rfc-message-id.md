# Plan: Outlook Undo via RFC Message-ID

## High-Level Goal

Fix Unipile undo for Outlook emails (issue #168). When Outlook moves an email, its Unipile `id` and `provider_id` go stale (404). The fix uses the RFC Message-ID header (stable across moves) to re-find the email under its new ID before performing the undo PUT.

Gmail IDs stay stable, so Gmail continues using the direct ID approach -- no change needed there. The branching is explicit: the provider is known at mutation time, so we pick the right strategy upfront.

## Important Technical Notes

### RFC Message-ID retrieval uses the email_id passed to mutations

The codebase already uses `provider_id` as the email identifier everywhere (set in `_map_to_email_summary`). The `email_id` parameter in the mutation functions IS the `provider_id`. No special ID translation is needed -- `_get_rfc_message_id` receives the same `email_id` that `read_email` already uses successfully.

### `message_id` filter behavior differs by provider

`GET /api/v1/emails?message_id=<RFC-Message-ID>` works for Outlook but returns 0 results for Gmail. This is fine because Gmail IDs are stable and never need re-finding. The undo code branches explicitly on provider, so Gmail never hits this code path.

### Ordering: fetch Message-ID BEFORE the move

For Outlook, `_get_rfc_message_id` must be called **before** the PUT that moves the email. If the header fetch fails, the mutation cleanly aborts (email stays in place). If the fetch were done after the move, the old ID would already be stale for Outlook, making the fetch impossible.

### Gmail Unipile undo sync delay

Gmail undo PUT returns 200 but the email doesn't reappear in inbox listings for an extended period (Unipile sync/cache issue). This is a separate problem from #168 and should remain xfailed. The xfail condition uses `account.email_ctx.provider == "gmail"` (not string matching on the label).

### Re-find may return multiple results

The `message_id` filter can return multiple emails (e.g., sent + received copies). The re-find helper picks the first result. In practice, the undo recipe knows the target folder, so the PUT moves the correct copy regardless of which ID is returned -- the folders array on the PUT determines where it ends up.

### Extra API call for Outlook mutations

For Outlook, each mutation adds one extra HTTP round-trip (`_get_rfc_message_id`) before the move, and undo adds one extra round-trip (`_refind_email_by_message_id`). This adds ~200-400ms per operation. Gmail is unaffected. This is acceptable for the voice pipeline since these are user-initiated, one-off operations.

### include_headers API contract

Verified empirically: `GET /api/v1/emails/{provider_id}?account_id=X&include_headers=true` returns a `headers` array of `{name, value}` dicts. The `Message-ID` header (case-insensitive match on `name`) contains the RFC 2822 Message-ID. Tested for both Gmail and Outlook.

### Undo recipe serialization

The undo recipe `params` dict is serialized as JSON to the `undo_recipe` column in the `actions` table. Adding `rfc_message_id` as a new key is safe -- the column is untyped JSON, no schema validation rejects unknown keys. Verified in `handlers.py` lines 179-183 (serialization) and lines 248-255 (deserialization).

### Additional fix discovered during testing

During e2e testing, the RFC Message-ID approach alone was not enough. The underlying bug was that
`_resolve_folder_by_role()` returned the Unipile internal `id` instead of `provider_id`. The PUT
`folders` field needs the Exchange `provider_id` for the move to actually happen. Also fixed
`list_folders()` to return `provider_id` in `FolderInfo.path`.

See `testscripts/2026.04.07-outlook-undo-rfc-message-id/README.md` for full investigation details.
