# Onboarding & Engagement Emails

## High-Level Goal

Add automated email engagement to guide users through onboarding and keep them active after signup. A cron-triggered API route checks user state against trigger conditions and sends the appropriate email via Resend. An `email_events` table prevents duplicate sends.

Key decisions:
- Lives in `apps/web` (at `/Users/Focus/Documents/Codebases/brief/apps/web`) where Resend is already configured
- Single cron route processes all email types in one pass
- Uses `createServiceRoleClient()` to bypass RLS (same pattern as end-of-session)
- Cron runs every 15 minutes via Vercel Cron
- Auth via `CRON_SECRET` env var (Vercel's built-in cron auth pattern)
- The onboarding site (helsinki-v1) is not modified -- incomplete onboarding emails link to its `/onboarding` URL via `NEXT_PUBLIC_LANDER_URL` env var
- Only users with `email_confirmed_at IS NOT NULL` receive emails
- Uses wide time windows + dedup log (not narrow windows) to survive missed cron runs
- Batch limit of 50 emails per cron invocation to stay within Vercel function timeout
- **One email per user per cron run** -- priority-based dedup prevents flooding (see Overlap Handling)

## Overlap Handling

A user can be eligible for multiple emails at the same time (e.g., signs up, completes onboarding 25h later -- eligible for both `welcome` and `no_call_nudge_24h`). To prevent flooding:

### Rules

1. **Eligibility first**: All filter functions run and produce a full list of candidates across all paths. The `email_events` dedup table excludes emails already sent, so only unsent emails appear as candidates.
2. **24h cooldown**: Before sending to a user, check their most recent `sent_at` in `email_events`. If it is less than 24h ago, skip them entirely for this cron run. This prevents multiple emails landing close together when a user becomes eligible for several at once.
3. **Priority second**: Per user, only the highest-priority email is sent per cron run. Priority order:
   - Path 1 (complete onboarding) > Path 2 (get started) > Path 3 (reactivation) > Path 4 (upgrade)
   - Within a path: lower letter wins (1a > 1b > 1c, 2a > 2b > 2c > 2d > 2e)
4. **Remaining emails survive**: Emails that were eligible but deprioritized or cooldown-skipped are NOT marked as sent. They remain eligible and will be picked up once the cooldown expires.
5. **Tracking**: Every sent email is recorded in `email_events` with `INSERT ON CONFLICT DO NOTHING`. The unique constraint on `(user_id, email_type)` is the ultimate safety net against duplicates, even if two cron runs race.

### Example flow

- **Cron run at T+0**: User is eligible for `welcome` + `no_call_nudge_24h`. Priority picks `welcome`. It gets sent. `email_events` records `welcome` with `sent_at = now()`.
- **Cron run at T+15m**: `welcome` is filtered out (already sent). `no_call_nudge_24h` is eligible, but the user's last `sent_at` is 15m ago -- cooldown blocks it. Skipped.
- **Cron run at T+24h**: Cooldown has expired. `no_call_nudge_24h` is the top candidate. It gets sent.

## Important Technical Notes

### Cron authentication

Vercel Cron sends an `authorization: Bearer <CRON_SECRET>` header. The route must verify this before processing. This is separate from `INTERNAL_API_KEY` used for service-to-service calls.

### Preventing duplicate sends

Each check query joins against `email_events` to exclude users who already received that email type. The `email_events` table has a unique constraint on `(user_id, email_type)` to prevent duplicates at the DB level even if two cron invocations race. Use `INSERT ... ON CONFLICT DO NOTHING` when recording sent emails.

### Wide time windows, not narrow

Queries use `created_at <= now() - interval 'Xh'` (not `BETWEEN`) combined with the dedup log. This means if a cron run is missed, the next run picks up all eligible users. The dedup constraint prevents re-sending.

### Determining onboarding completion time

There is no explicit `onboarding_completed_at` column. Onboarding is "complete" when `user_settings` has all three fields set: `phone` (JSONB), `imap_host`, `pin_hash`. The `updated_at` on `user_settings` serves as a proxy for completion time (since `pin_hash` is the last step set during onboarding).

Note: The `phone` column is JSONB (not text). Migration 011 dropped the old `phone_number` text column and replaced it with `phone jsonb`. The completeness check must be: `phone IS NOT NULL AND imap_host IS NOT NULL AND pin_hash IS NOT NULL`.

Known limitation: `updated_at` changes on any settings update (voice preference, approval config, etc.), not just onboarding completion. This means timing-based emails (welcome, no-call-nudge) may fire slightly early or late if the user tweaks other settings right after completing onboarding. This is acceptable -- the consequences are minor (slightly mis-timed emails).

### Email confirmed filter

All queries filter on `email_confirmed_at IS NOT NULL`. Users who signed up but never confirmed should not receive engagement emails.

### Data fetching pattern: admin API + JS join

The `auth.users` table is not queryable via the Supabase PostgREST `.from()` API. To get user emails and `created_at`/`email_confirmed_at`, the check functions must use `supabase.auth.admin.listUsers()` (paginated, max 1000 per page). The application tables (`user_settings`, `sessions`, `subscriptions`, `email_events`) are queried via `.from()` with the service role client.

The check functions follow a two-step pattern:
1. **Fetch**: Get confirmed users from admin API + relevant rows from application tables
2. **Filter**: Join and filter in JS to produce `EmailCandidate[]`

This split also makes the filter logic unit-testable with plain arrays (no Supabase mocking needed for the core matching logic).

### Template architecture

Each email type has its own template file under `lib/resend/templates/`. Each file exports a function that takes `landerUrl`/`appUrl` and returns an `EngagementEmailContent` (subject, heading, body, ctaText, ctaUrl). The HTML building happens in `sendEngagementEmail` in `client.ts`.

All engagement emails must reuse the exact same HTML structure and styles as the existing `confirm-email.html` and `sessionSummary.ts` templates:

- **Outer shell**: `#f4f4f5` background, centered 600px white container with `1px solid #e4e4e7` border
- **Logo**: 28x28 black square with white "B" (Georgia serif), "BrewDock" label beside it, padding `32px 40px 0 40px`
- **Heading**: `font-size:24px; font-weight:800; color:#000000; letter-spacing:-0.03em`
- **Body text**: `font-size:15px; font-weight:500; color:#52525b; line-height:1.5`
- **CTA button**: Black (`#000000`) background, white text, `padding:12px 28px; font-size:15px; font-weight:600`, with `&#8594;` arrow
- **Footer**: `#fafafa` background, "BrewDock" + "Do your email while you drive." + mailing address
- **Font stack**: `Inter,-apple-system,BlinkMacSystemFont,'Segoe UI',Roboto,sans-serif`
- **Outlook compat**: MSO conditional `PixelsPerInch` block, `role="presentation"` on all tables

Reference files:
- `apps/web/lib/resend/templates/sessionSummary.ts` -- existing TS template with shared constants
- `.docs/email-templates/confirm-email.html` -- static HTML template for Supabase auth emails

### Batch processing

The cron processes a maximum of 50 emails per invocation to stay within Vercel function timeout limits (60s on Pro). If more candidates exist, they'll be picked up on the next run (15 min later). Candidates are processed in signup-date order (oldest first).

### Unsubscribe

Engagement emails include Resend's `List-Unsubscribe` header support. Resend handles unsubscribe automatically when configured with a verified domain. The `email_events` table does not need to track unsubscribes -- Resend suppresses delivery to unsubscribed addresses.

### 016_email_events.sql (NEW)

```sql
create table email_events (
  id uuid primary key default uuid_generate_v4(),
  user_id uuid not null references auth.users(id) on delete cascade,
  email_type text not null,
  resend_email_id text,
  sent_at timestamptz default now(),

  constraint email_events_user_type_unique unique (user_id, email_type)
);

create index idx_email_events_user_id on email_events(user_id);
```

No RLS needed -- only accessed via service role client.
