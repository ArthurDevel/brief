# Batch IMAP Enrichment

## Goal

Replace the sequential per-action IMAP enrichment with a batched approach. Currently, each email action triggers a separate lock acquire/release and FETCH command, taking ~237ms per action (~40 seconds for 170 actions). A batched UID fetch achieves the same result in ~15ms per action (~2.5 seconds for 170 actions).

Additionally, make the end-of-session webhook fire-and-forget from the voice pipeline, removing the 10-second timeout constraint entirely.

## Important Technical Notes

### Batched UID FETCH

ImapFlow's `client.fetch(uidSet, { envelope: true, uid: true })` accepts a comma-separated UID string (e.g. `"5,12,89,102"`) and returns an async iterable of message objects. Note: `uid: true` is part of the fetch options object (not a separate third argument) -- see `searchEmails` in `imap-client.ts` line 188 for the existing pattern. This sends a single IMAP FETCH command to the server, ~16x faster than individual fetchOne calls (benchmarked at 743ms vs 11,846ms for 50 emails).

### Message-ID lookups cannot be batched

IMAP SEARCH by header only supports one value per command. These remain sequential but benefit from:
1. Calling `resolveSpecialUseFolder` (which uses `client.list()`, no lock needed) once before acquiring any mailbox locks
2. Holding the lock open for the entire loop per folder instead of re-acquiring per action

### Two-phase locking for Message-ID lookups

ImapFlow only allows one mailbox lock at a time. The message-ID path works in two phases:
1. Lock All Mail, search all message_ids, release lock
2. For any not-found message_ids, lock Trash, search remaining, release lock

### Grouping strategy

Actions are split into two groups before any IMAP calls:
1. **UID group** -- actions that have `email_id` but no `message_id`. Single batched FETCH in INBOX. UIDs are always INBOX UIDs (numeric string like `"42"`); if non-INBOX UIDs are ever needed, the interface must be extended.
2. **Message-ID group** -- actions that have `message_id`. Prefer message_id over uid when both are present (message_id is stable across folder moves).

Results from both groups are merged into a single `Map<actionId, EmailMeta>`.

### Folder resolution may throw

`resolveSpecialUseFolder` throws if the special-use folder is not found (e.g. non-Gmail accounts without `\All`). This is the same behavior as today -- the batch function does not add fallback handling for missing folders.

### Fire-and-forget with observability

The voice pipeline wraps the end-of-session POST in `asyncio.create_task()` with a wrapper coroutine that still awaits the response and logs success/failure. This way the call is non-blocking but errors are still logged.

### Enrichment uses its own IMAP connection

The end-of-session route creates its own IMAP connection (line 146 of route.ts), separate from the voice pipeline's connection which is closed earlier in `_cleanup_session`. These are fully independent.

## Types and Methods

### types.ts (MODIFIED)

#### Types

```
EmailMetaRequest {
  actionId: string           -- action row ID, used as key in the result map
  uid?: string               -- email UID for direct fetch (INBOX)
  messageId?: string         -- RFC Message-ID for header search (All Mail / Trash)
}
```

At least one of `uid` or `messageId` must be set. If both are present, `messageId` is preferred.

### imap-client.ts (MODIFIED)

#### Methods

| Method | Arguments | Returns | Description |
|--------|-----------|---------|-------------|
| `fetchEmailMetaBatch` | `client: ImapFlow, requests: EmailMetaRequest[]` | `Promise<Map<string, EmailMeta>>` | Groups requests by lookup type. UID group: single lock on INBOX, single `client.fetch()` call. Message-ID group: resolve folder paths once up front, lock All Mail then Trash for remainder. Returns map of actionId to EmailMeta. Individual failures are skipped, not thrown. |

Removed: `fetchEmailMetaByMessageId`, `fetchEmailMetaByUid`, `searchAndFetchMeta` (replaced by batch function).

### end-of-session/route.ts (MODIFIED)

#### Methods

| Method | Arguments | Returns | Description |
|--------|-----------|---------|-------------|
| `enrichActionsWithEmailMeta` | `actions: ActionRow[], imapClient: ImapClient, log: Function` | `Promise<ActionRow[]>` | Builds `EmailMetaRequest[]` from candidate actions, calls `fetchEmailMetaBatch` once, merges results back into action arguments. Replaces the current per-action loop. |

### server.py (MODIFIED)

#### Methods

| Method | Arguments | Returns | Description |
|--------|-----------|---------|-------------|
| `_trigger_end_of_session_hook` | `session_id: str` | `None` | Wraps the end-of-session POST in `asyncio.create_task()` with a coroutine that awaits the response and logs success/failure. Non-blocking to the caller. |

## Phases

### Phase 1: Add `fetchEmailMetaBatch` to the email package

1. Add `EmailMetaRequest` interface to `packages/email/src/types.ts`
2. Implement `fetchEmailMetaBatch` in `packages/email/src/imap-client.ts`:
   - Split requests into uid-group (no messageId) and messageId-group (has messageId)
   - UID group: single lock on INBOX, `client.fetch(uids.join(","), { envelope: true, uid: true })`, iterate async iterable, match results back to actionIds by UID
   - Message-ID group: call `client.list()` once to resolve All Mail and Trash paths, lock All Mail and loop SEARCH+fetchOne, release, then lock Trash for any remaining not-found, release
   - Return `Map<string, EmailMeta>` with all successful lookups
3. Grep the codebase to confirm no other consumer imports `fetchEmailMetaByMessageId` or `fetchEmailMetaByUid` outside of `route.ts`
4. Remove `fetchEmailMetaByMessageId`, `fetchEmailMetaByUid`, `searchAndFetchMeta`
5. Update exports in `packages/email/src/index.ts`

1. Replace imports with `fetchEmailMetaBatch` and `EmailMetaRequest`

3. Remove unused imports
