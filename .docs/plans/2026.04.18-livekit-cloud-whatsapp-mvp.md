# LiveKit Cloud WhatsApp MVP

## Goal

Validate the smallest end-to-end architecture that lets a user place a WhatsApp call, route that call through `@apps/whatsapp-server`, connect into a LiveKit Cloud room, and converse with a deployed LiveKit agent that can call Composio tools directly.

This plan is intentionally not trying to recreate `apps/voice-pipeline`.

Hard decisions for this plan:
- TypeScript only
- no Python
- no Supabase auth
- no queueing
- no dashboard flow
- no `voice-pipeline` port

Out of scope for this MVP:
- Supabase-backed user authentication
- PINs
- approval queues
- dashboard integration
- feature parity with Twilio / Pipecat flows

Instructions for whoever executes this plan:
- After each phase, check the completed boxes in this document.
- When new findings pop up, add them to this plan before moving on.

## Target Architecture

```text
WhatsApp Call
  -> Meta webhook
  -> apps/whatsapp-server
  -> WhatsApp WebRTC termination
  -> LiveKit Cloud room
  -> LiveKit Cloud-hosted agent
  -> Composio tools
```

Responsibilities:
- `apps/whatsapp-server` owns Meta webhook verification, WhatsApp call accept flow, and media bridging.
- LiveKit Cloud owns the room and hosts the agent runtime.
- `apps/whatsapp-agent` owns prompt, model config, and direct Composio tool usage.

Concrete implementation choices:
- Agent runtime: TypeScript on Node.js
- Agent hosting: LiveKit Cloud
- Bridge hosting: our server in `apps/whatsapp-server`
- Tool layer: Composio TypeScript SDK
- Temporary identity: one fixed Composio user ID, `demo`

## Key Tradeoffs And Technical Implications

### Why use LiveKit Cloud here

- It reduces operational burden for the agent runtime.
- It gives a clean place to deploy and iterate on the agent separately from the WhatsApp bridge.
- It supports agent secrets via environment variables, so Composio and later Supabase credentials can still be injected there.

### Why `apps/whatsapp-server` still exists

- LiveKit Cloud does not natively terminate WhatsApp calls.
- The WhatsApp call still arrives through Meta’s calling webhook and SDP exchange.
- Therefore a bridge service is still required even if the agent is fully hosted on LiveKit Cloud.

### Why we are not porting `apps/voice-pipeline`

- The Twilio/PIN/queueing stack solves a different problem.
- Porting it now would slow down validation of the WhatsApp + LiveKit architecture.
- The only useful references for now are call lifecycle ideas and later session persistence patterns.

### Temporary identity model

For the MVP, every call uses the same Composio user ID: `demo`.

Do not add caller-specific auth or user linking in this pass.

### Main technical risk

The highest-risk part is not the agent. It is the media bridge:
- accepting the WhatsApp WebRTC offer
- joining a LiveKit room as a participant
- forwarding inbound audio to LiveKit
- forwarding LiveKit agent audio back to WhatsApp

If this bridge is unstable, the rest of the stack does not matter.

Exit criteria:
- An inbound WhatsApp call reaches a LiveKit room.
- The LiveKit Cloud agent can hear the caller and respond audibly on the WhatsApp call.

- [ ] Ensure room names, participant identities, and call IDs are logged consistently.
- [ ] Add timeouts and cleanup for failed bridge setup.

- [ ] Add minimal health and debug logging for bridge state transitions.

Exit criteria:
- Repeated connect/terminate paths do not leak rooms, processes, or peer connections.
- Failures are debuggable from logs.

## Phase 5: Minimal Persistence And Future Hooks

- [ ] Decide whether to store any call metadata at all for the MVP; default to logs only.
- [ ] If needed, add a tiny call record with `call_id`, `room_name`, `caller`, and timestamps.
- [ ] Document the next-step path for later Supabase integration without implementing it now.
- [ ] Document the next-step path for real user mapping / account linking without implementing it now.

Exit criteria:
- The MVP is usable without Supabase auth.

## Fixed Decisions

- Use TypeScript everywhere.
- Do not create any Python service.
- Use a separate `apps/whatsapp-agent` app instead of extending `apps/voice-pipeline`.
- Host the agent on LiveKit Cloud.
- Keep the WhatsApp bridge in `apps/whatsapp-server`.
- Use separate LiveKit identities for bridge and agent participants.
- Use a fixed Composio user ID, `demo`.
- Do not implement Supabase auth, queues, or approval flows.

## Initial Findings

- `apps/whatsapp-server/src/callBot.ts` already handles the Meta call SDP offer/answer and currently plays a local greeting through RTP. This is the right interception point for replacing local playback with LiveKit bridging.
- `apps/voice-pipeline` is reference material only for now. Its Twilio auth, PIN, queueing, and approval model should not be copied into this MVP.
- LiveKit Cloud can host the agent and inject secrets at runtime, so Composio credentials and later Supabase credentials can live there if desired.
- Even with LiveKit Cloud, the WhatsApp-facing bridge still needs to be hosted by us because Meta sends the webhook and media negotiation to our service, not directly to LiveKit.
- `apps/whatsapp-agent` now exists as a standalone TypeScript LiveKit agent. It builds locally and exposes allowlisted Composio tools by converting raw Composio tool schemas into LiveKit `llm.tool(...)` definitions.
- `apps/whatsapp-server` now creates a LiveKit room per call, dispatches the configured agent, and bridges audio using `ffmpeg` as the RTP/Opus <-> PCM shim on both the inbound and outbound paths.
- The new bridge code compiles, but it has not been validated against a real WhatsApp call or a real LiveKit Cloud project because `LIVEKIT_*` and `COMPOSIO_API_KEY` credentials were not available in the implementation environment.

## Suggested First Execution Order

1. Complete Phase 1 before touching the WhatsApp bridge.
2. Complete Phase 2 before attempting full media forwarding.
3. Only then modify `apps/whatsapp-server` for Phase 3.

This keeps the hardest problem isolated: first prove the agent, then prove Composio, then prove the bridge.
