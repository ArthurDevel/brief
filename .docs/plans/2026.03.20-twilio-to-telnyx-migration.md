# Twilio to Telnyx Migration

## High-Level Goal

Replace Twilio as the telephony provider with Telnyx for incoming voice calls. The current system uses Twilio webhooks + TwiML for IVR (PIN authentication) and Twilio Media Streams for bidirectional audio over WebSocket. Telnyx uses a REST-based Call Control API instead of TwiML, and has a similar (but not identical) WebSocket media streaming protocol. The migration preserves all existing behaviour: phone number lookup, PIN verification via DTMF, usage limit checks, account locking, and bidirectional audio streaming into the Pipecat pipeline.

Key architectural difference: Twilio uses a "return XML" webhook model (server returns TwiML). Telnyx uses a "command API" webhook model (server receives webhook events and sends REST commands back to Telnyx). This means the IVR flow shifts from "return TwiML response" to "receive event webhook, then POST command to Telnyx API".

## Important Technical Notes

### Twilio vs Telnyx: Webhook Model Difference

Twilio uses a synchronous "return TwiML" model: the webhook endpoint returns XML that instructs Twilio what to do. Telnyx uses an asynchronous "command API" model: the webhook endpoint receives an event, then makes REST API calls back to Telnyx to issue commands (answer, gather, speak, stream, hangup).

This means:
- Twilio endpoints return `Response(content=twiml, media_type="text/xml")`. Telnyx endpoints return `200 OK` immediately, then fire off API calls to Telnyx.
- State must be tracked between webhook calls. Telnyx provides `client_state` (base64-encoded string) that gets forwarded through subsequent webhooks. We use this to pass `user_id` and `attempt` count through the IVR flow.
- The server needs an HTTP client (httpx) to call the Telnyx Call Control API. Each command is a POST to `https://api.telnyx.com/v2/calls/{call_control_id}/actions/{action}`.

### IVR Event Flow

The webhook flow is split across multiple async events. Important: you cannot `speak` on an unanswered call -- the call must be answered first.

**Happy path (registered user, correct PIN):**
1. `call.initiated` -- Incoming call arrives. No `client_state` exists yet. Do phone lookup. If user is unknown, call `reject` (silent rejection, no speech needed). If user is found, build client_state with user_id and call `answer`.
2. `call.answered` -- Telnyx confirms the call is answered. Decode client_state. Check if account is locked or usage limit exceeded -- if so, call `telnyx_speak_and_hangup` (the call is now answered so speech works). Otherwise, call `gather_using_speak` to prompt for PIN.
3. `call.gather.ended` -- DTMF digits collected. Decode client_state for user_id and attempt. Fetch `pin_hash` from Supabase (do NOT store pin_hash in client_state for security). Verify PIN, then either POST `streaming_start` (success) or `gather_using_speak` again (retry) or `speak_and_hangup` (max attempts, lock account).

**Rejection path (locked/over-limit):**
1. `call.initiated` -- Answer the call (need to answer before we can speak).
2. `call.answered` -- Detect locked/over-limit via client_state flag, speak rejection, hang up on `call.speak.ended`.

**Timeout/no input:**
- `call.gather.ended` with `status: "timeout"` or empty digits -- speak "No input received. Goodbye." and hang up via `call.speak.ended`.

**Other events:**
- `call.speak.ended` -- Check `hangup_after_speak` flag in client_state, issue hangup if set.
- `call.streaming.started` -- No-op, log only.
- `call.hangup` -- No-op, log only.
- Unknown events -- Return 200, log at debug level.

### client_state for IVR Flow

Telnyx forwards a `client_state` field through webhook events. We encode a JSON object `{"user_id": "...", "attempt": N}` as base64 and pass it through the answer -> gather -> verify flow. This replaces Twilio's approach of encoding userId/attempt in query parameters of the TwiML action URL.

### Speak-then-Hangup Sequencing

With Telnyx's async model, calling `speak` then immediately calling `hangup` would interrupt the speech. For rejections where we want to play a message before hanging up, we handle the `call.speak.ended` event in the webhook dispatcher to issue the hangup. The `telnyx_speak_and_hangup` helper only fires the `speak` command and sets a `client_state` flag `{"hangup_after_speak": true}`. The webhook handler then checks for this flag on `call.speak.ended` and calls `telnyx_hangup`.

### Media Streaming Protocol Differences

| Aspect | Twilio | Telnyx |
|--------|--------|--------|
| Start streaming | TwiML `<Connect><Stream>` | REST API `streaming_start` command |
| WS "start" event | `{"event": "start", "start": {"streamSid": "...", "customParameters": {...}}}` | `{"event": "start", "stream_id": "...", "start": {"call_control_id": "...", "client_state": "...", "media_format": {...}}}` |
| WS "media" event | `{"event": "media", "media": {"payload": "..."}}` | `{"event": "media", "media": {"track": "inbound", "payload": "..."}}` |
| WS "stop" event | `{"event": "stop"}` | `{"event": "stop", "stream_id": "...", "stop": {...}}` |
| Audio codec | Always mulaw 8kHz | Configurable: PCMU (mulaw), L16, OPUS, etc. We use PCMU 8kHz |
| Clear/flush audio | Send `{"event": "clear", "streamSid": "..."}` | Send `{"event": "clear", "stream_id": "..."}` |
| Stream identifier | `streamSid` | `stream_id` |
| Bidirectional send | `{"event": "media", "streamSid": "...", "media": {"payload": "..."}}` | `{"event": "media", "media": {"payload": "..."}}` |

The media format is very similar. We use PCMU (mulaw) 8kHz for Telnyx as well, so `transcoder.py` logic stays the same.

### Passing userId to the WebSocket

With Twilio, we passed `userId` via TwiML `<Parameter>` and extracted it from the "start" event's `customParameters`. With Telnyx, we encode `userId` in the `client_state` of the `streaming_start` command. Telnyx includes `client_state` in the "start" event, which we decode to extract the userId.

### Stream URL Construction

The `/telnyx/webhook` handler needs to construct the WebSocket stream URL when calling `telnyx_streaming_start`. Use `settings.public_url` to derive the URL: replace `http(s)://` with `ws(s)://` and append `/telnyx-stream`. This matches how the current Twilio code builds the stream URL in the `/twilio/verify-pin` endpoint (server.py lines 638-644).

### Error Handling for Telnyx API Calls

All `_telnyx_command` calls should be wrapped in try/except within the webhook handler. If a Telnyx API call fails (e.g., caller already hung up, network error), log the error but still return 200 to Telnyx. Returning non-200 causes Telnyx to retry the webhook, which could lead to duplicate processing. The `call_control_id` is extracted from the webhook event payload `data.payload.call_control_id`, not from client_state.

### All telnyx_auth Command Helpers Are Async

All `_telnyx_command` and its wrappers (`telnyx_answer`, `telnyx_gather_speak`, etc.) must be `async` functions since they make HTTP POST calls to the Telnyx API using httpx.
