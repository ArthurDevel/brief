# WhatsApp xAI Voice Providers Plan

Short summary: add a small voice provider layer to `apps/whatsapp-agent` so WhatsApp calls can switch STT and TTS between Deepgram and xAI while keeping shared WhatsApp audio post-processing.

## Goal

Support a clean provider race between Deepgram and xAI for the WhatsApp voice agent:

- switch live-call speech-to-text between Deepgram and xAI
- switch live-call text-to-speech between Deepgram and xAI
- keep the same WhatsApp TTS post-processing for both providers
- keep provider-specific logic isolated and easy to remove or change
- avoid cluttering `apps/whatsapp-agent/src/lib`

## Important Plan Maintenance Instructions

- After each phase, check the completed boxes in this plan.
- When new findings pop up during implementation, add them to this plan before moving on.
- If provider docs or LiveKit APIs differ from this plan, update the findings and adjust the phase steps before coding the affected part.

## Target Responsibilities

### `voice/factory.ts`

- Public entrypoint for the voice provider subsystem.
- Export `createWhatsAppStt(env)` and `createWhatsAppTts(env, voiceConfig)`.
- Select the configured provider with a simple `switch`.
- Keep `agent.ts` free of provider-specific imports.

### `voice/types.ts`

- Define provider names and DTOs.
- Define supported voice IDs and defaults.
- Validate provider names, voice IDs, and speed.
- Own the persisted voice config shape currently handled by `whatsappVoice.ts`.

### `voice/postprocessor.ts`

- Provide the shared WhatsApp TTS post-processing helper.
- Wrap existing audio helpers from `lib/audio`.
- Ensure Deepgram and xAI TTS use the same speed and normalization behavior.

### `voice/providers/deepgram.ts`

- Create the Deepgram STT config or instance.
- Own the Deepgram TTS adapter.
- Move or adapt the current `processedDeepgramTts.ts` here.
- Keep all Deepgram-specific imports and model details in this file.

### `voice/providers/xai.ts`

- Create the xAI STT config or instance.
- Own the xAI TTS adapter.
- Call xAI TTS directly if needed so the same post-processing can be applied.
- Keep all xAI-specific imports, API calls, model IDs, and voice IDs in this file.

## Tradeoffs And Technical Implications

### Why a `voice/` folder

Decision:

- Put the provider layer under `apps/whatsapp-agent/src/lib/voice`.

Why:

- `lib` already contains unrelated app concerns.
- STT/TTS provider selection, voice settings, and audio post-processing are one subsystem.
- Future agents can find the full voice provider stack without scanning root-level `lib` files.

### Why `factory.ts`

Decision:

- Use `factory.ts` instead of `client.ts`.

Why:

- This module creates provider instances.
- It is not an HTTP client and should not sound like one.
- The name makes `createWhatsAppStt` and `createWhatsAppTts` obvious.

### Why provider files for both Deepgram and xAI

Decision:

- Use `providers/deepgram.ts` and `providers/xai.ts`.

Why:

- Both providers need provider-specific TTS behavior.
- xAI must use the same WhatsApp TTS post-processing as Deepgram.
- Symmetric files make the provider race easier to reason about.

### Why no separate `xaiClient.ts` yet

Decision:

- Keep xAI API calls inside `providers/xai.ts` for the first implementation.

Why:

- There is only one current xAI consumer.
- Splitting a tiny HTTP helper out now would add indirection.
- If xAI TTS code becomes large or gets reused, split it later.

### LiveKit Inference vs direct provider APIs

Finding:

- LiveKit docs show xAI STT support in Node.js through both LiveKit Inference and `@livekit/agents-plugin-xai`.
- LiveKit docs show xAI TTS through LiveKit Inference for Node.js.
- However, plain LiveKit Inference TTS would not run our custom WhatsApp post-processing.

Implication:

- STT can use LiveKit's xAI integration.
- TTS should use a custom xAI adapter if we require the same post-processing as Deepgram.
- This means `XAI_API_KEY` is needed for direct xAI TTS unless a later LiveKit hook allows post-processing inference audio.

Implementation finding:

- The implementation uses LiveKit STT model descriptors for both Deepgram and xAI.
- No `@livekit/agents-plugin-xai` dependency was added in this pass.
- The implementation uses direct xAI TTS calls in `providers/xai.ts` so PCM can pass through shared post-processing before LiveKit playback.
- If the selected global TTS provider differs from a caller's stored voice provider, the factory uses the selected provider's configured default voice and preserves the stored speed.

### Voice-message transcription is separate

Finding:

- Live-call STT is in `apps/whatsapp-agent`.
- WhatsApp voice-message transcription is in `apps/whatsapp-server/src/deepgramVoiceMessageTranscriber.ts`.

Implication:

- This plan only covers live WhatsApp calls.
- If the user wants voice notes switched to xAI too, create a separate server-side transcriber provider plan or phase.

## Proposed Env

Keep app-wide env loading in `apps/whatsapp-agent/src/lib/env.ts`, but keep voice-specific interpretation inside `lib/voice`.

Suggested variables:

```text
WHATSAPP_STT_PROVIDER=deepgram
WHATSAPP_TTS_PROVIDER=deepgram

WHATSAPP_DEEPGRAM_STT_MODEL=deepgram/nova-3:en
WHATSAPP_XAI_STT_MODEL=xai/stt-1:en

WHATSAPP_DEFAULT_DEEPGRAM_VOICE=aura-2-andromeda-en
WHATSAPP_DEFAULT_XAI_VOICE=ara

XAI_API_KEY=
DEEPGRAM_API_KEY=
```

Notes:

- `DEEPGRAM_API_KEY` is required when Deepgram STT or TTS is selected.
- `XAI_API_KEY` is required when direct xAI TTS is selected.
- If xAI STT uses LiveKit Inference, it may not need `XAI_API_KEY`; document the final choice during implementation.
