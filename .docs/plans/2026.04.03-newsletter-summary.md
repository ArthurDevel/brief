# Newsletter Summary Feature

## High-Level Goal

Allow users to opt in to daily newsletter summaries. A background job runs once per day and generates an LLM-powered summary of all newsletters received that day, per opted-in user. When the user calls in, they can ask for their newsletter summary and hear yesterday's digest read aloud. The system tracks whether each summary has been listened to so the voice assistant can proactively mention unheard summaries.

Key design decisions:
- Summaries are generated **per day** (one summary per user per calendar day)
- Calling today returns **yesterday's** summary (today is still in progress)
- The background job only processes users who have **enabled** the newsletter feature
- Each summary tracks a **listened** flag so the assistant knows whether to mention it

## Important Technical Notes

### IMAP search for newsletters by sender + date

The existing `search_emails` function uses `translate_query` which supports `from:` and `after:`/`before:` operators. However, for the newsletter job we need to search for emails from **multiple senders** on a **specific date**. IMAP does not support `ON` + `OR(FROM ...)` in a single query on all servers.

The approach: run one IMAP search per configured sender address using `["FROM", sender, "ON", target_date]` criteria, then merge and deduplicate results by UID. This is simple and reliable across all IMAP providers. The number of searches equals the number of configured newsletter senders (typically 1-10), which is acceptable.

Note: the `target_date` must be formatted as an IMAP date string (e.g., `datetime.date` object -- imapclient handles the formatting). The `ON` keyword matches the internal date (when the server received the email), not the `Date` header. This is fine for newsletters which are typically received promptly.

### IMAP connection management in the background job

The background job creates its own IMAP connections per user (not reusing session connections). It constructs an `imap_holder` dict and uses the existing `with_reconnect` wrapper for resilience, same pattern as the voice pipeline. Each user's connection is opened, used for all sender searches, then closed.

### LLM summarization call

The newsletter summary uses a **separate LLM call** (not the voice pipeline's conversation LLM). It calls OpenRouter directly via `aiohttp` using the existing `OPENROUTER_API_KEY`. The model is set via the `NEWSLETTER_LLM_MODEL` constant in `config.py` (default: same as `LLM_MODEL`; changing it requires a code change).

The **system prompt** for summarization lives as a constant `SUMMARY_SYSTEM_PROMPT` in `newsletter.py`. It instructs the model to summarize the newsletter emails concisely. The user's `summary_prompt` from their config is appended as additional instructions (e.g., "focus on AI news", "keep it under 2 minutes when read aloud").

The `generate_summary` function is `async` (uses `aiohttp`). The `run_daily_newsletter_job` function is also `async` and is awaited from the FastAPI endpoint handler.

### Langfuse observability

Each LLM summarization call is logged to Langfuse using the Python SDK directly (not the Pipecat observer, which is for voice pipeline frames). The existing `src/langfuse_client.py` provides the Langfuse client. Each call to `generate_summary` creates a Langfuse trace (with `user_id` and `name: "newsletter-summary"`) containing a generation span with input messages, output text, model, and token usage. This gives visibility into newsletter summarization costs and quality alongside voice call traces.

### Daily scheduler integration

Rather than adding a second asyncio scheduler loop, the newsletter job is exposed as an HTTP endpoint `POST /api/newsletter/generate-daily` (protected by `INTERNAL_API_KEY`). This endpoint is called by a cron trigger (external scheduler, Supabase pg_cron, or the existing scheduler loop). The existing `_scheduler_loop` in `scheduler.py` is extended to also trigger newsletter generation once per day (at a configurable hour, default 06:00 UTC), reusing the same dedup pattern (`last_newsletter_run` timestamp).

### Upsert for idempotency

The `newsletter_summaries` table has a unique constraint on `(user_id, summary_date)`. The insert uses Supabase's `.upsert()` method (which generates `ON CONFLICT ... DO UPDATE`) so re-running the job for the same date overwrites rather than duplicates. This makes the endpoint safe to call multiple times.

### Timezone handling for "yesterday"

"Yesterday" is determined per-user using their timezone, derived from `phone.countryCode` in `user_settings`. The mapping uses a simple country-to-timezone lookup (e.g., `"BE"` -> `"Europe/Brussels"`, `"US"` -> `"America/New_York"`). For countries with multiple timezones (US, AU, etc.) a sensible default is chosen. This is imprecise but good enough for determining which calendar day is "yesterday."

The background job computes each user's local "yesterday" date and uses that as `target_date` for the IMAP search and `summary_date` for the DB row. The `get_newsletter_summary` tool also uses the user's timezone to determine which `summary_date` to query.

**Future improvement:** A standalone `timezone` field on `user_settings` (set explicitly by the user in the dashboard) would replace the country-code derivation. This is tracked in ArthurDevel/brief#129.

### Null handling for `set_newsletter_config`

When `newsletter_config` is currently `null` in `user_settings` (the default for existing users), the handler initializes a base object `{ enabled: false, newsletters: [], summary_prompt: null }` before merging the provided args. This prevents null-reference errors during the read-merge-write cycle.

### API key wiring

The HTTP endpoint in `server.py` calls `await run_daily_newsletter_job(supabase, settings.openrouter_api_key)`, sourcing the OpenRouter API key from the Settings object. This is passed through to `generate_daily_summary_for_user` and then to `generate_summary`.

### Scheduler dedup state

The `last_newsletter_run` timestamp is stored **in-memory** in the scheduler loop (not in the database). If the process restarts, the newsletter job may re-run for today, but the upsert makes this safe. This avoids adding DB state for a global singleton timer.

### Per-user error handling in the background job

`run_daily_newsletter_job` wraps each user's `generate_daily_summary_for_user` call in a try/except, logs the error, and continues to the next user. This matches the existing scheduler pattern in `scheduler.py` (lines 354-357). One user's IMAP or LLM failure does not block others.

## Per-File Methods and Types/DTOs

### 016_newsletter_summaries.sql (NEW)

Adds `newsletter_config` JSONB column to `user_settings` and creates the `newsletter_summaries` table.

```
newsletter_config JSONB on user_settings:
{
  enabled: boolean
  newsletters: string[]          -- sender email addresses to track
  summary_prompt: string | null  -- custom instructions for the LLM
}

newsletter_summaries table:
  id: uuid (PK)
  user_id: uuid (FK -> auth.users)
  summary_date: date
  summary: text
  email_count: integer
  listened: boolean (default false)
  listened_at: timestamptz | null
  created_at: timestamptz
  UNIQUE(user_id, summary_date)
```

RLS policies: users can SELECT and UPDATE their own rows. INSERT/DELETE reserved for service role (background job).

### newsletter.py (NEW)

Newsletter summary background job. Fetches newsletters via IMAP for each opted-in user, generates an LLM summary, and stores it in the database.

#### Types

```
NewsletterConfig {
  enabled: bool
  newsletters: list[str]         -- sender email addresses
  summary_prompt: str | None     -- custom LLM instructions
}

NewsletterEmail {
  subject: str
  body: str
  from_addr: str
  date: str
}

OptedInUser {
  user_id: str
  imap_config: ImapConfig
  newsletter_config: NewsletterConfig
  country_code: str              -- from phone.countryCode, used for timezone derivation
}
```

#### Methods

| Method | Arguments | Returns | Description |
|--------|-----------|---------|-------------|
| `get_opted_in_users` | `supabase: Client` | `list[OptedInUser]` | Query user_settings for users with newsletter_config.enabled = true and valid IMAP credentials. Retrieves IMAP passwords from Vault. Also reads phone.countryCode for timezone derivation. |
| `country_code_to_timezone` | `country_code: str` | `str` | Map a country code (e.g., "BE", "US") to a default IANA timezone string (e.g., "Europe/Brussels", "America/New_York"). Falls back to "UTC" for unknown codes. |
| `fetch_newsletters_for_date` | `imap_config: ImapConfig, senders: list[str], target_date: date` | `list[NewsletterEmail]` | Connect to IMAP, search for emails from each sender on the target date, merge and deduplicate results by UID. Returns subject + body for each email. Uses `with_reconnect` wrapper via an `imap_holder` dict. |
| `generate_summary` | `email_bodies: list[str], summary_prompt: str \| None, api_key: str, user_id: str` | `str` | (async) Call OpenRouter LLM via aiohttp with the email bodies and user's custom prompt. Logs the generation to Langfuse. Returns the summary text. |
| `generate_daily_summary_for_user` | `user: OptedInUser, target_date: date, api_key: str, supabase: Client` | `str \| None` | (async) Orchestrates the full flow for one user: fetch newsletters, generate summary if any found, upsert into newsletter_summaries. Returns the summary or None if no newsletters. |
| `run_daily_newsletter_job` | `supabase: Client, api_key: str` | `int` | (async) Top-level entry point called by the HTTP endpoint. Gets opted-in users, runs generate_daily_summary_for_user for each, returns count of summaries generated. |
