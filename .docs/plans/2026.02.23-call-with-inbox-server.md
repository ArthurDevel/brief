# Plan: Call With My Inbox - Voice AI Server

## High Level Goal

Build a voice AI server where users phone in via Twilio, have a streaming voice conversation with an AI assistant, and the AI can interact with their email inbox over IMAP through a CLI tool. The server handles the full audio pipeline: Twilio (mulaw/8kHz) -> ElevenLabs STT -> LLM (via OpenRouter) -> ElevenLabs TTS -> back to Twilio. No audio conversion needed -- ElevenLabs supports `ulaw_8000` natively in both directions.

```
Phone -> Twilio (mulaw WebSocket) -> ElevenLabs STT (ulaw_8000) -> transcript text
                                                                        |
                                                                        v
Phone <- Twilio (mulaw WebSocket) <- ElevenLabs TTS (ulaw_8000) <- LLM (OpenRouter, streaming)
                                                                        |
                                                                        v (tool calls)
                                                                   IMAP CLI (child process)
```

## Important Technical Notes

### Sentence-Level TTS Buffering

The LLM streams tokens one at a time. Sending each token individually to TTS produces choppy speech. Instead, buffer tokens in `LlmOrchestrator` until a sentence boundary is detected (`.`, `!`, `?`, `\n`). Send each complete sentence to `TtsService.sendText()`. This produces natural speech cadence. Call `TtsService.flush()` after the final sentence to ensure nothing is left in the buffer.

### Tool Call Streaming Accumulation

OpenRouter streams tool calls as partial JSON fragments across multiple SSE chunks. The `tool_call_delta` chunks contain incremental `arguments` strings that must be concatenated. A tool call is only complete when `finish_reason: "tool_calls"` is received. At that point, parse the accumulated arguments JSON and dispatch the tool call. During accumulation, also collect any text content that preceded the tool call (the narration).

### Barge-In Handling

Track an `isSpeaking` boolean on the session. Set to `true` when first TTS audio chunk is sent to Twilio. After the last audio chunk of an utterance (triggered by `TtsService.onUtteranceEnd`), send a `mark` message to Twilio via `sendMark()`. Twilio echoes the `mark` event back when playback finishes -- set `isSpeaking = false` at that point.

If `SttService` fires a partial transcript while `isSpeaking` is `true`:
1. Send `clear` event to Twilio (stops playback immediately)
2. Call `TtsService.interrupt()` (closes the TTS WebSocket)
3. Call `LlmOrchestrator.cancelCurrent()` to abort any in-progress LLM stream
4. Set `isSpeaking = false`
5. The STT continues and will commit the user's new utterance normally

Note: the server must send a `mark` message to Twilio for the `mark` event to fire back. Without this, `isSpeaking` would never reset.

### Utterance Serialization

`LlmOrchestrator.handleUserUtterance` must be serialized -- only one utterance processes at a time. If a new utterance arrives while one is in progress (e.g., after barge-in cancels the current one), it queues and processes next. Simple approach: maintain a promise chain or async mutex.

### Shared LLM-to-TTS Streaming Logic

Both `handleUserUtterance` and `handleToolCalls` need the same logic: stream LLM tokens, buffer until sentence boundary, send to TTS, flush at end, call `endUtterance`. Extract this into a private helper (e.g., `streamLlmResponseToTts`) to avoid duplication.

### Phone Number Passing from TwiML to WebSocket

The caller's phone number is available in the HTTP POST to `/twiml` but not directly in the WebSocket `start` event. Solution: the `/twiml` route stores `{ callSid: phoneNumber }` in an in-memory `Map`. The TwiML response includes the `CallSid`. When the WebSocket receives the `start` event (which contains the `callSid`), it reads the phone number from the map and deletes the entry.

### STT Reconnection

The ElevenLabs STT WebSocket may drop during long silences (e.g., while LLM processes a tool call). `SttService` should handle `close` and `error` events: on unexpected disconnect, attempt a single reconnect. If reconnect fails, log the error and let the call degrade gracefully.

### Greeting

On call start, send a hardcoded greeting directly to TTS (e.g., "Hi {displayName}, what would you like to do with your inbox?"). This avoids an LLM round-trip for the first utterance and keeps the greeting instant. The greeting must also be appended to `LlmOrchestrator.messages` as an assistant message so the LLM has context for the user's first reply.

### IMAP Credentials via CLI Args

For the MVP, IMAP credentials are passed as CLI arguments to the child process. Note: CLI args are visible in `ps` output. Acceptable for single-tenant/local development. Future improvement: pass via env vars on the child process instead.

### TTS WebSocket Lifecycle

Open a fresh ElevenLabs TTS WebSocket per assistant utterance rather than keeping one open for the full call. Benefits:
- Interruption is trivial (close the socket)
- Avoids ElevenLabs' 20-second inactivity timeout
- Connection overhead (~50ms) is negligible in voice conversation context

## Success Criteria

1. Server starts without errors and connects to all external services
2. Incoming Twilio call triggers WebSocket connection and plays greeting
3. User speech is transcribed via ElevenLabs STT with low latency
4. LLM responds conversationally via OpenRouter, streamed to TTS sentence-by-sentence
5. Tool calls (list, search, read, archive, draft, flag) execute correctly via IMAP CLI
6. LLM narrates tool calls before executing them ("Let me check your inbox...")
7. Sliding window context keeps only last 6 messages + system prompt
8. Transcript file is written to `transcripts/<userId>/<callSid>.md` with all messages and tool calls
9. Barge-in interrupts TTS playback and processes new user utterance
10. `transcript_search` tool allows LLM to grep earlier conversation context
