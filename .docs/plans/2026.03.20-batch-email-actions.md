# Batch Email Actions (Archive / Delete)

## High-Level Goal

Add two new tools -- `batch_archive_emails` and `batch_delete_emails` -- that allow the voice assistant to archive or delete multiple emails in a single tool call. Both tools accept an array of email IDs, then **fan out into individual action rows** -- one per email -- each with its own standard `move_email` undo recipe. Every email appears as a separate entry in the dashboard and is individually undoable.

No changes to the email package. No new undo operation type. The batch tools are thin orchestration on top of the existing single-email pipeline.

Returns an `ActionResult` with `result.total: 2, result.succeeded: 2, result.failed: 0`. Uses `handleToolCall` from `action-queue.ts`, verified via `listInbox` from `@dublin/email` and inspecting the fake Supabase store.

- **[integration]** Batch archive undo recipes contain stable Message-ID: after a batch archive, each action row's `undo_recipe.params.messageId` contains the RFC Message-ID from the original email (e.g. `<batch-msg-001@example.com>`). This ID is what allows the undo to locate the email after it has been moved (UIDs change across folders, Message-ID does not). Uses `handleToolCall` from `action-queue.ts`, verified by inspecting each action row's `undo_recipe` in the fake Supabase store against the seed data's `Message-Id` headers.

- **[integration]** Batch archive individual undo: after a batch archive of 2 emails, calling `undoAction` on one of the returned `actionIds` restores only that email to inbox. The other remains archived. Uses `handleToolCall` + `undoAction` from `action-queue.ts`, verified via `listInbox`.

- **[integration]** Batch delete queues individual actions: calling `handleToolCall` with `batch_delete_emails` and 2 email IDs creates 2 pending `delete_email` action rows in the store. No emails are moved. Returns summary with `result.total: 2`. Uses `handleToolCall` from `action-queue.ts`, verified by inspecting the fake Supabase store for `status: "pending"`.

- **[integration]** Empty email_ids array: calling `batch_archive_emails` with `[]` returns result with `total: 0, succeeded: 0, failed: 0` and empty `actionIds`. No DB rows created. Uses `handleToolCall` from `action-queue.ts`.

- **[unit]** Classification: `classifyAction("batch_archive_emails", {})` returns `"mutating_auto"`, `classifyAction("batch_delete_emails", {})` returns `"mutating_queued"`.

## Important Technical Notes

### Fan-out strategy in handleToolCall

`handleToolCall` intercepts batch tools **before** the normal classify/dispatch flow. For each `email_id` in the array:

- **batch_archive_emails** (mutating_auto): calls the existing `executeAndStore` with a synthetic `ActionInput` where `toolName="archive_email"` and `arguments={ email_id, source_folder }`. Each call creates an individual DB row with a `move_email` undo recipe.
- **batch_delete_emails** (mutating_queued): calls the existing `insertPendingAction` with a synthetic `ActionInput` where `toolName="delete_email"` and `arguments={ email_id, source_folder }`. Each call creates a pending DB row.

Errors on individual emails are caught and counted but do not abort the batch.

### IMAP concurrency: strictly sequential

ImapFlow supports only one operation at a time per connection (each email operation acquires a mailbox lock via `client.getMailboxLock()`). The fan-out loop must process emails **sequentially** -- no `Promise.all` / `asyncio.gather`. Each iteration waits for `executeAndStore` to complete (which internally acquires the lock, moves the email, stores the DB row, and releases the lock) before starting the next one.

**Performance:** ~500ms per email (4 IMAP round-trips + DB insert). 20 emails takes ~10 seconds. Acceptable for now; can be optimized later with batch IMAP commands (single FETCH + single MOVE) if needed.

### Fresh ActionInput per email (critical for Python)

Each loop iteration must construct a **new** `ActionInput` with a **fresh** `arguments` dict. In the Python voice pipeline, `_execute_and_store` mutates `input.arguments` in-place (line 342: `input.arguments["message_id"] = message_id`). If the batch handler reuses the same dict across iterations, the `message_id` from one email will leak into subsequent DB rows. Construct a new dict per email:

```python
for email_id in email_ids:
    individual_input = ActionInput(
        user_id=input.user_id,
        session_id=input.session_id,
        tool_name="archive_email",
        arguments={"email_id": email_id, "source_folder": source_folder},  # fresh dict
    )
```

The TS `executeAndStore` does not mutate arguments, but follow the same pattern for consistency.

### No new return type

`handleToolCall` keeps its existing `ActionResult` return type. For batch tools, the return value is:

```
{
  actionId: <first successful action's ID, or "" if all failed>,
  status: "executed" | "pending",
  result: {
    total: number,
    succeeded: number,
    failed: number,
    errors: string[],
    actionIds: string[]     // all created action IDs
  },
  message: "Archived 3 emails (3 succeeded, 0 failed)"
}
```

This avoids a breaking change to the return type. The voice assistant reads `result` for counts. The `actionIds` array lets any caller enumerate the individual actions if needed.

### Python voice pipeline mirrors TS changes

The Python `handlers.py` has its own `handle_tool_call` that mirrors `action-queue.ts`. Both need the same batch fan-out logic. The Python version calls `_execute_and_store` / `_insert_pending_action` per email, just like the TS version.

### ToolDefinition property type update

The TS `ToolDefinition` interface property type is `Record<string, { type: string; description: string }>`. For array parameters (`email_ids: string[]`), the JSON Schema requires `{ type: "array", items: { type: "string" } }`. The property type in `ToolDefinition` must be updated to include an optional `items` field:

```ts
Record<string, { type: string; description: string; items?: { type: string } }>
```

The Python `definitions.py` uses raw dicts, so no type change needed there.

### source_folder defaults to INBOX

Neither the single-email nor batch tool schemas expose `source_folder` as a parameter. The fan-out logic defaults to `"INBOX"`, consistent with the existing single-email tools.

## Success Criteria

- `batch_archive_emails` with N email IDs creates N individual `archive_email` action rows, each with its own `move_email` undo recipe
- `batch_delete_emails` with N email IDs creates N individual pending `delete_email` action rows
- Each action row is independently undoable from the dashboard
- If one email in a batch fails, the others still process
- Empty `email_ids` array returns cleanly with no errors and no DB rows
- Voice assistant receives a summary with `total`, `succeeded`, `failed` counts in the `result` field
- Return type of `handleToolCall` / `handle_tool_call` is unchanged (`ActionResult`)
- Classification matches single-email counterparts (archive = auto, delete = queued)
- No changes to `packages/email/` -- reuses existing single-email functions
- No new undo operation type -- reuses `move_email`
- All existing tests continue to pass
- New integration tests pass against Hoodiecrow in isolated server instances
