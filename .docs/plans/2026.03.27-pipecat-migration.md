# Pipecat Migration: Replace Custom Code with Built-in Framework Components

## High-Level Goal

Refactor the voice pipeline to use pipecat's built-in components instead of our custom implementations. This follows the patterns validated in `testscripts/2026.03.27-builtin-twilio-transport/test_builtin_twilio.py`. The result is less custom code, better audio quality (SOXR resampling), native turn detection (Flux), and alignment with pipecat idioms.

## Important Technical Notes

### Framework Gaps (must preserve workarounds)

1. **Gap #1: Tool call error handling is broken (pipecat v0.0.107).** If a handler raises, pipecat never calls `result_callback`, freezing the pipeline. Every handler MUST catch its own errors and return them via `result_callback`. Do not rely on pipecat's error handling.

2. **Gap #2: Instant tool handlers cause race condition.** `FunctionCallResultFrame` can arrive before `FunctionCallsStartedFrame`. Our IMAP handlers are not affected (always do blocking I/O), but if any fast/cached handler is added in the future, it needs `await asyncio.sleep(0)` at the start.

3. **Gap #3: TTSSpeakFrame in on_function_calls_started breaks TTS.** Do not use `tts.queue_frame(TTSSpeakFrame(...))` during function calls. Keep the HTTP TTS narration approach (Deepgram REST API).

4. **STT cleanup hack still needed with Flux.** `cancel_stt_tasks()` must be updated to accept `DeepgramFluxSTTService` and add a `hasattr(stt, "_task_manager")` guard (the test script has this, production currently doesn't). Without the `hasattr` guard, an `AttributeError` could be raised if pipecat changes internals.

### Twilio Sample Rate Change

Current pipeline runs Twilio at 16kHz (custom transport upsamples from 8kHz). New pipeline runs Twilio at 8kHz natively (TwilioFrameSerializer handles mulaw<->PCM16 at 8kHz via SOXR). This changes `TWILIO_PIPELINE_SAMPLE_RATE` from `16000` to `8000` in server.py. Flux STT and all processors (speed, normalizer, TTS) work at 8kHz.

**Important:** `_setup_pipeline_session` currently hardcodes `audio_config["sample_rate"]` to `16000`. After migration, it must pass `8000` for Twilio and `16000` for WebRTC. The `transport_type` parameter already exists -- use it to derive the sample rate.

### WebRTC Turn Detection After SmartTurn Removal

SmartTurn v3 + SileroVAD is removed for both paths. Flux STT handles turn detection natively. The test script validates this at 8kHz (Twilio). Flux at 16kHz (WebRTC) should work equally well or better since Flux's native sample rate is 16kHz. However, this should be validated manually after deployment -- if turn detection quality degrades on WebRTC, SmartTurn can be re-added as a `UserTurnStopStrategy` alongside Flux.

### Keep asyncio.wait_for() Inside the Lock

The `timeout_secs` on `register_function()` starts counting when pipecat invokes the handler, including time spent waiting for `imap_lock`. If two tool calls arrive concurrently, the second waits for the lock and pipecat's timeout may fire before the actual IMAP work starts. When pipecat's timeout fires, it does NOT call `result_callback` (Framework Gap #1 territory), freezing the pipeline.

**Solution:** Keep `asyncio.wait_for()` around the `asyncio.to_thread()` call INSIDE the lock (same as current code). Set `timeout_secs` on `register_function()` to a higher value (e.g., `20.0`) as a safety net only. The manual `asyncio.wait_for(timeout=TOOL_CALL_TIMEOUT_SECS)` remains the primary timeout mechanism.

### Import Paths (validated in test script)

Use these exact paths (from the test script, not the review doc):
- `from pipecat.processors.aggregators.llm_context import LLMContext`
- `from pipecat.services.llm_service import FunctionCallParams`
- `from pipecat.services.deepgram.flux.stt import DeepgramFluxSTTService`

### Narration HTTP Session Pattern

The production code uses `dict[str, aiohttp.ClientSession | None]` (mutable dict wrapper) because `create_pipeline` is sync and closures cannot reassign outer variables. The test script uses `nonlocal` (works because `twilio_stream` is async). Keep the dict pattern in production. `_synthesize_narration`'s signature stays as `dict[str, ...]`, not the bare `ClientSession` from the test script.

### AudioBufferProcessor Recording Flow

```
on_client_connected  -->  audio_buffer.start_recording()
pipeline runs...     -->  AudioBufferProcessor captures user/bot tracks
CancelFrame/EndFrame -->  AudioBufferProcessor auto-stops, fires events:
                          on_audio_data    -> _write_wav + upload_recording (merged)
                          on_track_audio_data -> optional separate tracks
```

The upload happens inside event handlers registered in `create_pipeline`. No manual combine/upload step needed in `_cleanup_session`.

### Narration HTTP Session Lifecycle

Created lazily on first tool call narration. Must be closed after pipeline ends. `PipelineResult` includes the session reference so `server.py` can close it in the `finally` block.

#### Key Changes in `create_pipeline`

- `DeepgramSTTService` -> `DeepgramFluxSTTService` (no `audio_passthrough` needed)
- `OpenAILLMContext` -> `LLMContext`
- Remove SmartTurn/SileroVAD branching. Use `LLMContextAggregatorPair(context)` for all sample rates.
- `MarkdownStripperProcessor` removed from chain -> `MarkdownTextFilter()` passed to `DeepgramTTSService(text_filter=...)`
- `AudioFrameWatchdog` -> `IdleFrameProcessor(callback=on_audio_idle, timeout=AUDIO_IDLE_TIMEOUT_SECS, types=[InputAudioRawFrame])`
- `AudioRecorder` pair removed -> `AudioBufferProcessor` added after `transport.output()` (conditionally, if recording enabled)
- `allow_interruptions=True` removed from `PipelineParams` (Flux manages turns)
- `enable_usage_metrics=True` MUST be preserved in `PipelineParams` (required by TrackedOpenAILLMService and TrackedDeepgramTTSService)
- `audio_in_sample_rate` and `audio_out_sample_rate` MUST be preserved in `PipelineParams`
- Pipeline chain: `transport.input() -> watchdog -> stt -> user_agg -> llm -> tts -> speed -> normalizer -> transport.output() -> [audio_buffer] -> assistant_agg`

#### Key Changes in `_register_tool_handler`

```python
# Old signature
async def handler(function_name, tool_call_id, args, llm_instance, context, result_callback):

# New signature
async def handler(params: FunctionCallParams):
    tool_name = params.function_name
    arguments = params.arguments
    # ... same logic, including asyncio.wait_for() inside the lock ...
    await params.result_callback(result_str)

# Old registration
llm.register_function(tool_name, handler)

# New registration -- 20s safety net, manual timeout remains primary
REGISTER_FUNCTION_TIMEOUT_SECS = 20.0
llm.register_function(tool_name, handler, timeout_secs=REGISTER_FUNCTION_TIMEOUT_SECS)
```

The handler signature changes to `FunctionCallParams` but the internal logic stays the same: `asyncio.wait_for(timeout=TOOL_CALL_TIMEOUT_SECS)` around `asyncio.to_thread()` inside the lock. The `timeout_secs=20.0` on `register_function()` is a safety net only (accounts for lock wait + IMAP timeout). See "Keep asyncio.wait_for() Inside the Lock" in Technical Notes.
