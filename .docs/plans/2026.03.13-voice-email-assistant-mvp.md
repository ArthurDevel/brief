# Voice Email Assistant -- MVP Implementation Plan

## High-Level Goal

Build a working voice email assistant where users call a phone number, authenticate via caller ID, and use voice to manage their email inbox (list, read, draft, archive, delete, send). A Next.js dashboard lets users configure settings, approve/undo actions, and review call history. Supabase handles auth + database, Twilio handles telephony, OpenAI Realtime API powers the voice AI.

Billing is out of scope for MVP -- hardcode generous limits.

Descoped for MVP: `search_emails` tool, `mark_as_read` tool, action expiration (pending actions stay pending until manually rejected). These are noted in the architecture doc but intentionally excluded from MVP.

## Important Technical Notes

### Twilio Media Streams Audio Transcoding

Twilio Media Streams sends audio as mulaw 8kHz over WebSocket. OpenAI expects PCM16 24kHz. The `audio-transcoder.ts` module handles bidirectional conversion:

```
Twilio (mulaw 8kHz) --> decode mulaw --> resample 8kHz -> 24kHz --> encode PCM16 --> OpenAI
OpenAI (PCM16 24kHz) --> resample 24kHz -> 8kHz --> encode mulaw --> Twilio
```

Resampling uses linear interpolation (simple, sufficient for voice). Use the `mu-law` npm package for mulaw encoding/decoding.

### Delete = Move to Trash (Not Permanent)

`deleteEmail` moves messages to the Trash folder instead of STORE \Deleted + EXPUNGE. This makes undo reliable -- just move back from Trash to INBOX. Permanent deletion happens naturally when the email provider empties Trash (typically 30 days).

### Undo Recipe System

Each action handler returns an `UndoRecipe | null` when it executes. The recipe is a serializable description of how to reverse the action, stored in the `undo_recipe` jsonb column on the action row. If null, the action is not undoable (e.g. send_email).

When `undoAction` is called, it reads the recipe from the DB, checks the deadline, and dispatches:

```
undo_recipe.operation     →  what happens
─────────────────────────────────────────
"move_email"              →  IMAP MOVE email between folders (params: emailId, from, to)
"delete_draft"            →  IMAP DELETE draft by UID (params: draftUid)
"restore_memory"          →  DB update memory entry to previous value (params: key, previousValue)
"delete_memory"           →  DB delete memory entry (params: key)
```

Undo deadlines per action type:
- `archive_email`: 30 seconds (auto-execute, quick undo window)
- `delete_email`: 30 seconds (same)
- `draft_email`: null (undoable indefinitely -- draft just sits there)
- `save_memory`: null (undoable indefinitely)
- `send_email`: null recipe (not undoable at all)

The `sourceFolder` parameter on `archiveEmail` and `deleteEmail` captures where the email was before the move, so undo puts it back in the right place (not always INBOX -- could be a label or subfolder).

Adding a new undoable tool in the future only requires: return the right `UndoRecipe` from its handler and add the operation to the undo dispatcher switch.

### IMAP Connection Lifecycle

One IMAP connection per phone call session. Opened when the call starts (after caller ID lookup), kept alive for the duration, closed on disconnect. This avoids reconnection latency during rapid tool calls. The `ImapFlow` instance is passed to `packages/tools.handleToolCall` directly.

For dashboard-triggered actions (approve from web), a new IMAP connection is opened per action execution since there is no persistent session.

### Dashboard Approvals During Active Calls

If a user approves a pending action from the dashboard while the voice call is still active, the model will not know about it. This is acceptable for MVP. The user can ask "did it send?" and the model can check by calling a tool. A future version could use Supabase Realtime subscriptions to push approval notifications to the voice gateway.

### Caller Authentication (Caller ID + DTMF PIN)

Two-step authentication on every call:

1. **Caller ID lookup** -- Twilio webhook includes caller's phone number. Look up in `user_settings.phone_number` to find the account. If no match, play "please register" and hang up.
2. **DTMF PIN verification** -- User sets a 4-6 digit PIN in the dashboard settings. On call, after caller ID match, Twilio `<Gather>` prompts "Please enter your PIN". User enters digits via keypad. If correct, connect to AI assistant. If wrong after 3 attempts, hang up.

TwiML flow:
```
<Response>
  <Gather numDigits="6" action="/twilio/verify-pin?userId=xxx" method="POST">
    <Say>Please enter your pin.</Say>
  </Gather>
  <Say>No input received. Goodbye.</Say>
</Response>
```

The `/twilio/verify-pin` endpoint checks the PIN against the hashed value in DB. On success, resets `pin_attempts` to 0 and returns TwiML with `<Stream>` to start the media stream. On failure, increments `pin_attempts` and returns another `<Gather>` for retry.

After 3 failed attempts:
- Set `pin_locked: true` in `user_settings`. Voice access is blocked until the user sets a new PIN.
- Send an SMS via Twilio to the user's phone: "Someone failed to access your voice email assistant 3 times. Your account has been locked. Set a new PIN: [dashboard URL]/dashboard/settings"
- Send an email via the user's SMTP config (or a system email) with the same message.
- On any subsequent call while locked, play "Your account is locked. Please set a new PIN in your dashboard." and hang up.
- User must set a new PIN in dashboard settings (or via the link in the SMS/email) to unlock. Setting a new PIN resets `pin_locked` to false and `pin_attempts` to 0.

DB columns on `user_settings`:
- `pin_hash: text` -- bcrypt hash of 4-6 digit PIN
- `pin_attempts: int (default 0)` -- failed attempts since last successful auth
- `pin_locked: boolean (default false)` -- locked until user sets a new PIN

The dashboard settings page has a "Set PIN" field. The PIN section shows a warning if the account is locked.

### IMAP Credential Validation

The PUT /api/user/settings endpoint attempts a test IMAP connection before saving credentials. If the connection fails, the settings are not saved and an error is returned. This prevents users from entering invalid credentials and then getting opaque errors on every call.

### ENCRYPTION_KEY Deployment

The same `ENCRYPTION_KEY` env var must be configured in both the voice gateway and the web app. Both need to encrypt (web: when saving settings) and decrypt (gateway: when loading settings for a call). Document this in a deployment checklist.

### Twilio Media Stream Correlation

When Twilio calls the `/twilio/voice` webhook, we look up the caller ID, find the user, and generate TwiML with a `<Stream>` element. Pass the `userId` as a custom parameter in the stream URL (e.g. `wss://host/media-stream?userId=xxx`). When the media stream WebSocket connects, extract `userId` from the query string to load the correct user context. This avoids any timing/race issues between the webhook and the stream connection.

### save_memory Tool

The `save_memory` tool handler lives in `openai-relay.ts` as a special case -- it does not go through the action handler since it's not an email operation. When the model calls `save_memory({ key, value })`, the relay upserts directly into the `user_memory` table via Supabase. It is classified as `read_only` (no approval needed).

### Token Usage Tracking

The OpenAI Realtime API emits `response.done` events with `usage.input_tokens` and `usage.output_tokens`. The voice gateway accumulates these per session via `session-manager.addTokenUsage` and writes totals to the sessions table on disconnect.

9. User preferences persist across calls via the memory system
